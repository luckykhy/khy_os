  • web-quant：api/largeTasks.js 扩展 + views/TaskBoard.vue + 路由 /tasks + HOST_MENU_ITEMS 一项。
  • 两端 vite build 实测通过（各产出 TaskBoard-*.js 13–14 kB + CSS chunk）。

七条判据（新增/订正）#

  1. @khy/ui-shared 可以放 .vue，但 barrel 绝不能 import .vue ⇒ 否则任何 Node 消费者（node --test）一 import 就因无法解析 SFC 而崩。.vue 走 "./board/TaskBoard.vue" 子路径导出，"./board" 只出纯 JS。实测 pnpm 链接包被 Vite 视为源码，plugin-vue 正常处理，无需 optimizeDeps.exclude。
  2. 共享 SFC 刻意不用 <el-*> 标签：两端 Element Plus 注册方式不同 —— web-quant 全局 app.use(ElementPlus)；ai-frontend 用 unplugin-vue-components 按需自动导入且默认 exclude 含 node_modules。包外 .vue 里的 <el-*> 是否被解析器扫到属未验证边界，扫不到就是静默渲染为空（只有 console 警告）。改用语义化 HTML + 消费 Element Plus 的 CSS 变量（带兜底）。
  3. ⚠ 同一 app 内行尾不一致：apps/ai-frontend（router/index.js、useRoutePrefetch.js = CRLF；nav/index.js = LF）、software/khyquant/frontend（pluginManager.js = CRLF；router/index.js = LF）⇒ 补丁必须按各文件实际 EOL 归一化，否则要么「锚点 0 命中」，要么整文件每行都变（假 diff）。验收：git diff --numstat 的增量须等于真正加的行数。
  4. ⚠⚠ git grep 不搜未跟踪文件 ⇒ 校验本轮新增的守卫/组件（全未跟踪）用 git grep 会得假绿。校验工作区一律用 ripgrep 系（Grep 工具）。本轮我一度因此差点误判 F3/F5「已达标」。
  5. 前端状态知识必须单表化：首版散落三处（summarize() 的桶、TaskCard.vue 的 CSS 选择器、各处 status === 'x'）。后端加第 12 态会静默降级（卡片变灰、不计入任何摘要桶）。已收敛为 model.js 的 STATUS_TONE 单表，summarize 从色调派生、CSS 由 11 态选择器收敛为 4 类 data-tone，并由源码级测试钉住。⚠ 附带：列 id 与状态名同形（LANE_ORDER 含 'paused'/'failed'）⇒ 按状态名扫源码的断言必须先剔除列 id 声明，否则误报。
  6. 加路由端点必须同步路由清单守卫：tests/routes/largeTasks.errorPathsAndWatch.test.js 硬编码 routes.length（29→30）并列出全部 方法×路径。⚠ 该测试标题原写「30 个端点」而断言是 29（存量笔误），补上 /board 后两者才自洽。
  7. 沙箱下 vite build 会因 safe-delete 拦 dist/ 清空而失败（实测 164 文件 > 阈值 50，报 SAFE_DELETE_BULK_CONFIRM_REQUIRED）⇒ 用 --outDir <全新目录> 规避。判据：出现 ✓ N modules transformed 即证明跨包 SFC 已编译成功，失败发生在之后的写盘阶段。⚠ 删临时产物目录时 rm -rf 与 PowerShell Remove-Item 都会被同一 shim 拦（417 文件）⇒ 用 find <dir> -type f -delete + find <dir> -depth -type d -exec rmdir {} +。别把临时产物建在未 gitignore 的路径下（.khyos-build-check 一度污染 git status）。

新增判据（★ 高价值）#

  1. ★★ gate=advisory 是死指针：GATE_ORDER.advisory=4 > release=2 ⇒ 15 条（LAYOUT-005/006/007、API-004、TOOLING-003、DOCS-002、IR-001、DR-001、BACKUP-001、NOTIFY-001、OPS-002/003、FF-001、PROMPT-001、FE-004）任何门档都不跑。实测 rules:gate:commit 只跑 6 个执行器，这 15 条一个不出现。根因：gate 字段混装了两套语义（强度档位 + 执行方式标签）。正解：gate 只留 commit|pr|release|manual，观察期用 gate=commit + severity=advisory。
  2. ★★ p0-unenforced 红线被 kind=manual 绕过：红线条件是 priority==='P0' && kind==='unenforced'，而 kind 来自登记表字段、gate 不参与推导 ⇒ P0 规则只要 kind/gate=manual 就永久豁免。实测 PROCESS-001（P0 + manual + 零 exec）下 buildCoverage().redLines === []，且输出"阻断红线：全部通过"。这是合法的豁免后门。
  3. ★★ coverage.js 主动放弃阻断权：coverageCode() 只认 redLines + registry.errors；unenforced/orphans/unregisteredCheckers/externalRules 全不阻断。:166-168 注释明写"缺的是登记不是执行，故 --ci 下也不阻断"，把最大盲区（31 未登记检查器 + 35 未登记规则 ID）降级为"需人工裁决"——在 PROCESS-006 框架下 = 永久挂着。
  4. ★ check-staged-secrets.js（148 行，防密钥泄漏）真实挂在 .githooks/pre-commit:74）但登记表无对应规则；check-commit-message.js 同理。⇒「有实际在拦人的门，在规则体系里查无此规则」。
  5. ★ 台账 measured 靠手填、与实测长期脱节：cross-layer-require 台账 37 / 基线 39 / 实测 18；dangling-task 台账 98 / 基线 88 / 实测 76。两项都是 status=open ⇒ check-debt-ledger 只校验 closed 项 ⇒ 填错也没人发现。违反其自身 QUAL-1（基线必须是实测值）。
  6. ★ severity 缺失 78/87（90%）：新写的规则会带（8 条 advisory + 1 条 ratchet），存量普遍没有 ⇒ 强度落执行器默认值，priority 与实际强度无强制绑定。
  7. ★ 守卫自曝范围漂移只当 warning：check:json-schemas 打印"COMMS-002 登记的 paths 与本执行器实际扫描范围不一致，属待修缺陷"，但不影响 exit code、不进台账。paths 是 rules:apply 的输入 ⇒ 失真会让"改这个文件适用哪些规则"给出错误答案。

★★ 核心判据：问题是「模块化做了一半」，不是「没有模块化」#

  • SB/src/services/domain/ 已存在完整模块化骨架：31 个领域、610 个 .js

（trajectory 50 / messaging 49 / project 43 / network 41 / security 35 / maintenance 34 / state 31 / desktop 31 …）。

  • 旧轨未迁完：SB/src/services/ 根仍平铺 658 个 .js + 150 个目录 = 811 项

（认知负荷标准 5–9 ⇒ 超标 90 倍，是全仓最大热点）。

  • ⇒ 新轨/旧轨双轨并存 才是真问题。

★★ 判据缺陷（最高价值）：archDebtScan.js 不知道 domain/ 存在#
