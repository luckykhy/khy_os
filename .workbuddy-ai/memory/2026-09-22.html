⚠⚠⚠ 事故记录：git stash 误伤 3 个孤儿 stash（已恢复）#

发生了什么#

排查 pluginContribResolver 的既有失败时，我用了 git stash push -- <单个文件> 想临时对比 HEAD 版。
结果 git stash pop 失败（报 cannot apply a stash in the middle of a merge +
invalid object ... aiManagementKhyosWs.js），我误判为「这个 stash 只含我的改动」，
执行了 git stash drop ⇒ 把用户原有的 3 个孤儿 stash 全部弹掉/丢失。

根因（两条，都要记）#

  1. 本仓 git stash push -- <path> 不可靠：它创建的 stash 会替换整个 stash 栈的引用语义，

而不是安全地追加一条。本仓历史重建后对象库本就有损坏对象，pop 会失败，留下危险中间态。

  1. git stash drop 在任何情况下都不该由 AI 执行 —— 它删的是栈顶，

而栈顶未必是「我刚 push 的那条」。

如何恢复的（可复用流程）#

# 1. 找所有悬空的 stash 型提交（message 以 "WIP on" 开头）
git fsck --unreachable --no-reflogs 2>/dev/null | grep 'unreachable commit' | awk '{print $3}' \
  | while read h; do m=$(git log -1 --format='%s' "$h" 2>/dev/null); case "$m" in WIP\ on*) echo "$h | $m";; esac; done
# 2. 按原始顺序**倒序** store（后 store 的在栈顶）
git stash store -m "<原始描述>" <hash>
# 3. 若 `is not a stash-like commit` → 该 stash 的 tree 对象已损坏
git cat-file -t <hash>^{tree}   # fatal: Not a valid object name ⇒ 对象库缺失，无法恢复内容

恢复结果：3 个中 2 个完整恢复（tree 可读）；第 3 个（Shizuku 09-18）
tree 对象在仓库里从未存在（verify-pack 零命中）⇒ 属既有对象损坏，非本次造成；
已用 tag stash-recovered-shizuku-20260918 保留引用，并确认其 index 提交无内容变更（无实质损失）。

  • ✅ 发现工作区异常时先 git status + git stash list 留证，再动任何写操作。
