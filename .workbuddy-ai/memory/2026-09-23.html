⚠ 本次踩到的两个坑（都很隐蔽，务必记牢）#

坑 1：git mktree 默认模式必须带 type 字段。
正确格式是 <mode> SP <type> SP <sha> TAB <name>（如 100644 blob abc…\tfoo.js）。
若省略 type 只写 <mode> <sha>\t<name>，git 会把 100644 当作 <mode=1006><type=44…> 解析，
报 fatal: input format error: 100644 e41f0767…。
⇒ 我第一版 rebuild-two-trees.js 就是这个 bug，导致 deploy/free-test/apps 与
services/ai-backend/test 静默未重建（脚本没报错，只是 sha 对不上）。
补充：git mktree --batch 的格式又不同（不含 type），别混用。

坑 2：sha 不一定是"目录自身"的 sha，可能是其子目录的 sha。
0373bcce 我最初以为是 …/doubt-driven-development 目录的 sha，
实际是它 references/ 子目录的 sha（父目录是 39b12d16）。
⇒ 判"某路径缺失"时，不能只按父路径建树后比 sha；要自顶向下逐层定位
（对每层每个子目录做 cat-file -t <sha> 存在性判定），别只按预期路径猜。

坑 3（方法论）：ls-tree -r <top> 遇缺失树会"中止并报错"，但 > /dev/null 后
你只能看到"有错"，看不到"到哪一条中止"。 本轮 ls-tree -r HEAD 的输出条数
234 → 692 → 5481 → 9978 是逐步推进的进度指标，比 grep 错误信息更可靠。

定位缺失树的正确姿势（本轮最终采用，可复用）#

⚠⚠ 新发现的严重事故：分支引用 refs/heads/chore/tui-ux-nightly 曾丢失#

现象与根因#

执行 git reset -q HEAD 时报 fatal: unable to read <blob sha>，
但即使把该 blob 用垫片补好，reset 仍失败，且 git rev-parse HEAD 报
fatal: ambiguous argument 'HEAD'。

⇒ 真根因不是 blob 缺失，而是 refs/heads/chore/tui-ux-nightly 这个 ref 文件不存在：
.git/refs/heads/chore/ 整个目录都没有，packed-refs 里也没有它。
cat .git/HEAD 显示 ref: refs/heads/chore/tui-ux-nightly（符号引用指向一个不存在的 ref）
⇒ HEAD 无法解析 ⇒ 所有依赖 HEAD 解析的命令（reset / checkout / status / read-tree HEAD）全炸。

报错信息完全误导：它报的是「某个 blob 读不到」，
真实原因是「HEAD 这个 ref 不存在」。这是最容易误诊的一类故障。

抢救过程（可复用）#

  1. git update-ref refs/heads/<name> <sha> 在这个状态下会「静默失败」

（返回 0 但不写盘、git show-ref 仍查不到）。
⇒ 必须直接写文件：

   mkdir -p .git/refs/heads/chore
   printf '<sha>\n' > .git/refs/heads/chore/tui-ux-nightly
  1. sha 从哪来：本轮成功之处在于修复前抓了引用快照

.khyos/diag/refs-snapshot-before-repair.txt，
里面有 refs/heads/chore/tui-ux-nightly e86bbf6dcc5782dd4976c805d7fe9e955d9cd984。
⇒ 教训：动任何 git 内部状态之前，先 git show-ref > snapshot.txt。
本轮正是靠这个快照才救回来；否则只能从 git fsck 的 dangling commit 里猜。

  1. 恢复后 git status / rev-parse HEAD 立即正常。

附带发现：git update-ref 与 git replace 的一个坑#

  • git replace <缺失对象> <目标> 会报 failed to resolve '<sha>' as a valid ref

⇒ 因为 replace 要求被替换对象必须存在。
绕过方法：直接 git update-ref refs/replace/<缺失sha> <目标sha>。
（注意这条路正是上面「update-ref 可能静默失败」的场景，写完必须 git replace -l 复核。）

关于 stub blob（对象垫片）的取舍 —— 必须写清#

原始内容丢失的 blob，二选一：

  • (a) 让它保持缺失 ⇒ reset/checkout/read-tree/diff 全都不可用，仓库等于废掉；
  • (b) 用工作区内容写一个名为该 sha 的 loose 对象 ⇒

git 正常读取路径可用，但 git fsck 会报 hash mismatch
（因为 sha1("blob <len>\0"+content) ≠ 文件名）。

本仓选 (b)，理由：可用性 > fsck 洁净度。已在审计表里如实记录。
脚本：.khyos/diag/shim-all-missing.js（自动从 HEAD 树里找缺失 blob，
注意不能只看 index——reset 读的是目标树，不是 index）。

⚠ 另一条重要教训：git reset 失败时的「假安全」#

git reset -q HEAD 失败后，暂存区会残留 9,978 条（等于「index 相对 HEAD 全量新增」），
状态显示为 AM（staged-add + worktree-modified），看起来像「有一条超大批次待提交」。
⇒ 千万别在这个状态直接 git commit（会提交上万文件）。
判据：git diff --cached --name-only | wc -l 若接近 git ls-files | wc -l，就是 index 失同步，不是真有改动。

正确复位姿势：git read-tree HEAD（只改 index，不动工作区）。
git read-tree HEAD 需要 HEAD 可解析 ⇒ 先修 ref，再 read-tree。

对象库损伤的「可达性」陷阱（fsck 计数会骗人）#

加完 4 条 git replace 后，git fsck 的计数变差了：

这不是新损伤，而是 replace 让 fsck 多遍历了此前不可达的区域
（4 条桥接链 + 135460c8 的整棵子树），把本来就存在的缺失对象暴露出来了。

⇒ 判据：fsck 计数不是单调指标，它依赖「可达集」。
比较前后必须固定可达集，或者改用「对象库内对象数」这类绝对指标。

  2. 我重建的 5 棵树 cat-file -t 全部仍是 tree；
  3. git ls-tree -r HEAD 仍是 9,978 条。

⇒ 零新增损伤，结论成立。

★★ 修复了一个全仓级潜伏 bug：MSYS 路径喂给 Windows Node ⇒ MODULE_NOT_FOUND#

现象#

第一次成功提交后，post-commit 钩子崩了：

Error: Cannot find module 'D:\d\Portable\khy-os\scripts\sync\mirror-sync.js'

注意那个 D:\d\Portable\ —— 多了一层 d。

根因（已复现，铁证）#

步骤结果
Git Bash 里 cd /d/Portable/khy-os && pwd/d/Portable/khy-os（MSYS 风格）
把它交给 Windows 版 nodepath.resolve('/d/Portable/khy-os') → D:\d\Portable\khy-os

⇒ Windows Node 把开头的 /d 解释为「当前盘符 + 名为 d 的目录」，
不是 MSYS 的「D 盘」。于是拼出的路径根本不存在。

scripts/sync/push-mirrors.sh 里是：

ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/../.." && pwd)"   # -> /d/Portable/khy-os
node "$ROOT/scripts/sync/mirror-sync.js" push ...           # -> D:\d\Portable\... 炸

修复#

在把路径交给 node 之前，用 cygpath -w 转成 Windows 风格：

NODE_ROOT="$ROOT"
if command -v cygpath >/dev/null 2>&1; then
  NODE_ROOT="$(cygpath -w "$ROOT")"     # -> D:\Portable\khy-os
fi
node "$NODE_ROOT/scripts/sync/mirror-sync.js" push "${ARGS[@]}"

三处同样隐患已一并修复（用 git grep -n 'node "\$[A-Z_]*/' 找出来的）：

  • scripts/sync/push-mirrors.sh:41（post-commit 钩子调用链，每 commit 必炸）
  • khy.sh:26（khy repair 子命令）
  • scripts/release/publish-dual.sh:293（发布时的 toolchain pin 门）

判据（可复用）#

只要 .sh / .githooks 里出现 node "$<大写变量>/*.js"，
且该变量来自 pwd，在 Windows + Git Bash 下就是 MSYS/Windows 路径混用 bug。
判别命令：git grep -n 'node "\$[A-Z_]*/' -- '*.sh' '*.githooks'
修法：在传给 node 前 cygpath -w。
反之，纯 bash 内部使用（cd "$ROOT" / ls "$ROOT/..."）不受影响——
因为 MSYS 的 coreutils 认识 /d/...。只有跨到 Windows 原生程序（node/python.exe）才出问题。

附带发现：post-commit 崩溃会连带丢掉分支 ref（严重）#

第一次提交时 post-commit 抛 MODULE_NOT_FOUND（退出码非 0），
结果 refs/heads/chore/tui-ux-nightly 没有被写入 ⇒
git log 报 "does not have any commits yet"，但提交对象 710cb4e9 其实已完整落盘
（git cat-file -t = commit，parent = e86bbf6d，正确）。
⇒ 抢救：直接从 git show --stat / cat-file 拿到完整 sha，写 ref 文件即可。
⇒ 教训：post-commit 钩子必须保证 exit 0（本仓 push-mirrors.sh 末尾确实有
exit 0 兜底，但它自己在更早的地方被 node 的 MODULE_NOT_FOUND 打断前就先失败了——
实测 || true 也没能兜住，因为崩溃发生在 node 进程内部且 bash 的 set -u 不是原因）。
结论：钩子里的 node 调用要加 || true 且要在同一行内兜住。

★★ 重大更正：ref 丢失的根因不是「钩子崩溃」，是「钩子被网络推送阻塞」#

上面那条「教训」的归因是错的，此处更正。前两次确实像崩溃，第三次用 ps 抓到了真相。

真相（第三次复现时的现场）#

第三次「ref 丢失」时进程表显示全部还在跑：

13760 ALIVE  git commit -m "fix(scripts): ..."
13782 ALIVE  bash .githooks/post-commit
13787 ALIVE  bash scripts/sync/push-mirrors.sh --non-interactive
13795 ALIVE  node scripts/sync/mirror-sync.js push --non-interactive --branch=chore/tui-ux-nightly

⇒ git 是同步执行 post-commit 的，只有钩子返回后 git 才去写
refs/heads/<branch>。而 mirror-sync.js push 在等远端（https://ghfast.top）
凭据时无限期阻塞 ⇒ 钩子永不返回 ⇒ ref 永不写入 ⇒ git log 报
"does not have any commits yet"，但提交对象其实早已完整落盘。

这一条解释了三件事：① 报错信息误导（报 ref 不存在，实为钩子未返回）；
② || true 兜不住（|| true 只在命令返回后才生效，而它根本没返回）；
③ 三次都发生在提交之后（正是 post-commit 阶段）。

判据（下次遇到「ref 莫名丢失」先跑这条）#

ps -ef | grep -E "mirror-sync|push-mirrors|post-commit" | grep -v grep

有存活进程 ⇒ 是阻塞，不是崩溃（崩溃的话进程早没了）。
⚠ 别急着写 ref —— 原地写会被钩子返回后的 git 覆盖；先决定等还是终止。

修复（已落地）#

scripts/sync/push-mirrors.sh：给网络推送加有界墙钟预算（默认 120s，
KHY_MIRROR_PUSH_TIMEOUT 可覆盖），超时即放弃推送并留
npm run sync:mirrors:retry 提示 —— 永不阻塞提交。
这正是本仓 RUNTIME-003（活动式超时）在自己的钩子上的应用。
有 timeout 走 timeout --kill-after=10；否则退化为「后台跑 + 轮询收割」。

★★★ 前端控制台 404/500 + WS 反复失败：四条根因，全部定位并修复#

用户报的控制台错误：/api/auth/sessions 404、/api/api-keys/current 404、
/api/proxy-subscriptions 500、/api/ai-gateway/payments/my-customer 404、
/api/workflow 500、/api/user-gateway/* 全部 500、
ws://127.0.0.1:8090/ws/cross-platform 反复失败。

四条独立根因叠加，缺一条都修不好：

根因 1（最致命）：daemon 与 web 后端抢同一个端口 3000#

  • services/backend/start-daemon.js 兜底端口写死 '3000'；

而 web 后端 serviceDefaults.BACKEND_PORT = PORT || 3000 也是 3000。

  • 更要命的是 daemon 绑 127.0.0.1:3000、web 后端绑 0.0.0.0:3000，

Windows 下更具体的绑定优先 ⇒ 浏览器访问 127.0.0.1:3000
全部落到 daemon 上，web 后端等于隐身。

  • 铁证（A/B）：同一路径两个地址返回两个不同服务
    • 127.0.0.1:3000/api/auth/sessions → Authentication required (set AI_MGMT_AUTH_TOKEN…)（daemon）
    • 192.168.1.193:3000/api/auth/sessions → 未提供认证令牌（web 后端）
    • netstat 同时显示两条 LISTENING：0.0.0.0:3000(server.js) + 127.0.0.1:3000(start-daemon.js)
  • 端口真源是 serviceDefaults.AI_BACKEND_DEFAULT_PORT（9090），

apps/ai-frontend/backendDiscovery.mjs 镜像同一个值，
测试 serviceDefaults.test.js 明写「AI backend default port is the single source mirrored by the frontend」。

  • ✅ 修：start-daemon.js 改为 argv[2] || KHY_DAEMON_PORT || serviceDefaults.AI_BACKEND_DEFAULT_PORT，

并刻意把 process.env.PORT 从优先级里移除（PORT 是 web 后端的，让 daemon 也读它会把两者钉在同一端口）。

根因 2：WS 握手协议错配 —— 客户端发 auth:request，服务端只认 auth#

  • 协议真源 crossPlatform/shared/protocol.cjs：ClientMessageTypes.AUTH = 'auth'。
  • 但 vite 实际加载的 ESM 版 wsClientCore.js（.js 优先于 .cjs）

在 handleHello 里硬编码 'auth:request' —— 这个值根本不在协议表里。

  • 服务端 syncServer.js 的 switch 没有该 case ⇒ 走 default 回

{type:'error', error:'Unknown message type: auth:request'} ⇒ 客户端卡在
AUTHENTICATING，10s 超时后断开重连 ⇒ 控制台刷屏。

  • .cjs 孪生件是对的（用 authMessage()），只有 ESM 版跑偏；

而单元测试把错误字面量固化成了断言（expect(frame.type).toBe('auth:request')）。
⇒ 判据：测试断言的是实现还是真源？改真源前先确认哪边是权威。

  • ✅ 修：ESM 版改为 import { ClientMessageTypes } from './protocol.cjs' 并用 ClientMessageTypes.AUTH；

测试同步改为引用真源常量（不再写字面量）。

  • 探针（可复用）：.khyos/diag/ws-handshake-probe.js <port> —— A/B 两种 type 各握一次手，

实测输出：A Unknown message type: auth:request（握手失败）/ B auth:ok, platforms:{web:1}（成功）。

根因 3：syncServer 心跳把每个客户端 60s 后踢掉#

  • attach() 里 30s 一次心跳：置 ws.isAlive = false 然后 ping()，

下一轮若仍为 false 就 terminate()。

  • 但全文件没有任何 'pong' 监听，也没有初始化 isAlive = true

⇒ 第 1 轮(30s)置 false，第 2 轮(60s)必杀。所有客户端无一幸免。

  • ✅ 修：_handleConnection 里加 ws.isAlive = true + ws.on('pong', () => { ws.isAlive = true; })。

根因 4：空闲看门狗看不到 syncServer 的客户端（上一轮已修，此处补验）#

  • server.js 的 getActiveWsClientCount() 只数 app 级 wss.clients，

而浏览器 socket 在 syncServer 自己的 _wss.clients 里 ⇒ 永远 0 ⇒ 60s 后
No frontend clients connected for 60s, shutting down to release port。

  • ⚠ 单独修根因 4 是无效的：_clients 只在收到 auth 后填充，

在根因 2 未修时浏览器永远进不了 _clients，计数照样是 0。
⇒ 这是个"修复依赖顺序"的典型：必须先修 2，再看 4 是否真的生效。

  • ✅ 验：.khyos/diag/idle-shutdown-live.js <port> <idleMs> ——

连上并完成 auth，等过看门狗窗口：
修前 WS CLOSED；修后 WS OPEN + health 200。100s 长窗仍 OPEN（根因 3 也修好了）。
