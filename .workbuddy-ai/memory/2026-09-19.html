★ 三个实测得出的新判据（值得进长期记忆）#

  1. ⚠⚠ 执行器强度写死 warning ⇒ STAGE 常量变成装饰。

初版所有 finding 都 SEV_WARNING，结果 S1 与 S3 跑出完全相同的输出与退出码
⇒ 升到 S3 后仍然不拦截，而所有守卫全绿（登记表说 S3、源码常量 S3、漂移比对也过）。
表现恰好伪装成 S1 的预期行为 —— 与 [DESIGN-ARCH-113] 踩过的坑同形。
修法：severityFor(criterion) 单点派生（按阶段 + R/S 判据）。
验收判据：同一改动集在 S1/S3 下 Summary 的 error 数必须不同
（实测：S1 0 error exit 0；S3 1 error exit 1）。这条已写成测试用例。

  1. ⚠ 测试副本不能落在 scripts/ci/。

初版把 S3 副本写 scripts/ci/_ct-timing-S3.js，而那正是 check-wiring.js 的扫描范围 ——
测试跑的几秒里另一个终端跑 check:wiring 会看到它「零接线」而报 1 error，
且间歇性、极难归因（「没改任何东西却突然变红」）。
⇒ 副本落 scripts/.ct-timing-tmp/：仍是 scripts/ 子目录（__dirname/../.. 推根层数不变），
但不在任何守卫 glob 里。推论：任何「临时脚本」都不要放守卫的扫描目录。

  1. ⚠ --files=（空值）与「未提供 --files」必须可区分。

初版 argValue() 对两者都返回 '' ⇒ 空 --files= 会静默 fall through 到真实暂存集，
在本仓读到 3993 项。调用方以为在测空集，其实在测仓库现状。
⇒ 单开 filesArgOrNull() 返回 null。

  1. --changed 必须读 --cached（暂存区）而非工作区全量。

本仓工作区长期 3000~4000 项未提交，按全量判会得到「跨 10 板块 / 3993 文件」
这种真实但不可行动的结论 ⇒ 4 条 finding 变成常驻噪声 ⇒ 噪声被整体忽略
（比没有守卫更糟）。暂存区 = 提交单元，且与 .githooks/pre-commit 的
git diff --cached 对齐。工作区视角保留为显式的 --worktree。

  const dangling = [];
  for (const area of (maintainerMap && maintainerMap.areas) || []) {
