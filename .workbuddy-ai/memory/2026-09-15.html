关键结论（后续会话可复用）#

  • MCP 是"半边合规"：工具面（权限门控、名称归一化防注入、注解映射）很规范；

协议面有硬缺口 —— PROTOCOL_VERSION='2024-11-05' 在 mcpServerProtocol.js:49 与
mcp/index.js:43 两处独立硬编码，且 buildInitializeResult 完全不读
params.protocolVersion（无协商）。客户端三处把 ServerCapabilities 当
ClientCapabilities 上报（index.js:523-527/574/641）。

  • MCP HTTP server 缺 Origin 校验（mcpHttpServer.js:142-224）→ P0：

loopback 绑定挡不住浏览器跨站调用，而该 server 默认暴露全量工具含 shell。

  • A2A 是"名义合规"：存在两套互不相通的东西 —— 真 A2A 出站客户端

（services/a2a/index.js，仅 127 行）与借 A2A 之名的私有 ACP 方言
（acpTransport.js 的 agent.spawn/task.submit 等，ACP_PROTOCOL_VERSION='1.0'）。
内部代码大量引用 a2a* 命名造成"已实现 A2A"的错觉。

  • 实测确认的硬 bug：a2a/index.js:62-63 传 'Authorization': undefined /

'X-User-Id': undefined。Node 22 对 undefined header 值同步抛
ERR_HTTP_INVALID_HEADER_VALUE，被 :40-42 的 catch 吞成 {status:0}。
→ 未配 KHY_A2A_API_KEY 时 sendMessage/createTask 100% 静默失败。

  • 工具调用循环是全仓最强项：11 个死循环检测器（toolLoopDetector.js）、

9 类终止路径、MAX_ITERATIONS=100 可 env 覆盖并 clamp。
缺口在"证明它正确跑完"：无逐轮 journal（orchestrationJournal.js 仅子代理用，
主循环零引用）、结果层无 schema 校验、可观测性默认关。

  • 仓库内标准不一致是系统性问题：同一件事常有"做对"和"做错"两个版本

（CORS 白名单 vs '*'；全局错误中间件 vs 直出 err.message；
spawn 无 shell vs execSync 拼串；ACP 有 JSON Schema vs MCP 结果层无校验）。

方法沉淀#

  • 审计这类超大仓库，Grep 全仓会 30s 超时 —— 必须先 Glob 定位目录再限定路径搜索；

.research-tmp/ 是第三方参考代码（opencode 等），必须排除，否则结论失真。

  • 关键行为断言要实测（如 undefined header），不能只靠读码推断。
  • 自拟了一套循环完整性判定规范 LC-1~LC-7（有界性/终止完备/进度性/可恢复性/

可观测性/取消传播/结果保真），已在报告第三部分给出可执行判定标准与逐条判定结果。

M8 — 401 补 WWW-Authenticate + 移除 ?token=#

M6 — MCP-Protocol-Version 头#

  • 新增纯函数 checkProtocolVersionHeader()；rejectBadProtocolVersion() 挂三个分支入口。
  • 刻意的取舍：规范说缺头应假定 2025-03-26，但本仓没实现其流式语义，照抄＝假兼容。

故缺头回落「本服务端支持的最高版本」并标注 assumed:true。

  • 回归锁：PROTOCOL_VERSION_HEADER 必须全小写 —— Node req.headers 键全小写，

写成驼峰会永远取不到值而静默走"缺头"分支。

M7 — 会话校验#

  • 改造前「回显或现签」＝会话 id 是装饰品。现在 initialize 签发并记账，

其余请求须带已知 id 否则 404；DELETE /mcp 销会话回 204。

  • 会话表拆两张：sseSessions（→ stream）与 streamSessions（→ 记账）。

生命周期不同，混一张会让 DELETE 误关别人的 SSE 流。
