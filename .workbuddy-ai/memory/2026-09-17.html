版本管理与发布触发规则（DESIGN-ARCH-118 / PROCESS-005）#

背景：用户要求新增「版本管理」规则，覆盖 ①何时 bump ②命名与递增 ③何时/如何推 GitHub+Gitee
④哪些操作自动触发（避免人工判断发布时机）。

产出：docs/03_DESIGN_设计/[DESIGN-ARCH-118] 版本管理与发布触发规范.md（+ .html 孪生件，
已回写 00_INDEX_设计-分类索引.md）。编号 118 实测可用（117 = 当前最大）。

调研到的硬事实（可复用）：

  • 版本真源 9 源三轨道：G1 主包 4 源 / G2 ai-backend 3 源 / G3 浏览器 UI 3 源（G2 已从 2 → 3，

plugin-sdk 入 G2）。G1 必改 3 处：pyproject.toml、packaging/npm/package.json、
services/backend/package.json；第 4 处 packaging/modules/modules.json 由构建维护。

  • check-version-sync.js 的 isSemver = ^\d+\.\d+(?:\.\d+)?$（容两位，但本仓按三位收口）；

另有反硬编码闸：platform/khy_platform/__init__.py 写死 __version__ 即 fail。

  • CHANGELOG 锚点是 pyproject（changelog-new.js --check）→ 顺序必须「先写 CHANGELOG 段再 bump」。
  • 触发链路实测：dual-channel-release.yml ← push: tags:['v*'] + workflow_dispatch；

sync-gitee.yml ← push: branches:[main,master]（只同步分支，不含 tag）；
pr-gate.yml ← PR 到 main。当前分支 = main，master 是影子（6 个 workflow 都列了两者）。

  • 发布通道仍手动：publish-dual.sh 头部自述「不带 --tag = 只发包，不 push——版本红线需人另行点头」。
  • release-gate.js 是薄壳，阶段定义在 scripts/release/lib/releaseGateStages.js（tier must/recommended）。

规则要点：bump 三触发 T1/T2/T3（按 CHANGELOG 段落可机判）+ 四条不 bump；三轨道独立递增、
禁对齐；推送分层「main 推代码、tag 推发布」，先 main 后 tag；自动链路 A1–A4 + 四条硬阻断
（check-version-sync / changelog --check / release-gate / tag 与 pyproject 相等），
禁止把四条改成 continue-on-error。

关键边界（写进规则，勿忘）：本规则只自动化「推 tag 之后」的长链路，
不触碰 PROCESS-001（P0）的「AI 不得自动 push」红线 —— 人工只在「推 tag」处点头一次，
之后不允许第二次人工判断。要自动化推 tag 必须先改 P0 并单独评审。

交付边界：本次只交付规则条款（设计真源）。登记表条目 + check-release-triggers.js
守卫 + pr-gate.yml 接线属实现，按 SOURCING-006「一次提交只做一步」另起提交。

副作用已点明：跑 scripts/docs/build_docs_site.js（不加 docs:build 前缀，避免联网
ensure-mermaid）重写全站陈旧孪生件 —— 本次实测 288 个 .html 变更。
docs:verify 通过：996 md / 997 html / 11945 链接全绿。

五条硬约束（全部实测，勿重复调研）#

C1 🔴 路径自推算是阻断性约束：hq_common.py:26-29 靠自身位置向上四级推
PORTABLE_ROOT，find_khyos() 取 <PORTABLE_ROOT>/khy-os。HQ 现位于
D:/Portable/Projects/khy-os-hq → PORTABLE_ROOT=D:/Portable → 能找到 khy-os ✅。
HQ 一旦嵌进 khy-os 内部（如 khy-os/Projects/hq/）→ PORTABLE_ROOT 变
khy-os/Projects → 去探测 khy-os/Projects/khy-os（不存在）→ 7 个脚本集体失效。
且只能改探测算法（不能写死路径，会违反 HQ 第一铁律）。

C2 🔴 hq_check 会拿整个 khy-os 当自己的源码扫：iter_files() 只跳
{.git,node_modules,__pycache__,logs}，会递归进同级树。嵌套后扫描量 35 → 3985 文件；
check_portability 会对 khy-os 的 407 个含盘符引用的文件报 ERROR
（khy.bat、platform/khy_platform/*.py、scripts/release/*.ps1 等）
→ hq_check 永远不可能全绿 → sync.py 收工门禁永久卡死 → 自动同步瘫痪。

比undefined更致命：C1 是"找不到"，C2 是"必然红"。

C3 🔴 根文件正面冲突：HQ 与 khy-os 根目录都有 README.md/AGENTS.md/CLAUDE.md；
会撞 khy-os check-repo-layout.js:124 的 ROOT_DOC_WHITELIST 与 DESIGN-LAY-005 §1.3。

C4 🟠 有真实前科：khy-os/.gitignore:172-180 明文记录 —— tools/deepseek-eyes
曾是 phantom git link（mode 160000、无 .gitmodules），嵌套仓库无法在 clone 时检出 +
本地 HEAD 漂移使 worktree 永脏 → 双机 autopull 的 --clean-only 永不触发
→ 任务闭环永不关闭。这段就是本次合并的预言。

C5 🟠 指令文件冲突：khy-os AGENTS.md 已 42155 字节且走 compat 链（无预算不截断）；
HQ 另有 AGENTS+CLAUDE 且 hq_check drivability 强制双入口同步。合并 → 角色打架；
保留两份 → 需给 DOCS-003 场景矩阵补新形态。

认知纠偏（关键）#

搬家被否 ≠ 目标不可达。用户要的是「废弃这个仓库」，不是「把目录挪进去」。

  • 搬家的死因：HQ 7 脚本靠向上四级推算 PORTABLE_ROOT（hq_common.py:26-29）定位 khy-os，

嵌进去就找不到宿主；hq_check.py 会递归自扫整个 khy-os（35 → 3985 文件）必然报错。

  • 不迁移脚本、只迁移数据与知识 → 上述两个死因同时消失。

khy-os 已有承接件（实测，无需新造）#

  • .ai/ 已入库（git ls-files .ai = 4 个 .md + .html 孪生件；

git check-ignore .ai 无输出）→ 已有「入库状态目录」先例。

  • .khy/、.khyos/、.khyquant/ 均 gitignore（本机态）→ 别把 HQ 数据放这里。
  • khy-os 自带 3 远端（origin/gitee/khy-mirror）→ HQ 的 sync.py 是多余的一层编排。
  • 任务基础设施约 30 个模块（taskControlService/taskClosure/taskScheduler/planModeService/

goalModeService/todoStorePath…）；src/cli/handlers/ 152 个自注册 handler；
scripts/ci/ 61 个检查器 + ruleguard。

落点判据（实测）#

  • .ai/hq/（数据）+ .ai/hq/prompts/（19 提示词）← 推荐。

根级 prompts/ 会被 check-repo-layout.js 的 layer-registry 判「未登记目录」

被显式排除在层级体系外（check-repo-layout.js:395）→ 放 .ai/ 下免登记例外。

  • 命令面：khy hq <status|next|verify|bug new|bug set|task set>。

⚠️ 不要新建第 62 个检查器（重要纪律）#

HQ 的 7 组检查大半应删除或降级，而非搬进 scripts/ci/：

  • 删：portability（khy-os 对应 RUNTIME-001 已有守卫）、autopull_task、sync_readonly、merge_flow
  • 降级为命令写入路径校验：meta（JSON↔MD 一致性）
  • 并入 DOCS-003 场景：prompts、drivability

理由（MEMORY §七.2）：新检查器落 scripts/ci/ 即被 check-wiring.js 要求有门引用；
HQ 这些是自有流程自检，搬进 CI 属职责错配。
判据：能落在命令写入路径上的约束，就不要升级成仓库级门禁。
