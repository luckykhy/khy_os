偏差 ① —— ./ 边不等于「兄弟边」：规范 §1.3 用 ./ 前缀判定兄弟边，
但 services/ 是一个 808 条的平铺巨目录，家族文件的 ./xxx 绝大多数指向父目录里的其他文件
（如 require('./flagRegistry')、require('./capabilityMatrix')，后者还是目录 index）。
⇒ 正确判据是解析目标落在哪（同族目录内 / 父目录 / 目录 index），不是前缀字符串。
修法：迁移后逐条 path.resolve 试解析——能解析则保留，否则升一级 ../。

偏差 ② —— 留壳使父目录条目数 +1，不是 −N（最严重）：
classifyEntry 只看名字、不看内容 ⇒ 壳被计入 counted（EXEMPT_NAMES 无 shell/re-export 概念）。
对 N 个文件的家族：移动前顶层 = N 文件；移动后 = N 个壳 + 1 个新目录 ⇒ 净 +1。
只有 §4.2 的壳清理条件满足后删掉 N 个壳，才真能 −N+1；
而 §4.2 写「存在超过一个大版本且入边降为 0」才强制删 ⇒
在壳清理之前，规范主张的「拆分使可发现性预算下降」在守卫读数上不成立甚至反向。
⇒ 步骤 3 若按原计划把 flat-overflow 升 error，会把「照 §4 做完示范批」的目录判红。
