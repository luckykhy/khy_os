修复 khy 启动慢（用户报「启动太慢」）#

诊断方法（可复用）：① STARTUP_PROFILE=1 跑 bin/khy.js 看 startupProfiler 检查点时间线（注意 process.exit() 会跳过 .finally() 里的 printSummary()，需要外层 wrapper + process.on('exit') 兜住）；② 包一层 Module._load 统计模块自耗时（父减子），定位"千刀万剐"型 require 图；③ --cpu-prof + 自写脚本按 callFrame 聚合 self time 并回溯祖先栈；④ 包一层 child_process.*Sync 打印慢派生的调用栈。

实测三处真凶（都在 Node 侧，Python 侧 bootstrap 仅 ~350ms 且已并行化）：

  1. init.js 的 DB 体检"假延后"：Promise.resolve().then(_initDbHealth) 看着像后台，但微任务会在调用方 await init() 的续体之前排空 → PRAGMA quick_check 的同步突刺（28MB sessions.db ~450-850ms）照样卡在 init:done → main:start 之间，实测 ~1100ms 空档。→ 改成 setTimeout(..., KHY_DB_HEALTH_DEFER_MS 默认 2500) 宏任务 + unref()。
  2. khy-Trajectory/sessions.db 是 .khy/sessions.db 的硬链接（utils/dataHome._ensureVisibleAlias 每次启动重建的可见别名，同 inode 同 realpath），_discoverDatabases() 两条都收 → 同一个 28MB 文件连做两遍 quick_check。→ _dedupeByRealPath() 按 realpath 去重（Windows 转小写），导出供测试。
  3. bin/khy.js:308 顶层 execFileSync(chcp.com, ['65001'])：控制台代码页是进程共享的，而 Python 启动器 cli.py 早已用 SetConsoleOutputCP/SetConsoleCP 设过 65001 → 这次同步 CreateProcess 纯属重复，实测 230-475ms。→ cli.py 成功设置后导出 KHY_CONSOLE_CP=65001 握手；khy.js 见到握手就跳过，直连 node bin/khy.js 仍保留旧派生。

收益：main:start（启动路径解锁点）~1696ms → ~260-330ms；--no-server 整进程 2720-3166ms → 1202-1289ms；init() 自身 1471ms → 127ms。约省 1.5-1.9s。

改动文件：services/backend/src/bootstrap/init.js、services/backend/src/services/dbHealthService.js（+导出 _dedupeByRealPath）、services/backend/bin/khy.js、platform/khy_platform/cli.py、新增 services/backend/tests/services/dbHealth.dedupeDatabases.test.js（node:test，5 例）。

验证：node --test 三个 dbHealth 套件 30/30 绿；node --check 全绿；check-flag-registry.js 通过；实跑确认延后体检确实在 +2.5s 执行且审计落盘（现在只查 2 个库）。

未解决 / 后续可做：

  • 延后体检在 +2.5s 仍会阻塞事件循环 ~0.9s（better-sqlite3 是同步的）。彻底解法是丢 worker/子进程，改动较大，未做。可用 KHY_DB_HEALTH_DEFER_MS 调。
  • 剩余大头：require('../src/cli/repl') ~1.1-1.6s（420+ 模块，无单点热点，见 [DESIGN-PERF-001] 卡点 A）+ import('ink') ~1.4s。NODE_COMPILE_CACHE 实测无明显收益（且 khy.js:51-55 已因开发期陈旧字节码问题主动禁用）。
  • 环境债：khy_os.egg-info / 已安装元数据停在 1.1.11，源码树是 1.1.15 → khy --version 报错版本，且每次启动都触发 _check_version_upgrade「token 缓存将强制刷新」。需刷新 editable 安装元数据。

方法：自研零依赖静态分析器（对齐 archDebtScan.js 的「零外部依赖 / 确定性 / 离线可跑」纪律）。
依赖图 → 入口可达性 BFS → 孤儿文件 → 代码语境引用反查 → 三级置信度分类。全程只读，未改任何业务代码。

产物（.khyos/deadcode-audit/，该目录已被 .gitignore 第 65 行 .khyos/ 覆盖，不污染仓库）：

  • deadcode-scan.js 主扫描器 · verify-orphans.js 引用反查 · classify-refs.js 引用强度分类
  • generate-report.js → khy-os-死代码诊断报告.md（823 行）
  • 数据：deadcode-report.json / orphan-verdict.json / ref-classification.json

规模：3921 源文件 / 823 入口 / 3208 可达。
结果：孤儿 713（18.2%）= A 确证死代码 129 + B 重名副本 321 + C 其余疑似 242；
另有冗余导出 844、未使用依赖 27、文件内死声明 156、垃圾文件 20。A 类抽验 6/6 准确。

关键发现：

  1. software/khyquant 的 Python 业务层整体不可达 —— khy_quant/cli.py 是纯启动器

（subprocess.run([node, bin/khy.js]) 交出控制权），app.py 只是底座适配器，
没有任何 .py import services/ / models/ / routes/ / ml/。

  1. software/khyquant/models/ 9 个 model 是 platform/packages/shared/src/models/ 的旧副本

（活的引用走 require('@khy/shared/models')）。

  1. khyquant 前端多套并行实现：6 个 K 线图组件（Simple/RealTime/Enhanced/Lightweight/Strategy/Professional）、

5 个交易面板组件并存，路由只挂其中一条链。

  1. 一批 CI 脚本（check-f2e-spec / check-f2e-wiring / check-core-safety / security-scan 等）

不在任何 npm script 里，即从未被 CI 执行。

  1. 根目录与前端目录共 20 个 shell 引号转义事故垃圾文件（-p / 1 / console.log(r)) / {if(l.includes(... 等）。

扫描器踩过的坑（重要，下次别重蹈）：

（扫 handlers/，150 个）、software/khyquant/tools/index.js。漏掉会让 tools/ 与全部 handler 被误判为死代码。

硬编码到 ai-frontend 会整条路由链断裂，khyquant 前端孤儿一度虚高到 124 个。
