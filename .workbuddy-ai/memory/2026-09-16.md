## 修复：khy-os TUI「输出回显看不见」+「滚轮回溯历史记录」

朋友报的两个缺陷（3 张截图，窗口最大化 + 小窗口）：

1. 窗口最大化后所有输出回显都看不见；小窗口下同样看不到输出内容。
2. 鼠标滚轮会「回溯历史记录」，期望像 Claude Code —— 输入框固定在底部，内容区正常滚动。

### 根因（全部经无头 harness 实证，不是推断）

**A. 转录被 ink 的 fullscreen 清屏抹掉，且抹掉后不重画**

`node_modules/ink/build/ink.js:320` 的 `isFullscreen` 看 `outputHeight`，但**真正清屏的分支条件
是 `this.lastOutputHeight >= this.options.stdout.rows`** —— 用的是**上一帧**高度。
`outputHeight` 口径（`renderer.js:9`）= `output.split('\n').length` = **行数**，
所以「帧有 N 个换行」→ outputHeight = N+1。**帧换行数必须 ≤ rows − 2。**

后果链（备用缓冲区 = alternate screen，无回滚缓冲）：
`clearTerminal + fullStaticOutput + output` → 转录被擦掉；`scrollbackPreserve` 第三层
`KHY_SUPPRESS_STATIC_REPRINT` 剥掉 `fullStaticOutput` → 抹掉后不重画；第四层
`KHY_FULLSCREEN_TAILCUT` 从底部锚定裁到 rows−1 → 砍掉的正是顶部转录。

**而且会自锁**：一旦某帧 ≥ rows，`lastOutputHeight` 就永远 ≥ rows，此后**每一帧**都清屏。

**B. chrome 账本漏计三项，live 区恒定超预算**

| 漏项 | 实情 |
|------|------|
| PreviewLayout 的 Topbar(1) + 底部分隔线(1) | 完全没进 `shares`，宽终端恒定多 1~2 行 |
| 忙态 spinner 块 | 记成 1~2 行，**实际 3 行**。ink 的边框语义是「设了 `borderStyle` 就四边全画，单写 `borderBottom: true` 不会关掉其余三边」；Preview 的 `paddingY:1` 包法也是 3 行 |
| `_viewportHeight` 声明在 `_taskProps` 之前 | TDZ 顺序错误 → `taskH` 恒 0，任务清单高度从未计入 |

修前实测：legacy 100×24 忙态帧 **24 行 = rows**（outputHeight 24 ≥ 24）→ 每帧清屏，自锁。

**C. 视口永远停在顶部（「回显看不见」的另一半）**

`Viewport.js` lines 模式：`if (autoScroll && scroll >= maxScroll) clamped = maxScroll;`
初值 `scroll = 0`，内容长过视口后 `0 >= maxScroll` 恒假 → **视口停在顶部**，
用户看到的是最早那几行。即使把转录搬进应用内 Viewport 并修好清屏，体感依然「看不见」。

**D. 滚轮被终端合成为 ↑/↓**

备用缓冲区无回滚缓冲 → 关掉鼠标追踪后终端把滚轮**合成为 ↑/↓ 键**送进 stdin；
↑/↓ 已被 `arrowRouting` 绑成 `history:previous/next` → 用户看到的「滚轮回溯历史记录」
是键位串扰。旧 dispatcher 把所有滚轮事件交给 `fireNative()`（`enterNativePassthrough`）。

## khyos repl 六步工具闭环：断点在审批通道（2026-09-16 上午）

### 结论

朋友要求的六步闭环（repl 组装请求 → 查询引擎注入工具 → 模型输出 tool_use →
并行分发执行 → tool_result 回传 → repl 渲染循环）**代码层面早已全部存在**，
但 **repl 的 QueryEngine 路径实际跑不通**，卡在第 4 步之前。

### 根因（不可推导，必须记住）

`toolUseLoopCore.js:7855` 的 preflight 批量审批：
```js
if (iteration === 1 && toolCalls.length >= 2 && KHY_PREFLIGHT !== 'false' && !preflightApproved)
  const pfResult = await runPreflight(toolCalls, { onControlRequest });
```
- `preflightPermission.js:35` —— **有** `onControlRequest` 时直接返回空集（不拦），
  审批交给宿主逐个做；**没有**时走经典 raw-mode 批量对话框，
  非 TTY 环境读不到输入 → `denied.size>0 && approved.size===0` →
  循环 `return {stopped:true}`，文案 `⚠ All tools denied in preflight check, stopping.`
- 所以 **`onControlRequest` 的存在本身就是开关**：工具是 low-risk 只读时
  它一次都不会被真正调用（实测审批次数 0），但少了它就全拒。

**两条断链**：
1. `replSession.js:9243`（QE 分支）只传 `{ effort }`，没传 `onControlRequest`
   —— legacy 路径在 10920/11010/11413 都传了 `handleControlRequest`。
2. `queryEngine.js` `_submitMessageLegacyWithHarness` 的 `loopOptions` 里没有
   `onControlRequest`，而 repl 默认走 harness（`KHY_QUERY_ENGINE_HARNESS` 默认 true）。

两处均已修（各加一行 + 注释）。`agenticHarnessService` 的 4 处 `runToolUseLoop`
全部 `{...loopOptions}`，所以补 loopOptions 一处即覆盖主路径/续作/修复/验证四条。
