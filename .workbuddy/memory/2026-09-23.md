### 环境教训（下次直接用）

- **NTFS ADS 陷阱**：日志/输出文件名**不能含 `:`** —— 会被写成备用数据流
  （`check:structure.log` → 文件 `check` 的 `structure.log` 流），正常读取路径永远读不到。
  清洗正则须写 `/[^a-zA-Z0-9_.-]/`（`:` 必须映射掉）。本轮已修 `.khy/tmp/baseline-driver-0923.js`。
- `git status --porcelain -z` 输出里 **rename 记录占两段**（源 + 目标），解析时必须 `i += 1` 跳过，
  否则会把目标路径当成一条独立记录。
- 基线 jsonl 的字段是 **`status`**（不是 `exit`），`signal`/`timedOut`/`bytes` 同层。
- `git archive HEAD <单文件>` **可用**，`git archive HEAD`（整树）在本仓**必失败**

## khy 终端启动卡死 — 根因取证（已实测复现）

学生报「khyos 在终端中输入 khy 启动时容易卡死，找找原因」。
结论：**不是单一 bug，而是 4 个叠加的等待/失败源**。R1 在本会话内**完整实测复现**。

### R1 内核预构建状态机：每次启动都复发 + 阻塞等待（主因，已实锤）

代码：`platform/khy_platform/_bootstrap.py`

- `_maybe_prebuild_khyos_kernel()` L543 —— 每次 `khy` 启动都跑（`ensure_bootstrapped` L765）
- `_decide_kernel_prebuild_action()` L422 —— 纯状态机决策
- `wait_for_kernel_prebuild()` L704 —— 有锁时同步阻塞等待
- `_pid_alive()` L310 —— nt 分支走 `tasklist /FI "PID eq N" /NH`

**实测复现（本会话意外触发真实 khy 进程，非推演）**：

| 时刻 | 磁盘状态 |
|---|---|
| 起点 | `.khy_kernel_prebuilt` = `building pid=20140 ts=1789893701 attempt=1`；`.kernel-prebuild.lock` **不存在**；pid 20140 已死；无 ISO |
| 离线回放预判 | action = **spawn**，attempt 1→2 |
| 真实执行后 | marker = `building pid=47052 ts=1790126115 attempt=2`；lock = `47052`；`kernel-build.log` mtime 刷新 |

注：非交互 `khy` 走轻量分支（不打「重试第 N 次」那行，该行由完整启动打）；
**两种分支都会重新 spawn**，这才是卡死的根。

**确定性失败链**：

1. `_maybe_prebuild_khyos_kernel` L669 detached `Popen([node, bin/khy.js, "os", "build"])`，
   `stdin=DEVNULL`、`stdout=<log>`（**全非 TTY**）
2. Node 侧 `bin/khy.js` L2119–2123：`khy os` 无子命令且 `!isInteractiveTerminal()`
   （L1063 = `stdin.isTTY && stdout.isTTY`）→ 打「当前环境不支持交互终端」→ `process.exit(1)`
3. 构建**从未开始**：实测 `python.exe` / `make.exe` / `gcc.exe` 全部不存在
4. Python 侧**从不回收子进程、从不读退出码**（detached + 无 join）
5. → `.kernel-prebuild.lock` **永久残留**，pid 变死号
6. → 下次启动 `_lock_pid_alive` 为 false → 状态机判「上次构建死了」→ 按 attempt 重试
7. → `wait_for_kernel_prebuild()` 只要**看到锁存在**就进 2s 轮询，
   上限 `KHY_KERNEL_BUILD_WAIT`（默认 **900 秒 = 15 分钟**）

**两个独立 bug**：

- B1：`wait_for_kernel_prebuild` 只在**被调用时**才有机会清锁；锁残留期间用户看到
  15 分钟静默等待。`if not _pid_alive(pid): break` 后必然 `_remove_quiet(lock)`（L736），
  但那是「已经等完了」才清。
- B2：**退役态从未被写下**。`giveup` 只在 `attempt >= max_attempts`（默认 3）触发，
  但 `_decide_retry` 在 `(now - last_ts) < retry_interval`（默认 **21600s = 6h**）返回
  `skip` —— 于是**每次开机刚好落在 6h 退避窗口内**，既不重做也不推进计数器，
  永远停在 `building/attempt=2`。

**用户侧立即处置**：`KHY_KERNEL_AUTOBUILD=0`（一劳永逸）；或删
`~/.khyos/cache/.khy_kernel_prebuilt` 与 `.kernel-prebuild.lock`；`KHY_KERNEL_BUILD_WAIT=0`。

### ★ 实施时推翻了方案初稿的核心写法（重要教训）

方案初稿写「host 改调 `ai.chat(message, opts)`」——**这是错的**。
实测：`cli/ai.js` 导出的 `chat` 是**内层 LLM 调用**，`aiChatCore.js:3422-3425` 注释自述
*"so the **toolUseLoop** can process the tool calls"*，返回 `{ reply, toolUseBlocks, toolCallLog }`
—— **它把工具调用交回调用方，自己一个都不执行**。
正确形态是**驱动既有循环**：`runToolUseLoop(msg, { chat, chatOpts, onToolCall, onToolResult, ... })`
（`queryEngine.js:992` / `replSession.js:10897` / `AgentTool/index.js:1258` 三处同款）。
只调 `chat` 会让工具调用返回后无人执行，**症状与修复前一模一样**。

三条实测结论（已写进 skill §8.7）：

1. **`cwd` 必须在 `chatOpts.cwd`**，不是 `options.cwd` —— `toolUseLoopCore.js:1332` 的
   `effectiveChatOpts = { ...chatOpts }` 是唯一消费点（`:9292`/`:9754` 用它定工具执行根）。
2. **`onControlRequest` 传桩 = 拒绝写操作** —— `:6803`/`:7726` 判 `typeof === 'function'`；
   传恒返回 `undefined` 的桩 ⇒ fail-closed deny（网页端 SSE 只能这样）。**不传**则走后端默认策略。
   所以 P0「不接权限确认」不只是分期问题，**是让 P0 验收（文件真的变了）成立的前提**。
3. `runToolUseLoop` 的 `onToolCall/onToolResult` **不带调用 id**，同名工具可并行
   ⇒ 在 host 侧按**同名 FIFO** 自行配对（`registerToolCall`/`settleToolCall`），
   否则 renderer 只能按名字猜，并行同名会张冠李戴。
