## TUI 鼠标：滚轮 vs 原生拖选的"两全"方案（[DESIGN-ARCH-119] 续，只讨论未改码）

已确认的判据（用户实测）：`?1000h` 一开，press/wheel 全进 stdin，终端不再做原生拖选；
`return false` 只是「不吞」，事件已被 ink 从 stdin 读走、物理上回不到终端。
⇒ 在鼠标通道内部做「收窄 C」无解，Press 起点永远拿不回来。

**本次结论：冲突不在档位，在投递通道。** 滚轮不必走鼠标通道 ——
`?1007h`（alternate scroll）把备屏滚轮投递成 ↑/↓，走键盘通道。
于是鼠标通道可整个关闭 → 原生拖选（无需 Shift）恢复，滚轮不丢。

- **方案 A（推荐）**：备屏不写 `?1000h`，改写 `?1007h`；↑/↓ 按 §0.9.1 已有的
  「视口贴底哨兵」分流（贴底 = 输入历史，离底 = 视口滚动）；
  **滚轮合成的 ↓ 在贴底时必须 no-op**，否则立刻退化成「回溯历史」。
- **方案 B**：保留鼠标层，应用自绘选区 + OSC 52 复制。写入侧已有 `ccClipboard`
  （OSC 52 + native），只需补「选中 + 取文本」那半程。
- **待实测三项**：① 1007 在 WT / kitty / iTerm / conhost 的支持矩阵；
  ② 不支持 1007 时终端默认的 alt-scroll 行为；③ 合成 ↑/↓ 与真实 ↑/↓ 字节是否可区分
  （若可区分则无需上下文分流，判据更硬）。

落地位置：`mouseButtons.js`（enableBytes/disableBytes 补 1007l）、
`app.js:294-316`（备屏强制接管分支）、`arrowRouting`（↑/↓ 路由）。

### 第二轮全仓筛查（结论加固 + 三处新发现）

**三需求的正交性（这是"两全"存在的根本理由）**：
- 滚轮 —— **可走键盘通道**（1007 或 1001+1003）→ 不独占
- 原生拖选 —— **要求鼠标通道完全关闭**（任何追踪模式下 press 都被读走）
- 点击 —— **要求鼠标通道开启** → 与拖选**物理互斥**，只能靠等价键位满足

即：滚轮能解放，拖选与点击不能。而 P6 已经承诺"每个鼠标动作必须有等价键位"，
所以点击的收益本就被压缩到接近零。

**全仓可点元素实测（纠正了一个长期误信）**：`mouseButtons.js` 头部说"只有两个可点元素
（麦克风按钮、待发图片的 ×）"——**不准确**：
| 元素 | 位置 | 等价键 |
|---|---|---|
| 麦克风 | `PromptFrame.js:390` | ✅ `Alt+M` |
| 工具卡展开 | `ToolLines.js:1371` | ✅ `Ctrl+O` |
| 右栏折行 | `RightPanel.js:114` | ❌ 无等价键（**违反 P6**，建议补键） |
| 会话列表 | `SessionSidebar.js:78` | ⚠ `ThreeColumnLayout` **未接线**（`App.js:5773-5794` 自述），死代码 |
| 待发图片 × | — | ❌ **未找到任何 onClick 实现**，需核实是否已 abandon |

⇒ 关掉鼠标层实际只损失 **1 个** 元素（右栏折行），且它本来就违约。

**候选②（新，之前未考虑）**：`1001`（X11 鼠标、只报 press/release）+ `1003`（任意移动），
在 dispatcher 里**只吞 button 64/65**，press 按坐标白名单放行。
好处：滚轮保持"精确滚轮事件"（不依赖 1007 支持矩阵），且不送 AnyEvent。
代价/风险：1003 不再有任何节制（1001 下鼠标不移动就不发）；备屏里驱动
`onInput → collectLayout`（整树 DFS）易卡；且**必然有终端不发 1003**（否则现有
hover 就够用），→ 需 1007 兜底 → 复杂度翻倍而**仍有 1007 风险**。故 1007 直做更优。

**新发现的轻量选项**：TUI 已启用 bracketed paste（`useTextInput` 有粘贴路径）。
若终端把拖选写入发成 paste 事件，则还有两条路：① 保留鼠标层、靠终端 Shift 拖选 +
OSC 52 兜底（需确认发送方是否兼容选择缓冲区）；② 干脆把 TUI 输出镜像到日志文件，
用户去编辑器复制（缺陷是从"复制不了"变成"不好方便"）。

#### Claude Code（anthropic）—— 提供双档 ESCAPE HATCH，不是"两全"

1. **启动时打印本终端对应的"原生选择修饰键"**（Terminal.app `Fn` / iTerm2 `Option` /
   VS Code `Shift`）—— 本仓 §6.2 只说"Shift 永远走原生"，**漏了 iTerm2/Terminal.app**。
2. **`Ctrl+O` 转录模式 + `[`** 把完整对话**写回终端原生 scrollback**，此后 `Cmd+F`、

> "mouse - 在 TUI 中启用或禁用鼠标捕获（默认：true）。禁用后，会保留**终端原生的
> 鼠标选择和滚动行为**"

`packages/` 是 OpenTUI（作者 sst）自研 Go/Rust TUI 框架——**自绘选区**。
有 `scroll_acceleration`（macOS 风格惯性，**需要逐格精确滚轮事件**），
这印证了"鼠标通道下才有精确滚轮"这一点。
⇒ **opencode 连"保留滚轮"那一档都没做，只有全开/全关。**

⇒ 作为参照价值低：它证明"这个问题在 CC 系里没人另解"。

**给本仓的最终判断**：

## TUI 鼠标/拖选专题 —— 第四轮：三参考项目「正文可复制 + 点击选择 + 选择复制 + 上下文回滚」的真实做法

用户纠正了我的框架：这三个项目（claude-code / claude-code-best / opencode）**并非只是给逃生舱**，
它们确实同时交付了「正文可复制、可点击选择、选择后复制、上下文可回滚」。要求研究它们**怎么做**。

**结论：决定性机制不是终端原生选择，而是「应用内自绘选择 + 松手即复制」。**

### Claude Code（全屏模式）
1. **上下文回滚靠自绘视口虚拟化**，不靠终端 scrollback：FullscreenLayout.tsx +
   VirtualMessageList.tsx（窗口化 + blit 复用未变化屏幕段）+ Messages.tsx。
   备屏无回滚缓冲这一点被视口接管消化掉。
2. **选择靠自绘**：拖选任意文本；**双击选中一个词**（明确对齐 iTerm2 的 word boundary，
   所以一条文件路径整体选中）；**三击选整行**；**松手即自动复制**到剪贴板；
   /config 的「Copy on select」可关掉自动复制。
3. **键盘等价**：有选区时 Shift+方向键 从键盘扩展选区；Shift+↑/↓ 在选区抵达上下边缘时滚动视口；
   有选区时 Ctrl+c 复制。
4. **剪贴板多通道**：本机工具链（pbcopy/xclip/wl-copy/PowerShell）→ tmux buffer → SSH 下 OSC 52 兜底。
5. **三条逃生舱**：启动时打印本终端对应的原生选择修饰键；Ctrl+O 转录模式把整段会话灌进原生 scrollback；
   v 写临时文件并开 $VISUAL/$EDITOR。

### opencode
- mouse: true|false（tui.json，默认 true）/ OPENCODE_DISABLE_MOUSE=1。
- viewport 有 MouseWheelEnabled / MouseWheelDelta = 3（逐格精确滚轮事件 —— scroll_acceleration
  惯性滚动依赖它，所以滚轮不能被合成方向键替代）。
- 另有 HighlightStyle / SelectedHighlightStyle / SetHighlights / HighlightNext / HighlightPrevious
  —— 这是**高亮区间 API，与自由文本选择不是一回事**：它服务于自身导航，不产出可复制文本。
- 真复制走 textarea 的 ctrl+e 开 $EDITOR。即 opencode 的「可复制」偏向**原生选择 + 外部编辑器**。

### claude-code-best
- 继承 CC，无独立实现。

### 映射到 khy-os（可行性已实测）
- **复制写入半边已经齐了**：utils/ccClipboard.js 的 writeClipboard() native 优先；
  本地 TTY 下 shouldEmitOsc52 返回 {on:false, reason:'tty'} ⇒ **走 native-only**，
  正是 copy-on-release 需要的路径（SSH 场景才需另验）。
- **行模型天然适配**：_mainContentLines（App.js:5275）是**扁平纯字符串数组**，
  且 Viewport lines 模式按 height 切片渲染 ⇒ **屏幕行 == 数组下标（1:1）**，
  行列 ↔ 文本位置换算不需要任何布局反查。
- **高亮原语已在生产使用**：ink Text 的 inverse prop 在 PromptFrame.js:408、
  QuestionPrompt.js:440 已被用于光标块 ⇒ 选区着色是已验证能力，不是新赌注。
- **坐标已到位**：createMouseDispatcher 的 press/release 分支已拿到 ev.col/ev.row，
  且 hitTest(layout, col, row, offset) + offset = screenOffset(layout.height, ctx) 已能算屏幕行。
- **缺口**：_transcriptLines.buildTranscriptLines() 产出的是**纯字符串**，没有
  「第 N 行属于哪条消息/哪个角色」的元数据 ⇒ 要支持按消息复制、双击选词、三击选行，
  需要给行投影加一层 sidecar 元数据（或新增一个 buildTranscriptLineRecords）。

### 架构判断（本轮最重要的一条）
