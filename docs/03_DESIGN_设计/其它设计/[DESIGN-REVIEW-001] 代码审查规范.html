[DESIGN-REVIEW-001] 代码审查规范#

本文档定义 khy-os 项目的代码审查标准，包括审查流程、清单、职责等。

1. 审查概述#

1.1 目的#

  • 确保代码质量
  • 发现潜在问题
  • 分享知识
  • 保持一致性

1.2 原则#

  1. 尊重：建设性反馈，避免人身攻击
  2. 及时：24 小时内响应
  3. 全面：关注功能、安全、性能、可维护性
  4. 学习：审查是学习的机会

2. 审查流程#

2.1 提交审查#

  1. 完成代码开发
  2. 本地运行测试
  3. 创建 Pull Request
  4. 填写 PR 模板
  5. 请求审查

2.2 审查分配#

自动分配：

  • CODEOWNERS 文件定义模块负责人
  • 自动请求相关模块所有者审查

手动分配：

  • 作者可以手动添加审查者
  • 建议添加至少 1 个相关模块所有者

2.3 审查时限#

PR 大小建议审查时间
< 100 行4 小时
100-400 行8 小时
400-1000 行24 小时
> 1000 行48 小时

2.4 审查结果#

结果说明
Approve批准合并
Request Changes需要修改
Comment建议性意见

3. 审查清单#

3.1 功能正确性#

  • [ ] 代码实现了预期的功能
  • [ ] 边界条件处理正确
  • [ ] 错误处理完善
  • [ ] 没有逻辑错误

3.2 代码风格#

  • [ ] 遵循代码风格规范
  • [ ] 命名清晰、一致
  • [ ] 代码格式正确
  • [ ] 无未使用的变量或导入

3.3 安全性#

  • [ ] 无 SQL 注入风险
  • [ ] 无 XSS 漏洞
  • [ ] 敏感数据已加密
  • [ ] 输入已验证
  • [ ] 认证和授权正确

3.4 性能#

  • [ ] 无明显性能问题
  • [ ] 数据库查询优化
  • [ ] 避免不必要的计算
  • [ ] 使用缓存（如适用）

3.5 可维护性#

  • [ ] 代码结构清晰
  • [ ] 函数职责单一
  • [ ] 适当的注释
  • [ ] 无重复代码

3.6 测试#

  • [ ] 添加了必要的测试
  • [ ] 测试覆盖关键路径
  • [ ] 测试可重复运行
  • [ ] 测试独立、无依赖

3.7 文档#

  • [ ] API 文档已更新
  • [ ] 变更日志已更新
  • [ ] README 已更新（如适用）

4. 审查者职责#

4.1 审查前#

  • 了解 PR 的背景和目的
  • 阅读相关 Issue 和设计文档
  • 了解变更的影响范围

4.2 审查中#

  • 仔细阅读代码变更
  • 运行代码验证功能
  • 检查是否符合规范
  • 提供具体、建设性的反馈

4.3 审查后#

  • 及时提交审查意见
  • 跟进修改情况
  • 最终批准或请求修改

5. 作者职责#

5.1 提交前#

  • 本地运行所有测试
  • 确保代码符合规范
  • 填写完整的 PR 描述
  • 标记相关 Issue

5.2 审查中#

  • 及时响应审查意见
  • 解释设计决策
  • 修改发现的问题
  • 保持开放的态度

5.3 合并后#

  • 监控部署状态
  • 处理反馈

6. 审查模板#

6.1 审查评论格式#

问题：

**问题**：[简要描述问题]

**位置**：file.js:123
**建议**：[具体建议]
**原因**：[为什么需要修改]

赞扬：

**优点**：[值得肯定的地方]

建议：

**建议**：[可选的改进建议]

6.2 常见审查意见#

类型示例
功能这个边界条件处理是否正确？
风格变量名是否可以更清晰？
安全这里是否存在 SQL 注入风险？
性能这个循环是否可以优化？
测试这个场景是否有测试覆盖？

7. 特殊场景#

7.1 紧急修复#

  • 简化审查流程
  • 至少 1 个批准
  • 事后补充完整审查

7.2 大型 PR#

  • 拆分为多个小 PR
  • 每个 PR 独立审查
  • 确保每个 PR 可独立部署

7.3 跨模块 PR#

  • 添加所有相关模块所有者
  • 协调审查意见
  • 确保一致性

8. 审查工具#

8.1 自动化检查#

Prettier代码格式化
Jest/Vitest单元测试

8.2 GitHub 功能#

  • Code Review：行级评论
  • Suggested Changes：建议修改
  • CODEOWNERS：自动分配审查者
