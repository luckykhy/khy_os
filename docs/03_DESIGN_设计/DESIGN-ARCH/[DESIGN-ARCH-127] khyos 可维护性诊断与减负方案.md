## 0. 结论先行

**「难以维护」不是感觉，是三个可测量的数字。**

| # | 结构性事实 | 实测值 | 后果 |
|---|---|---|---|
| **1** | **单点改动的同步触点过多** | 新增一条规则须同步 **13 处** | 想加一条约束的心理成本 ≈ 写 13 个文件；于是「懒得加」和「加了半截」同时发生 |
| **2** | **文档经济倒挂** | 文档 1090 万字符 vs 后端代码 2982 万字符（**1 : 2.7**）；906 个 `.md` 强制配 895 个 `.html` | 改一句规范文字 = 改 2 个文件，其中 1 个是生成物 |
| **3** | **管控强度与执行强度错配** | 88 条规则中 **15 条 `gate=advisory` 永不执行**；另有 **12 条 `manual`** 无执行器；pr-gate 61 步中 7 步 `continue-on-error` | 三分之一的规则是「写了但不管」，却照样占用维护心力与文档面 |

**核心判断**：khy-os 的治理层已经**过了「加得越多越安全」的拐点**。
`[RESEARCH-017]` 已于 2026-09-17 给出同一结论（原文：「**不要再新增检查器**」，74 个检查器 / 91.8% 可执行覆盖）。
本方案**承接该结论**，回答它未回答的下一步：**既然不能再加，那该减什么、怎么减。**

**方案主轴一句话**：**把「13 处触点」压到「1 处声明 + 自动派生」，把「15 条永不执行的规则」显式降格，把「906 份孪生件」改为按需生成。**

## 2. 根因分析

三条各自独立、但互相放大的机制：

### 根因 A — 「声明」与「派生」没有分离

13 处触点里，**只有 1 处是真正的语义输入**（#5 登记表条目 + #1 规范正文），
其余 12 处**全部是从这 1 处可派生的**（生成物 5 项、索引回写 2 项、别名 1 项、标记行 2 项、卡片 2 项）。

⇒ **「维护成本 ≠ 工作量，而是同步成本」。** 成本高不是因为事情难，是因为同一件事要写 13 遍。

### 根因 B — 文档密度超过代码密度

| 对象 | 字符数 |
|---|---|
| `docs/**/*.md` | **10,924,209** |
| `services/backend/src/**/*.js` | 29,824,127 |
| `scripts/ci/**/*.js` | 988,817 |

文档 : 后端代码 = **1 : 2.7**。对一个「AI 平台操作系统」而言，**规范文档体量已接近代码的三分之一**。

⇒ 每加一条规则，真正的负担不是执行器（几十行），而是**围绕它的文档生态**（正文 + 卡片 + 两处索引 + 两处标记行 + 两处孪生件）。

### 根因 C — 「登记」与「生效」解耦，且解耦处无告警

`gate=advisory` 的 15 条规则是合法的登记状态，通过全部守卫。
⇒ 仓库**无法从守卫输出中看出**「哪些规则其实从没跑过」。

⇒ 维护者的心智模型是「有 88 条规则在管我」，实际是「73 条在管，15 条只是写着」。
**这是最伤人的一类成本：为不存在的东西付钱。**

### 三者如何互相放大

```
根因 A（13 处触点）
   └→ 加规则变贵 → 「反正加了也不跑，先登记 advisory」→ 根因 C 恶化（15 条）
   └→ 为了「补齐」而写的文档 → 根因 B 恶化（文档 : 代码 = 1:2.7）
根因 B（文档过密）
   └→ 改一句规范要动 2 个文件 → 每次改动都更贵 → 更倾向 batched 大改动 → 未提交积压（532）
```

## 4. 设计公理（3 条，不可让渡）

### 公理 1 — **一条规则只应有 1 处语义输入**

> 若某个事实需要在 N 个文件里各写一遍，那么它**一定会在 N 个文件里漂移**。
> 维护成本的上限不是「写第 1 处的难度」，而是「同步剩下 N−1 处的难度」。

**推论**：任何新增的「必须手工同步」的触点，都是一种**设计缺陷**，而不是「规范严格」。

### 公理 2 — **不生效的规则比没有规则更贵**

> 没有规则 → 维护者知道这里没人管，会自己小心。
> 有不生效的规则 → 维护者以为这里有守卫，**放松警惕**，而实际零防护。

**推论**：`advisory` 状态必须**在可被看见的地方**显现（guard 输出 / 清单），否则它就是负资产。

### 公理 3 — **减负不得以降低防线为代价**

> 任何压缩成本的措施，必须**同时给出强度守恒证明**（哪些检查真的还在跑）。
> 若一个动作让「会拦截的检查」减少，它就不是减负，是**削弱**。

**推论**：本方案 §5 的每条措施都带**「强度守恒验收」**，无此项者不得采纳。

## 5. 方案：三阶梯减负（每条含强度守恒验收）

> **强度梯度**遵循 `[DESIGN-PROCESS-002]` 四阶段：**事前 advisory、事中 warning、事末 error**。
> 本方案的每条措施**均落在「事前 advisory」**，绝不越过。**过早阻断会逼 AI 撒谎。**

---

### M1 —— 触点压缩：把 13 处压到 2 处（**收益最高、风险最低**）

**问题**：13 处触点中 5 项是生成物、2 项索引、2 项标记行、2 项卡片 —— 均可从登记表派生。

**做法**：新增一个**单一入口脚本**，从 `RULES-REGISTRY.json` 一个条目出发，**幂等**地派生其余 11 处。

| 落点 | 内容 | 状态 |
|---|---|---|
| `scripts/lib/ruleScaffold.js` | **纯叶子**：零 IO、确定性、绝不抛、可单测。`auditRule(ruleEntry, ctx)` → 返回「哪几处触点缺失」的**判定对象**，不落盘 | ✅ 已落地（2026-09-22） |
| `scripts/ci/check-rule-scaffold.js` | 走盘层：采集磁盘事实喂给叶子，输出缺口报告（**只报不改**） | ✅ 已落地 |
| `scripts/lib/touchCostProbe.js` | **纯叶子**：6 个 `measure*` 纯函数，计算四类维护成本读数 | ✅ 已落地 |
| `scripts/ci/check-touch-cost.js` | 走盘层：采集 git/文件系统事实，渲染读数 | ✅ 已落地 |
| `scripts/ci/scaffold-rule.js` | 走盘层：`--check`（只报缺口）/ `--apply`（幂等落盘） | ⏸ **刻意缓建**，理由见下 |

> **为什么 `--apply` 那一半刻意缓建**：本仓所有通过评审的机制都是「检测 + 报告 + 建议」，
> **没有一个是自动改写文件的**（`archDebtScan` 的 `--update-baseline` 被明令禁用即为此理）。
> 自动落盘会在「派生逻辑本身写错」时把漂移**批量固化**，且违反 `PROCESS-009`「改机制先改描述」的顺序。
> 因此 M1 的真实收益**已由「检测」这半边兑现**：13 处触点的缺口从此**可见且可复现**，
> 而不必先拥有自动修复器。`--apply` 待 S1 观察期满、漂移检出率稳定后再评估。
>
> **已落地的接线**（四处触点齐备，非「声明未接线」）：
> `TOOLING-009`（`check-rule-scaffold`）+ `TOOLING-010`（`check-touch-cost`），
> 两者均 `gate="commit"` + `severity="advisory"`（真跑、只记录、恒 `exit 0`），
> 已在 `rules:gate:commit` 的 `action=start` 中实测被 spawn。


**关键设计约束**（每条都有实测依据）：

1. **必须幂等**：重复运行结果一致（`[DESIGN-ARCH-111]` 的生成器契约）。
2. **不得扫到生成物**：`build_docs_site.js` 的产物不能被本脚本改写（会破逐字节契约）——
   **只改生成器再重跑**，不可直接写 `.html`。
3. **不得用 `node -e` 内联中文 + 反引号**（bash 会当命令替换，静默吃字段）。
4. **`--check` 必须能发现漂移**：这是它的主要价值——不是省事，是**让漂移可见**。
5. **`ssot` 不是路径而是目标列表**（实测踩坑，见下）：`ssot` 用 ` / `（带空格）分隔多个目标，
   每个目标可带段尾修饰（`§1`、`#anchor`、函数名、甚至 `npm run x` 命令），
   **只有以已知扩展名结尾的那一段才是文件路径**。初版把整串当路径 ⇒ **37 条全是误报**
   （「文件不存在」）。修复后降为 5 条，且**逐条人工核验为真**。
   教训：**低精度守卫比没有守卫更糟**（§5 精度纪律）。

**强度守恒验收**（已实测）：
```bash

node --test scripts/tests/touchCostProbe.test.js   # 18 pass / 0 fail
npm run check:rule-scaffold                        # 90 条规则 → 5 条 gap + 15 条 advisory（恒 exit 0）
npm run check:touch-cost                           # 四项读数（恒 exit 0）
npm run check:wiring                               # ✅ 90 个检查器全部接线
npm run check:rules                                # ✅ 登记表与真源双向可达、规则卡逐字节一致
npm run docs:verify                                # ✅ 1191 md 全有 html
npm run rules:gate:commit                          # action=start 两条新执行器 → 阻断 0
```
> **反例场景（必测）**：手工把某条规则的卡片删掉 → `--check` **必须**报出来。
> 若报不出，说明它是空转断言（`[DESIGN-ARCH-126]` §5.7 的教训）。
>

## 6.1 实现期新增的两条判读纪律（**实测踩坑，写给下一个人**）

两处都不是设计缺陷，而是**本仓既有的隐式契约**，不写下来必被重踩：

**（1）finding 输出必须用「聚合方言」，否则静默失效。**
`ruleguard` 认两种方言（`scripts/ruleguard/lib/run.js`）：
- 逐项：`[ERROR] <file> <finding>:<line>` —— 定宽 6 字符标签 + **必须带 file:line**；
- 聚合：`- [warn] <消息…> (id: <finding>)` —— **无 file:line**，用于「计数/盘点」型发现。

初版用了两行缩进的 `[WARN ] …`（既非逐项也非聚合），结果是
**人眼看起来报了 15 条、`ruleguard` 却解析出 `errors=0 warnings=0`**——
人类可读输出与机器判定**同时都是绿的**，最危险的一种失败。
⇒ 本方案的两条执行器统一走聚合方言、全部 `[warn]`、`return 0`。

**（2）`--changed` 必须过滤「清单型」发现，否则 commit 快档被淹没。**
`advisory-never-executes` 是**存量盘点**（15 条恒定不变），
若不过滤，每次提交都会重报一遍同样 15 条 ⇒ 快档失去信噪比。
⇒ `--changed` 下，仅当**改动集触及该规则相关文件**时才报；
`--list` 保留全量清单（供人工裁决用）。

## 7. 若新增检查器：接线四处（缺一即红）

> ⚠ **本方案原则上不新增检查器**（承接 `[RESEARCH-017]` 结论）。
> 本次落地新增了 **2 个**（`check-rule-scaffold` / `check-touch-cost`）——
> 二者都不是「新判据」，而是**让存量成本首次可见的度量器**，
> 因此 `severity="advisory"`、恒 `exit 0`、不改变任何既有规则的强度。
> 四个接线触点如下（**缺一即红**）：

1. `package.json` 加 `check:*` 别名 → 否则 `check-wiring` 判 **error**
2. `RULES-REGISTRY.json` 补条目（若认定它是「规则」而非「工具」）
   ⚠ `domain` 是**十域封闭枚举**；`formerly` 必须是**字符串**（无前身写 `"无"`）
3. `<!-- RULES-REGISTRY: ID -->` 标记行放 **`ssot` 首个目标文件**（第 3 行），**不是 `AGENTS.md`**
   ⚠ **多个规则共用一个 ssot 文件时，标记行要并列写**：
   `<!-- RULES-REGISTRY: TOOLING-009, TOOLING-010 -->`
   （解析器认逗号分隔，不是写两行——写两行只有最后一行会生效）
4. `npm run docs:rules-cards` 重生成（**先修登记表再生成**，否则错误扩散），
   **再** `node scripts/docs/build_docs_site.js` 出规则卡的 `.html` 孪生件
   ⚠ **生成器的顺序是刚性的**：规则卡 `.md` 由 `gen-rules-cards.js` 出，
   规则卡 `.html` 由 `build_docs_site.js` 出；**只跑前者会让 `check:rule-scaffold` 报 `.html` 缺失**

**门档不用改**：commit ⊂ pr ⊂ release 的成员资格从登记表派生（`[DESIGN-ARCH-111]`）。
⚠ 但 `exec.args` 必须含 `--changed`，否则 commit 档**不会**收它
（commit 档只收集支持 `--changed` 的执行器）。

## 11. 一句话总结
