[DESIGN-ARCH-098] 系统提示词结构重设计：静态/动态分层与缓存优化方案#

性质：设计方案（提案），尚未实施。当前运行时结构与分层规范见
[[DESIGN-PROMPT-002] 系统提示词分层规范](../../10_规范/其它规范/[DESIGN-PROMPT-002] 系统提示词分层规范-静态与动态分区.md)；
本文描述目标结构与迁移路径。
目标：① 提升前缀缓存命中率；② 让模型更准确地理解用户意图；③ 让两部分（静态/动态）的组织方式与加载时机可被机器校验。

⚠️ 已被调研修正（2026-09-15）：横向比对 Claude Code / opencode / Codex CLI / Gemini CLI /
DeepSeek Harness 后，本文 §3 的「项目章程搬进 L1 前缀」与 §7 改动 9 的路径被修正——
改为 Codex 式的 messages 增量注入。原因：khy 走自建 relay 路径、无跨用户共享缓存，
前缀方案与 messages 方案命中率等价，但后者下前缀永不因项目文件改动而作废。
修正细节与新增的 R1–R9 对齐清单见
[`[DESIGN-ARCH-099] 提示词架构横向调研与 khy-os 对[DESIGN-ARCH-099] 提示词架构横向调研与khy-os对齐方案.md齐方案.md)。
本文其余结论（五问判据、L0–L4 分层、锚点方案、L4 意图块、四时机加载）在调研中得到强化，无需修改。

0. 结论摘要#

诊断：实测单轮装配产物 66,780 字符，其中静态前缀只有 13,927 字符（20.9%），
而 boundary 之后的动态区占 52,817 字符（79.1%）——但真正每轮必变的只有约 2,037 字符（3.0%）。
也就是说，约 76% 的提示词字节是「会话内基本稳定」的，却被排在了缓存边界之后。

方案：把 boundary 从「常量 / 动态 的分界」重新定义为
「会话级可缓存前缀 / 每轮区 的分界」，并按三轴分离（稳定性、作用域、触发条件）
把内容重排为五层 L0–L4。核心是把会话级稳定内容整体前移进可缓存前缀。

指标现状目标
可缓存前缀占提示词字节20.9%≥ 60%
每轮重算字节数≈ 52,817≤ 8,000
同一规则被重复表述的段数（验证类）13 段≤ 2 段
跨段冗余字符≈ 9,578（14.3%）≤ 2,000
意图信号是否显式否（埋在 khy_specific 的 cacheKey 里）是（独立 intent 块）

1. 现状诊断（实测）#

1.1 分区占比#

单轮实测（cwd + 一条普通工程类用户消息）：

区域字符数占比
静态前缀（boundary 之前，12 段）13,92720.9%
动态区（boundary 之后）52,81779.1%
合计（21 个装配段）66,780100%
其中「每轮必变」候选（env_info 1,100 + git_status 937）2,0373.0%

1.2 动态区最大的五段#

段字符数占全量归属真实变化频率
# claudeMd（项目指令注入）26,37839.5%project_instructions会话内几乎不变
# Runtime (khy OS v1.1.15)11,58717.4%khy_specific + model_guidance每轮可能变（键含 taskScale）
# Project structure5,2977.9%project_structure顶层增删才变
# Available Skills2,1513.2%skill_catalog装/卸技能才变
# Planning and verification1,7642.6%按需胶囊按意图选片

结论：占比最大的三块（合计 50.3%）都是「会话级稳定」，却被安排在缓存边界之后。
只有 3% 的字节真正需要每轮重算。

1.3 三个具体病灶#

病灶 A：稳定内容被关在缓存门外（最大损失）
按现状 76% 的字节每轮重新计算/重新计费。在中转（relay）/ DeepSeek 路径上标记被剥离、
命中率完全依赖「最长前缀匹配」，这部分字节一次都命中不了。

病灶 B：每轮变量混在静态前缀里（反向污染）
deferred_tools_hint（router 逐轮算）、using_your_tools（enabledTools 的函数）、
simple_intro / doing_tasks（outputStyle 的函数）都在 boundary 之前。
一次 deferred 揭示、一次工具档位切换、一次样式切换，静态前缀即从该点起全部作废。
当前设计在最需要稳定的位置放了最会变的内容。

病灶 C：规则跨段重复（稀释重点 + 虚耗 token）
按「规则主题」统计跨段覆盖：

规则主题被多少段重复表述冗余估算
改动后验证13 段（ExecutionDiscipline、ScopeMinimization、PlanningAndRecovery、PlanningAndVerification、ErrorHandling、MultiAgent、FileOperations、CommandExecution、ResponseFormatting、ToneAndStyle、UnifiedOutput、GitOperations、CompactTaskDiscipline）~2,500 字
最小改动 / 不越界6 段~1,700 字
破坏性/外部动作先确认6 段~1,100 字
输出简短直接5 段~700 字
失败先诊断再重试4 段~700 字
改前先读4 段~600 字
并行工具调用4 段~500 字
敏感信息脱敏 / 不确定就说不确定各 3 段~800 字
合计—≈ 9,578 字（14.3%）

除数量浪费外还有语义副作用：同一条规则说 13 遍，模型无法判断哪条是重点——
重点被平均化，这直接损害「准确理解意图」。

2. 设计原则：三轴分离#

现状把三个正交维度揉成一个隐式判断（「这个段放哪」由它在数组里的位置 + 它的 cacheKey
两处共同隐性决定）：

轴含义决定现状
A 稳定性会不会变、多久变一次位置（能否进可缓存前缀）隐式，散落五处
B 作用域对谁生效：进程 / 会话 / 项目 / 轮次归属（属于哪一层）未建模
C 触发条件何时必须出现（无条件 / 上下文变化 / 意图命中）加载时机只用了一个「按需胶囊」概念

重设计的第一原则：位置只由轴 A 决定，归属只由轴 B 决定，出现与否只由轴 C 决定。
三者互不越界——这正是当前设计最缺的纪律。

第二原则：能进前缀的字节，绝不留到边界之后。
判据是「它会不会在不使用户产生新输入的情况下变化」：不会 → 进前缀；会 → 进每轮区。

第三原则：同一条规则只有一个真源段落，其他段落用引用而非复述。

3. 目标结构：L0–L4 五层#

层名称内容稳定性契约失效方式位置
L0不可变内核角色设定、使命、能力边界（能/不能做什么）、绝对红线（安全/合规）、输出格式约定、冲突裁决优先级编译期常量：无参数、无 env、无 Date只在发版时变前缀最前
L1会话配置语言、输出风格、模型族与执行纪律档位、权限模式、工具档位（enabledTools）、项目指令的稳定部分（角色/约定/架构规范）会话内不变（装配一次）用户显式切换前缀（boundary 之前）
L2项目与记忆项目指令的易变部分（当前任务清单、进行中的约定）、memory、references、persona/role/companion、skill_catalog、project_structure只在底层文件变化时变新鲜度戳（mtime:size / 指纹）边界之后第 1 段（可打第 2 个缓存断点）
L3轮次状态env_info（时钟）、git_status、task_memory、mcp_instructions、deferred_tools_hint每轮或每分钟可变每轮重算尾部
L4本轮意图与任务intent 块（任务规模、命中的能力胶囊、判定理由）、按需胶囊正文、任务参数每轮必变每轮重算绝对尾部（dead-last）

3.1 与现状的映射#

现状 tier目标层变化
staticL0剔除参数化内容（simple_intro / doing_tasks 的 output-style 依赖）
dynamic_stable拆为 L1 + L2会话级配置前移进前缀；文件级内容留在 L2 并修 cacheKey
dynamic_volatileL3位置不变，补齐新鲜度戳
on_demandL4增加显式 intent 块作为「为什么选它们」的解释

3.2 关键改动：boundary 后移#

这是本次重设计的核心动作。

现状：
  [ 常量 12 段 13.9k ] │ boundary │ [ 会话配置 + 项目 + 记忆 + 每轮 52.8k ]
     可缓存 20.9%                            每轮重算 79.1%

目标：
  [ L0 内核 + L1 会话配置 ≈ 40k+ ] │ boundary │ [ L2 项目/记忆 │ L3 每轮 │ L4 意图 ]
       可缓存 ≥ 60%                                 每轮重算 ≤ 8k
                └─ 原生路径在此再打第二个缓存断点，得到两级缓存

为什么可行：L1 的失效条件是「用户显式切换语言/风格/模型/工具档位」——这是低频的
用户主动动作，不是每轮波动。为低频事件付出一次前缀失效，换掉每轮 50k 的重算，是划算的。

风险与对策：L1 一旦变化，前缀全部失效（比现状更「一刀切」）。对策是把 L1 收敛到
真正由用户显式设定的四五项，任何「系统自动推导」的值都不许进 L1（如 taskScale
必须留在 L4）。

4. 两部分的组织方式#

4.1 显式锚点，而非隐式位置#

现状靠 getSystemPrompt() 返回数组里的位置来隐含分区。目标改为显式锚点标记：

<!-- khy:l0 -->
  # Who you are
  # What you can and cannot do
  # Non-negotiable rules
  # Conflict resolution order
  # Output format contract
<!-- /khy:l0 -->

<!-- khy:l1 -->
  # Language
  # Output style
  # Model execution discipline
  # Tooling profile
  # Project charter            ← 项目指令中「不变」的部分
<!-- /khy:l1 -->

__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__

<!-- khy:l2 -->
  # Project state             ← 项目指令中「会变」的部分
  # Memory
  # Persona / Role
  # Skill catalog
  # Project structure
<!-- /khy:l2 -->

<!-- khy:l3 -->
  # Environment
  # Git status
  # Task memory
  # MCP servers
  # Deferred tools
<!-- /khy:l3 -->

<!-- khy:l4 -->
  # This turn                  ← intent 块
  # <启用的能力胶囊正文>
<!-- /khy:l4 -->

锚点的三个用途：

  1. 可机器校验：守卫直接断言「L0/L1 必须在 boundary 之前」「L3/L4 必须在最后」，

不再依赖人工核对数组位置。

  1. 可解释：khy prompt --explain 能按层列出字节数与命中情况，缓存问题可定位。
  2. 可裁剪：调试/小模型路径可按层裁剪（如低档模型只保留 L0 + L4）。

4.2 声明式装配#

把「哪一段、属于哪层、cacheKey 是什么、什么时机装配」从代码里的调用顺序
提升为一张声明表（即 [DESIGN-PROMPT-002] 已有的 promptSectionTaxonomy.js，
在 P1 阶段把 tier 从 static/dynamic_* 重命名为 L0..L4）。
装配器只消费声明表，杜绝「新增段忘了声明分层」。

5. 加载时机（四时机模型）#

现状只有「每轮全部重跑一次」和「段缓存」两种机制混用。目标明确四个时机：

时机触发装配内容频次字节量目标
T0 进程启动进程拉起L0 全量：编译期常量，进程级复用一份不可变字符串1 次/进程≈ 14k（零成本复用）
T1 会话开始新会话 / /clear / /compactL1 全量：读语言、风格、模型、权限、工具档位、项目章程；装订一整块1 次/会话≈ 26k
T2 上下文变更L2 各段的戳变化（文件 mtime、技能集指纹、git 状态摘要）只重算戳变了的那一段低频0–5k
T3 每一轮每次用户消息L3 + L4：时钟、git、任务板、MCP、deferred、intent 块、胶囊选片每轮≤ 8k

5.1 每轮重算的字节预算#

硬指标：T3 每轮重算 ≤ 8,000 字符（现状 ≈ 52,817）。构成：

段预估说明
env_info~1,100时钟桶，60s 滚动
git_status~940折入 status 摘要哈希
task_memory0–1,500无任务时为空
mcp_instructions0–800无 MCP 时为空
deferred_tools_hint0–600无 deferred 时为空
intent 块~300新增
命中的胶囊（1–3 个）1,000–3,000其余留空

5.2 绝不每轮重算的清单（必须进 T0–T2）#

claudeMd 项目指令、Runtime 执行纪律、Project structure、Available Skills、
Memory、persona/role/companion、语言与风格、工具档位描述。

6. 提升意图理解的四个机制#

缓存的另一个前提是不要为了缓存牺牲理解。以下四项专门解决后者。

6.1 本轮意图块（intent block）—— 把「系统认为你要做什么」说出口#

现状：意图判定（任务规模、命中哪些胶囊）只体现为「哪些段出现了」，模型只能靠猜；
而 taskScale 还被折进 khy_specific 的 cacheKey —— 既破了缓存，又没让模型看清意图。

目标：在 L4 顶部注入一个约 300 字符的短块：

# This turn
- Task scale: large
- Active guidance: file_operations, command_execution, planning_verification
- Because: the request names a source file and asks for a behavioural fix
- Note: if this reading of your intent is wrong, say so and the guidance set will change

三个作用：

  1. 模型看得见：不必再从段落有无反推意图，减少误用（例如把"改一行"当重构来规划）。
  2. 用户可纠偏：显式写「读错了就说」——用户一句"不对，我要的是 X"即可让 re-selection 生效。
  3. 不破缓存：它本身就在 L4（每轮区），把 taskScale 从 khy_specific 的 cacheKey 里移除，

L1/L2 因此不再受逐轮评分影响。

6.2 胶囊自解释#

每个能力胶囊首行写明触发条件：

# File operations
Applies when: reading, editing, or creating files.
Since: the request references a source file.

模型因此知道「这段为什么在这儿」，比不知道来由的规则更容易被正确执行；
也让「胶囊该不该出现」的调试变得可读。

6.3 冲突裁决优先级（写进 L0，只写一次）#

现状：规则之间的优先级从未声明，模型在矛盾指令（如「最小改动」vs「完整验证」）之间摇摆。
L0 明确一条链，全局只此一处：

1. 安全与合规红线（绝对）
2. 用户在本轮消息中的显式指令
3. 项目章程（khy.md / AGENTS.md 中的约定）
4. 本轮能力胶囊的建议
5. 风格与措辞偏好

6.4 规则去重（单一真源 + 引用）#

按 §1.3 的实测重复清单合并。合并原则：保留最完整的表述，其余段改为一句引用。

规则主题真源段落（保留全文）其他段处理
改动后验证# Verification（由 PlanningAndVerification 收敛而来）13 → 改为 1 句引用，或直接删除
最小改动 / 不越界# Scope discipline（ScopeMinimization 收敛）6 → 2（保留 L0 的总则 + 真源段）
破坏性动作先确认# Acting with care（Actions 收敛）6 → 1
失败先诊断再重试# Error handling（ErrorHandling 收敛）4 → 1
改前先读# File operations4 → 1
并行工具调用# Using your tools4 → 1
输出简短直接# Output and tone5 → 1

注意：tone_and_style 与 unified_output_and_tone 实测为 100% 重合，但二者由
KHY_PROMPT_UNIFIED_OUTPUT 门控互斥，属设计内，不在去重范围。

7. 具体改动清单#

#问题（对应 CONCERNS）改动收益风险
1staleKey：git_status 键只有 cwd，会话内冻结cacheKey 折入 git status --short 的摘要哈希状态真实、可观测每轮多一次 git 调用（可缓存 60s）
2staleKey：project_instructions 键只有 cwd折入指令文件集合的 mtime:size编辑 AGENTS.md 立即生效无
3staleKey：skill_catalog 键只有 contextWindowTokens折入技能集指纹新装技能立刻可见无
4volatileInPrefix：deferred_tools_hint 在前缀内移入 L3揭示 deferred 不再破前缀无（本就是每轮值）
5parametrizedStatic：simple_intro / doing_tasks 读 output styleoutput-style 相关句子拆出，移入 L1静态段变纯常量需要一次文案搬迁
6volatileInPrefix：using_your_tools 是 enabledTools 的函数移入 L1（档位是会话级设定）档位切换只失效一次无
7misfiledTaskScale：taskScale 折进 khy_specific 键从键中移除；改为 L4 intent 块 的一个字段措辞变化不再击穿缓存；意图显式需验证 re-selection 行为不变
8规则跨段重复（9,578 字）按 §6.4 收敛到单一真源省 token + 重点突出文案搬迁需逐条回归
9claudeMd 26.4k 整块在动态区按「稳定/易变」切分：章程入 L1，任务态入 L2最大单块进入可缓存前缀最高风险项，见 §10

8. 迁移路径（5 步，每步可字节回退）#

风险

  1. 规则去重可能改变语义：合并措辞会带来行为漂移。
