# [DESIGN-ARCH-098] 系统提示词结构重设计：静态/动态分层与缓存优化方案

## 0. 结论摘要

**诊断**：实测单轮装配产物 66,780 字符，其中**静态前缀只有 13,927 字符（20.9%）**，
而 boundary 之后的动态区占 52,817 字符（79.1%）——**但真正每轮必变的只有约 2,037 字符（3.0%）**。
也就是说，**约 76% 的提示词字节是「会话内基本稳定」的，却被排在了缓存边界之后**。

**方案**：把 boundary 从「常量 / 动态 的分界」重新定义为
**「会话级可缓存前缀 / 每轮区 的分界」**，并按**三轴分离**（稳定性、作用域、触发条件）
把内容重排为五层 L0–L4。核心是**把会话级稳定内容整体前移进可缓存前缀**。

| 指标 | 现状 | 目标 |
|------|------|------|
| 可缓存前缀占提示词字节 | 20.9% | **≥ 60%** |
| 每轮重算字节数 | ≈ 52,817 | **≤ 8,000** |
| 同一规则被重复表述的段数（验证类） | 13 段 | **≤ 2 段** |
| 跨段冗余字符 | ≈ 9,578（14.3%） | **≤ 2,000** |
| 意图信号是否显式 | 否（埋在 `khy_specific` 的 cacheKey 里） | **是（独立 intent 块）** |

## 1. 现状诊断（实测）

### 1.1 分区占比

单轮实测（`cwd` + 一条普通工程类用户消息）：

| 区域 | 字符数 | 占比 |
|------|--------|------|
| 静态前缀（boundary 之前，12 段） | 13,927 | **20.9%** |
| 动态区（boundary 之后） | 52,817 | **79.1%** |
| 合计（21 个装配段） | 66,780 | 100% |
| 其中「每轮必变」候选（`env_info` 1,100 + `git_status` 937） | 2,037 | **3.0%** |

### 1.2 动态区最大的五段

| 段 | 字符数 | 占全量 | 归属 | 真实变化频率 |
|----|--------|--------|------|------------|
| `# claudeMd`（项目指令注入） | 26,378 | **39.5%** | `project_instructions` | 会话内几乎不变 |
| `# Runtime (khy OS v1.1.15)` | 11,587 | 17.4% | `khy_specific` + `model_guidance` | **每轮可能变**（键含 `taskScale`） |
| `# Project structure` | 5,297 | 7.9% | `project_structure` | 顶层增删才变 |
| `# Available Skills` | 2,151 | 3.2% | `skill_catalog` | 装/卸技能才变 |
| `# Planning and verification` | 1,764 | 2.6% | 按需胶囊 | 按意图选片 |

**结论**：占比最大的三块（合计 50.3%）都是「会话级稳定」，却被安排在缓存边界之后。
只有 3% 的字节真正需要每轮重算。

### 1.3 三个具体病灶

**病灶 A：稳定内容被关在缓存门外（最大损失）**
按现状 76% 的字节每轮重新计算/重新计费。在中转（relay）/ DeepSeek 路径上标记被剥离、
命中率完全依赖「最长前缀匹配」，这部分字节**一次都命中不了**。

**病灶 B：每轮变量混在静态前缀里（反向污染）**
`deferred_tools_hint`（router 逐轮算）、`using_your_tools`（`enabledTools` 的函数）、
`simple_intro` / `doing_tasks`（`outputStyle` 的函数）都在 boundary **之前**。
一次 deferred 揭示、一次工具档位切换、一次样式切换，静态前缀即从该点起全部作废。
**当前设计在最需要稳定的位置放了最会变的内容。**

**病灶 C：规则跨段重复（稀释重点 + 虚耗 token）**
按「规则主题」统计跨段覆盖：

| 规则主题 | 被多少段重复表述 | 冗余估算 |
|---------|----------------|---------|
| **改动后验证** | **13 段**（ExecutionDiscipline、ScopeMinimization、PlanningAndRecovery、PlanningAndVerification、ErrorHandling、MultiAgent、FileOperations、CommandExecution、ResponseFormatting、ToneAndStyle、UnifiedOutput、GitOperations、CompactTaskDiscipline） | ~2,500 字 |
| 最小改动 / 不越界 | 6 段 | ~1,700 字 |
| 破坏性/外部动作先确认 | 6 段 | ~1,100 字 |
| 输出简短直接 | 5 段 | ~700 字 |
| 失败先诊断再重试 | 4 段 | ~700 字 |
| 改前先读 | 4 段 | ~600 字 |
| 并行工具调用 | 4 段 | ~500 字 |
| 敏感信息脱敏 / 不确定就说不确定 | 各 3 段 | ~800 字 |
| **合计** | — | **≈ 9,578 字（14.3%）** |

除数量浪费外还有**语义副作用**：同一条规则说 13 遍，模型无法判断哪条是重点——
**重点被平均化**，这直接损害「准确理解意图」。

## 2. 设计原则：三轴分离

现状把三个正交维度揉成一个隐式判断（「这个段放哪」由它在数组里的位置 + 它的 cacheKey
两处共同隐性决定）：

| 轴 | 含义 | 决定 | 现状 |
|----|------|------|------|
| **A 稳定性** | 会不会变、多久变一次 | **位置**（能否进可缓存前缀） | 隐式，散落五处 |
| **B 作用域** | 对谁生效：进程 / 会话 / 项目 / 轮次 | **归属**（属于哪一层） | 未建模 |
| **C 触发条件** | 何时必须出现（无条件 / 上下文变化 / 意图命中） | **加载时机** | 只用了一个「按需胶囊」概念 |

**重设计的第一原则**：**位置只由轴 A 决定，归属只由轴 B 决定，出现与否只由轴 C 决定。**
三者互不越界——这正是当前设计最缺的纪律。

**第二原则**：**能进前缀的字节，绝不留到边界之后。**
判据是「它会不会在**不使用户产生新输入**的情况下变化」：不会 → 进前缀；会 → 进每轮区。

**第三原则**：**同一条规则只有一个真源段落**，其他段落用引用而非复述。

## 3. 目标结构：L0–L4 五层

| 层 | 名称 | 内容 | 稳定性契约 | 失效方式 | 位置 |
|----|------|------|-----------|---------|------|
| **L0** | 不可变内核 | 角色设定、使命、能力边界（能/不能做什么）、绝对红线（安全/合规）、输出格式约定、冲突裁决优先级 | 编译期常量：无参数、无 env、无 `Date` | 只在发版时变 | 前缀最前 |
| **L1** | 会话配置 | 语言、输出风格、模型族与执行纪律档位、权限模式、工具档位（`enabledTools`）、项目指令的**稳定部分**（角色/约定/架构规范） | 会话内不变（装配一次） | 用户显式切换 | 前缀（boundary 之前） |
| **L2** | 项目与记忆 | 项目指令的**易变部分**（当前任务清单、进行中的约定）、`memory`、`references`、`persona/role/companion`、`skill_catalog`、`project_structure` | 只在底层文件变化时变 | 新鲜度戳（`mtime:size` / 指纹） | 边界之后第 1 段（可打第 2 个缓存断点） |
| **L3** | 轮次状态 | `env_info`（时钟）、`git_status`、`task_memory`、`mcp_instructions`、`deferred_tools_hint` | 每轮或每分钟可变 | 每轮重算 | 尾部 |
| **L4** | 本轮意图与任务 | **intent 块**（任务规模、命中的能力胶囊、判定理由）、按需胶囊正文、任务参数 | 每轮必变 | 每轮重算 | 绝对尾部（dead-last） |

### 3.1 与现状的映射

| 现状 tier | 目标层 | 变化 |
|-----------|--------|------|
| `static` | **L0** | 剔除参数化内容（`simple_intro` / `doing_tasks` 的 output-style 依赖） |
| `dynamic_stable` | 拆为 **L1** + **L2** | 会话级配置前移进前缀；文件级内容留在 L2 并修 cacheKey |
| `dynamic_volatile` | **L3** | 位置不变，补齐新鲜度戳 |
| `on_demand` | **L4** | 增加显式 intent 块作为「为什么选它们」的解释 |

### 3.2 关键改动：boundary 后移

**这是本次重设计的核心动作。**

```text
现状：
  [ 常量 12 段 13.9k ] │ boundary │ [ 会话配置 + 项目 + 记忆 + 每轮 52.8k ]
     可缓存 20.9%                            每轮重算 79.1%

目标：
  [ L0 内核 + L1 会话配置 ≈ 40k+ ] │ boundary │ [ L2 项目/记忆 │ L3 每轮 │ L4 意图 ]
       可缓存 ≥ 60%                                 每轮重算 ≤ 8k
                └─ 原生路径在此再打第二个缓存断点，得到两级缓存
```

**为什么可行**：L1 的失效条件是「用户显式切换语言/风格/模型/工具档位」——这是低频的
用户主动动作，不是每轮波动。**为低频事件付出一次前缀失效，换掉每轮 50k 的重算，是划算的。**

**风险与对策**：L1 一旦变化，前缀全部失效（比现状更「一刀切」）。对策是把 L1 收敛到
**真正由用户显式设定**的四五项，任何「系统自动推导」的值都不许进 L1（如 `taskScale`
必须留在 L4）。

## 4. 两部分的组织方式

### 4.1 显式锚点，而非隐式位置

现状靠 `getSystemPrompt()` 返回数组里的位置来隐含分区。目标改为**显式锚点标记**：

```text
<!-- khy:l0 -->
  # Who you are
  # What you can and cannot do
  # Non-negotiable rules
  # Conflict resolution order
  # Output format contract
<!-- /khy:l0 -->

<!-- khy:l1 -->
  # Language
  # Output style
  # Model execution discipline
  # Tooling profile
  # Project charter            ← 项目指令中「不变」的部分
<!-- /khy:l1 -->

__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__

<!-- khy:l2 -->
  # Project state             ← 项目指令中「会变」的部分
  # Memory
  # Persona / Role
  # Skill catalog
  # Project structure
<!-- /khy:l2 -->

<!-- khy:l3 -->
  # Environment
  # Git status
  # Task memory
  # MCP servers
  # Deferred tools
<!-- /khy:l3 -->

<!-- khy:l4 -->
  # This turn                  ← intent 块
  # <启用的能力胶囊正文>
<!-- /khy:l4 -->
```

锚点的三个用途：
1. **可机器校验**：守卫直接断言「L0/L1 必须在 boundary 之前」「L3/L4 必须在最后」，
   不再依赖人工核对数组位置。
2. **可解释**：`khy prompt --explain` 能按层列出字节数与命中情况，缓存问题可定位。
3. **可裁剪**：调试/小模型路径可按层裁剪（如低档模型只保留 L0 + L4）。

### 4.2 声明式装配

把「哪一段、属于哪层、cacheKey 是什么、什么时机装配」从代码里的调用顺序
**提升为一张声明表**（即 [DESIGN-PROMPT-002] 已有的 `promptSectionTaxonomy.js`，
在 P1 阶段把 tier 从 `static/dynamic_*` 重命名为 `L0..L4`）。
装配器只消费声明表，杜绝「新增段忘了声明分层」。

## 5. 加载时机（四时机模型）

现状只有「每轮全部重跑一次」和「段缓存」两种机制混用。目标明确四个时机：

| 时机 | 触发 | 装配内容 | 频次 | 字节量目标 |
|------|------|---------|------|-----------|
| **T0 进程启动** | 进程拉起 | **L0** 全量：编译期常量，进程级复用一份不可变字符串 | 1 次/进程 | ≈ 14k（零成本复用） |
| **T1 会话开始** | 新会话 / `/clear` / `/compact` | **L1** 全量：读语言、风格、模型、权限、工具档位、项目章程；装订一整块 | 1 次/会话 | ≈ 26k |
| **T2 上下文变更** | L2 各段的戳变化（文件 mtime、技能集指纹、git 状态摘要） | 只重算**戳变了的那一段** | 低频 | 0–5k |
| **T3 每一轮** | 每次用户消息 | **L3 + L4**：时钟、git、任务板、MCP、deferred、intent 块、胶囊选片 | 每轮 | **≤ 8k** |

### 5.1 每轮重算的字节预算

**硬指标：T3 每轮重算 ≤ 8,000 字符**（现状 ≈ 52,817）。构成：

| 段 | 预估 | 说明 |
|----|------|------|
| `env_info` | ~1,100 | 时钟桶，60s 滚动 |
| `git_status` | ~940 | 折入 status 摘要哈希 |
| `task_memory` | 0–1,500 | 无任务时为空 |
| `mcp_instructions` | 0–800 | 无 MCP 时为空 |
| `deferred_tools_hint` | 0–600 | 无 deferred 时为空 |
| **intent 块** | ~300 | 新增 |
| 命中的胶囊（1–3 个） | 1,000–3,000 | 其余留空 |

### 5.2 绝不每轮重算的清单（必须进 T0–T2）

`claudeMd` 项目指令、`Runtime` 执行纪律、`Project structure`、`Available Skills`、
`Memory`、`persona/role/companion`、语言与风格、工具档位描述。

## 6. 提升意图理解的四个机制

缓存的另一个前提是**不要为了缓存牺牲理解**。以下四项专门解决后者。

### 6.1 本轮意图块（intent block）—— 把「系统认为你要做什么」说出口

现状：意图判定（任务规模、命中哪些胶囊）**只体现为「哪些段出现了」**，模型只能靠猜；
而 `taskScale` 还被折进 `khy_specific` 的 cacheKey —— 既破了缓存，又没让模型看清意图。

目标：在 L4 顶部注入一个约 300 字符的短块：

```markdown
# This turn
- Task scale: large
- Active guidance: file_operations, command_execution, planning_verification
- Because: the request names a source file and asks for a behavioural fix
- Note: if this reading of your intent is wrong, say so and the guidance set will change
```

三个作用：
1. **模型看得见**：不必再从段落有无反推意图，减少误用（例如把"改一行"当重构来规划）。
2. **用户可纠偏**：显式写「读错了就说」——用户一句"不对，我要的是 X"即可让 re-selection 生效。
3. **不破缓存**：它本身就在 L4（每轮区），把 `taskScale` **从 `khy_specific` 的 cacheKey 里移除**，
   L1/L2 因此不再受逐轮评分影响。

### 6.2 胶囊自解释

每个能力胶囊首行写明触发条件：

```markdown
# File operations
Applies when: reading, editing, or creating files.
Since: the request references a source file.
```

模型因此知道「这段为什么在这儿」，比不知道来由的规则更容易被正确执行；
也让「胶囊该不该出现」的调试变得可读。

### 6.3 冲突裁决优先级（写进 L0，只写一次）

现状：规则之间的优先级从未声明，模型在矛盾指令（如「最小改动」vs「完整验证」）之间摇摆。
L0 明确一条链，全局只此一处：

```text
1. 安全与合规红线（绝对）
2. 用户在本轮消息中的显式指令
3. 项目章程（khy.md / AGENTS.md 中的约定）
4. 本轮能力胶囊的建议
5. 风格与措辞偏好
```

### 6.4 规则去重（单一真源 + 引用）

按 §1.3 的实测重复清单合并。合并原则：**保留最完整的表述，其余段改为一句引用**。

| 规则主题 | 真源段落（保留全文） | 其他段处理 |
|---------|-------------------|-----------|
| 改动后验证 | `# Verification`（由 PlanningAndVerification 收敛而来） | 13 → 改为 1 句引用，或直接删除 |
| 最小改动 / 不越界 | `# Scope discipline`（ScopeMinimization 收敛） | 6 → 2（保留 L0 的总则 + 真源段） |
| 破坏性动作先确认 | `# Acting with care`（Actions 收敛） | 6 → 1 |
| 失败先诊断再重试 | `# Error handling`（ErrorHandling 收敛） | 4 → 1 |
| 改前先读 | `# File operations` | 4 → 1 |
| 并行工具调用 | `# Using your tools` | 4 → 1 |
| 输出简短直接 | `# Output and tone` | 5 → 1 |

**注意**：`tone_and_style` 与 `unified_output_and_tone` 实测为 100% 重合，但二者由
`KHY_PROMPT_UNIFIED_OUTPUT` 门控**互斥**，属设计内，不在去重范围。

## 7. 具体改动清单

| # | 问题（对应 CONCERNS） | 改动 | 收益 | 风险 |
|---|---------------------|------|------|------|
| 1 | `staleKey`：`git_status` 键只有 `cwd`，会话内冻结 | cacheKey 折入 `git status --short` 的摘要哈希 | 状态真实、可观测 | 每轮多一次 git 调用（可缓存 60s） |
| 2 | `staleKey`：`project_instructions` 键只有 `cwd` | 折入指令文件集合的 `mtime:size` | 编辑 `AGENTS.md` 立即生效 | 无 |
| 3 | `staleKey`：`skill_catalog` 键只有 `contextWindowTokens` | 折入技能集指纹 | 新装技能立刻可见 | 无 |
| 4 | `volatileInPrefix`：`deferred_tools_hint` 在前缀内 | 移入 **L3** | 揭示 deferred 不再破前缀 | 无（本就是每轮值） |
| 5 | `parametrizedStatic`：`simple_intro` / `doing_tasks` 读 output style | output-style 相关句子拆出，移入 **L1** | 静态段变纯常量 | 需要一次文案搬迁 |
| 6 | `volatileInPrefix`：`using_your_tools` 是 `enabledTools` 的函数 | 移入 **L1**（档位是会话级设定） | 档位切换只失效一次 | 无 |

## 8. 迁移路径（5 步，每步可字节回退）

对齐仓库既有的「门控 + 逐字节回退」文化：每步独立门控，关闭后产物与改动前逐字节一致。

| 阶段 | 内容 | 门控 | 验收 | 回退 |
|------|------|------|------|------|
| **P0** | 打锚点：在装配产物中插入 `<!-- khy:lN -->` 标记，**不改变段序与内容** | `KHY_PROMPT_ANCHORS` | 除锚点外逐字节一致 | 关掉即完全还原 |
| **P1** | 修 3 处 cacheKey 戳（改动 1–3），并把 `taskScale` 移出键（改动 7 的一半） | `KHY_PROMPT_FRESH_KEYS` | 单测 + 会话内状态更新实测 | 关掉回旧键 |
| **P2** | **boundary 后移**：`using_your_tools` + output-style 相关句子 + 项目章程移入 L1 | `KHY_PROMPT_L1_PREFIX` | 前缀占比 ≥ 60%；缓存命中率提升可观测 | 关掉回旧序 |
| **P3** | 引入 **L4 intent 块**（改动 7 的另一半） | `KHY_PROMPT_INTENT_BLOCK` | 意图纠偏用例 + re-selection 行为等价 | 关掉不注入 |
| **P4** | 规则去重（改动 8），按主题逐条合并、逐条回归 | 每主题一个子门控 | 主题跨段数达标；行为回归测试全绿 | 按主题单独回退 |

## 10. 风险与不做的事

**风险**

1. **`claudeMd` 切分（改动 9）是最高风险项**。26.4k 字符是用户项目约定的唯一入口，
   切错会**静默丢失上下文**——而且丢失是「模型不再遵守某条约定」这种难以察觉的形式。
   对策：先只做「加新鲜度戳 + 保持整块位置」，切分单独立项、单独验收。
2. **L1 一刀切失效**：L1 内容比 L0 多，变化时前缀失效范围更大。
   对策：L1 只放用户显式设定项；任何系统推导值（`taskScale`、意图、工具推荐）不得进 L1。
3. **规则去重可能改变语义**：合并措辞会带来行为漂移。
   对策：逐主题独立门控、逐主题回归（P4 分解为子门控）。
4. **原生路径断点数**：多打一个断点会占用 provider 的断点配额。
   对策：L2 断点做成可配置，默认仅在提示词总量超阈值时启用。

**不做的事（明确划界）**

- 不改任何规则的**语义**，只改位置、去重与暴露方式。
- 不做语义召回式胶囊选择（向量检索）——那是另一个课题，且会引入不可预测的字节变化。
- 不做自动压缩/摘要式裁剪：它会让「前缀稳定」这个前提失效。
- 不为小模型单独维护第二套结构：`HARDCORE_SYSTEM_PROMPT` 走同一份 L0 的子集
  （按锚点裁剪），而非另写一套。

### 12.3 完成定义（DoD）

本次视为「完成」需同时满足：

1. **零产物变更可证**：门控关时，装配产物与改动前逐字节一致（AC-1）。

### 12.4 文档未覆盖处的假设与偏离（实施时明确声明）

| # | 情形 | 处理方式 | 理由 |
|---|------|---------|------|
| A1 | 098 §8 的 P1 写「把 `taskScale` 移出键（改动 7 的一半）」 | **不执行**该半步 | `getKhySpecificSection` 的**内容**依赖 `taskScale`（`if (opts.taskScale === 'large')`）。只移键不移内容 = 把段缓存冻结在首轮的 taskScale 上，**制造一个新的 staleKey**。改动 7 必须与 P3（intent 块）原子完成 |
| A2 | 锚点的默认值 | 定**默认关**（`opt-in`） | 锚点进入模型可见文本（约 +1.4KB），P0 只服务度量/守卫，不应改变线上产物。且 flagRegistry 对未登记 name 保守放行为 true —— 不登记就等于默认开，故**必须**显式登记 |
| A3 | 锚点标注的是现状还是目标 | 标注**现状** | `deferred_tools_hint` 目标层是 L3 但当前位于 prefix 槽 → 锚点如实标 `prefix`。锚点必须先反映现实，P2 真正搬动后才改 slot 语义 |

| A5 | 扁平路径如何避免锚点污染 | `assembleSystemPrompt` **过滤锚点元素**（与它已过滤 boundary 同款） | 曾有方案是「字符串层 strip 掉标记」，但段正文可能自带前导换行，导致无损重建不可行；在装配层过滤是结构性解法 |
| A6 | 测试中的时间不确定性 | 单测内**冻结 Date** | `# Environment` 段含墙钟时间戳（不受 `KHY_SYSTEM_CLOCK` 门控影响），两次装配跨秒即产生伪差异 |
