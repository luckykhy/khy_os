## 1. 结论先行

**六条投诉全部有对应物，且互相独立。** 不是一件事的不同说法，是六件事叠加：

| 投诉 | 实测对应物 |
|---|---|
| 1 不美观 | 291 处 hex 颜色散落在 26/48 个 vue/css 文件里，token 体系（64 个 custom prop）只被 3 个文件真正遵守；`KhyFloatBall.vue` 一个组件内 42 个 hex + 30 个 `rgba()`，是「第二套设计系统」 |
| 2 接线不对 | **42 处 API 调用指向不存在的端点**，其中 2 个整页功能完全空转（`/usage`、`/pricing`）；1 个菜单项点进去是 NotFound；**6 个 API 命名空间只在守护进程里有，单体服务没有** |
| 3 功能区划分不合理 | 管理员不是一个区域，是 `el-switch` 切 `workspace` 字段把整个侧边栏换掉（`stores/user.js:86`）；23 个管理页在裸路径，2 个在 `/admin/*` |
| 4 有的功能不能用 | `routes/crossPlatform.js` 238 行**完全没有鉴权**，而 `Settings.vue:486/:504` 用裸 `fetch()` 不带 token 调它——这是全应用唯一的两处未鉴权写入 |
| 5 重复嵌套 | `Layout.vue` 到叶子菜单项 6–7 层深；导航声明了两遍（路由表 + `Layout.vue` 两个硬编码数组）；`resolveWsUrl` 复制粘贴在 5 个文件里 |
| 6 页面冗余 | GuiEval 与 WebFrontendEval 两栈 14 个文件、dashboard 相似度 **Jaccard 0.97**；`/gateway` 与 `/my-gateway`、3 个「AI 渠道端点 + 加密 Key」页面（`ChannelApis` + `ChannelApiEditor` + `BridgeChannels`） |

**核心判断：这不是重做 UI 的任务，是「收口 IA + 修接线」的任务。** 视觉是症状，接线和 IA 是病根——因为 40 处 404 全被 `catch {}` 吞掉返回空默认值，所以用户看到的是「功能不能用」而不是「报错」，而 `TODO`/`FIXME` 全仓为 0，代码库里没有留下任何「这里坏了」的痕迹。

**一条不采纳的常见做法**：调研的 7 个项目里 **7/7 都没有独立的 admin 登录页，6/7 没有独立的 admin 前端**。所以不建第二个 shell、不建 `/admin/login`——「管理员也是用户」应该通过角色位 + 导航数据化解决，不是通过应用分区解决。`/admin/*` 路径前缀**保留**（13 个以上管理页，路径隔离有实际价值），但这些路由全部渲染在**同一个** `AuthenticatedLayout` 内，见 §4.2。当前实现恰好用了唯一一个反模式（persona 切换器），这是 Phase 2 要拆掉的东西。

**仓库地址更正（原提示里的都不对）**：`ForumForge/newapi` 与 `Calcium-Ion/new-api` 均 404，正名是 `QuantumNous/new-api`；`chat2db-community/chat2db` 404，正名 `OtterMind/Chat2DB`。**「cpa」= CLI Proxy API**，由约 8 个独立第三方仓库交叉印证；但**上游仓库 URL 无法核实**（两个候选都 404，疑已改名或下架）——这一点不能填成猜测。

### 2.1 规范（多数项目都这样做）

1. **认证壳 + 公共壳分离，6/7。** New API 的 `authenticated-layout.tsx` 与 `public-layout.tsx` 是同目录兄弟组件；NPM 在 `Router.tsx` 里三个显式分支。**除登录外的所有路由都渲染在认证壳内。**
2. **登录是唯一在认证壳外的路由，7/7**（有账号概念的项目）。New API 额外把 `/pricing`、`/about`、`/setup` 放壳外，因为它兼做营销站——我们不做营销站，这条不适用。
3. **无独立 admin 登录页，7/7。** 这个生态里根本不存在 `/admin/login` 这个概念。
4. **无独立 admin 前端/SPA，6/7。** 唯一例外 AppFlowy Cloud 的 admin 是**另一个产品**，不是同一产品的另一个视图。
5. **数字角色阶梯 0/1/10/100**：New API `GUEST/USER/ADMIN/SUPER_ADMIN`，One API `Guest/Common/Admin/Root`（fork 继承）。若希望与生态保持可比，值得原样采用。
6. **首启设置是全屏门控，不是弹窗**——1Panel/NPM 用 `!health.setup` 整个换掉应用，New API 有 `/setup` 路由。
7. **登录审计日志是一等公民的管理页**（1Panel `views/log/login/`、NPM `/audit-log`）。

### 2.2 例外（值得单独记一条，避免误当「标准功能」）

- **「忘记密码」只有 2/7 有。** New API（完整流程）和 One API（berry 视图）有；**1Panel、Nginx Proxy Manager、CPA、Chat2DB、AppFlowy Cloud 都没有**。1Panel 唯一的「reset」是宿主机上跑的 Go CLI 命令 `core/cmd/server/cmd/reset.go`。**在这个生态里，自建运维者带外恢复凭据是常态而非例外。** 我们要做忘记密码页，是**超过**参考集的事——这是对的（khyos 有普通用户，不只是运维者），但不能认为参考项目漏了它。
- **角色机制有四种，没有赢家**：New API 用 `role >= ROLE.ADMIN` 数值比较；1Panel 用 `isAdmin` + `permissions[]` 字符串权限码；NPM 用 `{section, verb}` 权限对；One API 用每菜单项一个 `isAdmin` 布尔。必须自己选一个。
- **侧边栏 3/7，顶栏横菜单 2/7**，无强多数，两者都可辩护。
- **7/7 都不渲染面包屑**。One API 在**每个**菜单项上都显式设 `breadcrumbs: false`——这是刻意扁平化。这个体量的管理台不需要面包屑。

### 2.3 直接可迁移的决策

1. **一个壳、两个布局。** `PublicLayout` / `AuthenticatedLayout` 同目录兄弟，共享组件。
2. **管理员是导航条目，不是路由前缀。** New API 把 `admin` 做成 `NavGroup`；NPM 把 Users 做成十个平级路由之一。两者都对。**加 `/admin` 什么都不换来，只换来一套重复的 shell 代码。**
3. **导航和路由两处都要拦。** New API 既隐藏 admin 分组，又在 `beforeLoad` 里把非 super-admin 重定向到 `/403`。One API 只隐藏菜单项、`AuthGuard` 从不查角色——**这就是「接线不对」的形状**。永远不要只靠隐藏导航。
4. **粗角色位 + 细权限码字符串。** 1Panel 的 `isAdmin` + `permissions[]` 是分层的正确做法：单个布尔无法表达「能看日志但不能管用户」。所有判定收进**一个** util 文件（1Panel `rbac.ts`），不要散在每页里。
5. **导航项建模成带 `requiredRole`/`permission` 字段的数据。** 这样渲染导航就是一个 map，加一页是数据变更而不是代码变更。这是让「管理员也是用户」变便宜的关键。
6. **登录方式由服务端开关决定。** New API 从 `/api/status` 读约 10 个布尔决定显示密码/passkey/OAuth/微信。一套构建、运维可选。
7. **登录路由文件保持薄。** New API 的 `sign-in.tsx` 约 50 行，UI 全在 `@/features/auth/sign-in/components/`。登录逻辑是你写测试最重的代码（重定向消毒、OAuth 弹窗、回调模式都要测），路由层要保持声明式。

### 2.4 这个品类特有的两个坑

1. **两种「auth」概念会撞名。** 代理/网关类产品里，**运维者认证**（谁在用管理台）和**上游凭证认证**（Claude/Codex/Gemini 的 OAuth 文件）是完全无关的两件事。CPA 的解法是永远把凭证面命名为 `authFiles`，绝不叫 `auth`。**khyos 同时管两者**（有 `ChannelApis.vue` 存上游 Key、也有 `Login.vue`），这个命名纪律必须第一天立住， retrofit 很贵。
2. **不要把壳布局叫 `loginLayout`。** Chat2DB 就这么做，`src/layouts/loginLayout` 包着 `/dashboard`、`/workspace`、`/plugin`、`/settings/:tab`，它的 i18n `login.ts` 装的是数据库连接文案。读者（或 AI）会得出「这个应用没有登录页」的结论。布局按它包含什么命名。

## 3. 现状证据（按四个表面）　·　主要服务 Phase 1（§3.6→Phase 4，§3.7→Phase 5）

### 3.1 登录页 —— 存在，但有一个必坏按钮

调用 `GET /api/auth/default-admin`（`Login.vue:89`）、`POST /api/auth/login`（`stores/user.js:42`）、`GET /api/auth/me`（`stores/user.js:58`）。

后端：`/login` 与 `/me` 两个服务端都有（`routes/auth.js:242/:533`；`aiManagementServer.js:2178/:2184`）。**`/default-admin` 只在守护进程有**（`aiManagementServer.js:2181/:3211`），`routes/auth.js` 里该字符串出现 0 次。所以生产（单体服务 `dist/`）环境下这个按钮必然 404，代码里的退化只是给一行 hint（`Login.vue:99`）。

### 3.2 忘记密码页 —— 后端建好了两套，前端一个都没有

**这是最大的单块缺口，也是最典型的「接线不对」。**

`server.js:482` 挂载 `/api/password-reset` → `routes/passwordReset.js`（162 行），**实际注册的三个端点**：

```
POST /api/password-reset/get-question   (passwordReset.js:34, resetLimiter)
POST /api/password-reset/reset          (passwordReset.js:73, resetLimiter)
POST /api/password-reset/set-security   (passwordReset.js:126, authMiddleware)
```

这是**安全问题方案**。但 `src/services/cliAuthService.js` 调的是另一套：

```
POST /api/password-reset/send-code    (cliAuthService.js:785)
POST /api/password-reset/verify-code  (cliAuthService.js:821)
```

`findstr /s /c:"send-code" /c:"verify-code" services\backend\src\routes\*.js` **返回 0 命中**。**邮件验证码方案的后端端点根本不存在。** 同一件事存在两套设计，只有安全问题方案被挂载，CLI 调的是不存在的那套。

前端引用 `password-reset` / `get-question` / `set-security` / `找回密码`：**0 处**。无视图、无路由、无菜单项。

另外 `POST /api/auth/change-password`（`routes/auth.js:679`）存在且前端从不调用。

### 3.3 用户页 —— 存在但是个空壳

`views/UserHome.vue`，276 行，路由 `/home`（`/` 重定向过来）。构成：渐变 hero + 动画 glow div、首次访问可关闭引导 `el-alert`（localStorage `khy_ai_home_onboarded`）、成功 `el-alert`、`el-row` 两张卡——「快速开始」（进入 AI 对话 / 切换到管理员视图）和「连接提示」（3 条硬编码 `<li>`，讲 Network Errors 和 `ai-backend` 容器）。

**零 API 调用。** 它纯粹是导航装饰 + 排障文案。而后端 `routes/user.js`、`routes/apiKey.js`、`routes/dashboard.js`、`routes/webauthn.js` 都已存在。

### 3.4 管理员页 —— 不是一个页面，是三种东西拼起来的

没有 `Admin.vue`。所谓「管理员区域」实际是：

- `stores/user.js:7` `WORKSPACE_STORAGE_KEY = 'khy_ai_workspace'`，`:86` `toggleWorkspace()` 在 `user`↔`admin` 间翻转
- `Layout.vue:83-90` 头部一个 `el-switch`，`:274-278` 翻转后把侧边栏在 `USER_MENU`（11 项）和 `ADMIN_MENU`（15 项）之间整体重写，并路由到 `/dashboard` 或 `/home`

## 4. 信息架构方案　·　Phase 2

### 4.1 角色模型

采用 New API 的数字阶梯（与生态可比），配 1Panel 的字符串权限码：

```js
// src/auth/roles.js —— 唯一真源
export const ROLE = { GUEST: 0, USER: 1, ADMIN: 10, SUPER_ADMIN: 100 } as const;
export const PERMISSIONS = [
  'channel.view', 'channel.manage',
  'gateway.view', 'gateway.manage',
  'billing.view', 'billing.manage',
  'usage.view',
  'user.view', 'user.manage',
  'eval.view', 'eval.manage',
  'audit.view',
  'system.manage',
];
```

三条纪律：

1. **判定收进一个文件。** `src/auth/permissions.js` 导出 `hasRole(user, minRole)` 与 `can(user, perm)`。任何页面**不许**自己写 `role === 'admin'`。
2. **导航和路由两处都拦。** 导航按 `requiredRole` / `permission` 过滤；路由守卫 `beforeEach` 二次校验，不满足跳 `/403`。**不允许只靠隐藏导航。**
3. **角色位与权限码分工**：角色位决定「你能不能进管理类导航组」，权限码决定「组内某项你能不能碰」。粗角色位是唯一的导航分组依据。

**同时删掉 `workspace`。** `stores/user.js` 的 `workspace` 字段、`WORKSPACE_STORAGE_KEY`、`toggleWorkspace()`、`Layout.vue:83-90` 的 `el-switch` 全部移除。角色是服务端返回的用户属性，不是客户端可切的状态。

### 4.2 路由结构

### 5.1 登录页 `/login`

**布局**：`PublicLayout` 内单栏居中。品牌区（上）+ 表单卡（下），最大宽 430px。

**字段与元素**：
1. 品牌 logo + 产品名 + 一行副标题（不写「统一入口」这类自述式文案，写「管理你的 AI 渠道与用量」这种能力描述）
2. 用户名或邮箱（一个输入框，服务端区分）
3. 密码（`show-password`；密码框右上内嵌「忘记密码?」小字链，位置 `end-0 -top-0.5`，样式 `text-muted-foreground text-sm`——New API 的做法）
4. 登录方式区：**由服务端开关驱动**，不是前端硬编码
5. 提交按钮「登录」

**服务端开关（新增 `GET /api/auth/capabilities`）**

当前 `/api/auth/default-admin` 是「按钮式」探测，粒度不够。改为一次性返回能力位：

```json
{
  "passwordLogin": true,
  "oauthProviders": ["github"],
  "cliTokenLogin": true,
  "defaultAdminAvailable": false,
  "passwordReset": { "mode": "security-question" },
  "setupRequired": false
}
```

`passwordLogin=false` 时密码框整体不渲染；`setupRequired=true` 时整个应用替换成 `/setup` 全屏（§2.1 规范 6）。`passwordReset.mode` 直接决定「忘记密码?」链接是否显示——**不要前端猜后端实现了哪套**。

**行为契约（每条都要有测试）**

| 场景 | 行为 |
|---|---|
| 已登录访问 `/login` | 重定向到 `?redirect=` 消毒后的目标，或 `/home`。**重定向目标必须消毒**，拒绝外部域名，防 open redirect |
| 未登录访问受保护路由 | 跳 `/login?redirect=<当前路径>` |
| 登录失败 401 | 错误信息走「问题 + 识别码 + 修复」三段式（仓库规则 2.2），不写「登录失败」 |
| 登录成功 | 拉 `/api/auth/me`，写角色位，按角色落 `/home` 或 `/admin/overview` |
| `defaultAdminAvailable=false` | 不渲染那个按钮（当前 `Login.vue:86-103` 的退化逻辑可以删） |

**删除**：2 个装饰性 orb div（装饰不是功能）、提示段里的排障文案（属于文档，不属于登录页）。

### 5.2 忘记密码页 —— 先定方案，再写 UI

**第一步是决策，不是画页面。** 后端存在两套方案，必须先选一套并补齐：

| 方案 | 后端现状 | 评估 |
|---|---|---|
| **A 安全问题** | 三个端点已挂载（`get-question`/`reset`/`set-security`），有 `resetLimiter` 限速 | 可用。但需要用户**先设置过**安全问题，否则这条路不通 |
| **B 邮件验证码** | CLI 在调（`cliAuthService.js:785/821`），**端点不存在** | 是行业常态（New API 走这条），但要先建 `send-code`/`verify-code` |

**建议：A + B 双轨，A 立即交付，B 排 Phase 4。**

理由：A 后端已在跑，UI 补上就能用，是当前唯一的可用恢复路径；B 是主流方案且 CLI 已经假设它存在（CLI 现状是坏的），但需要后端新增端点 + 邮件投递通道，超出「修接线」范围。**`/api/auth/capabilities.passwordReset.mode` 必须反映真实可用的方案组合**，UI 只渲染服务端说有的路径——这是 §5.1 服务端开关纪律的直接应用。

**页面拆分（3 个页面，不是 1 个）**

```
/forgot-password      输入账号 → 取回安全问题
  字段：账号（用户名或邮箱）
  提交：POST /api/password-reset/get-question
  结果：显示问题 → 进 /reset-password?token=
  防枚举：账号不存在时返回与存在时**同形**的成功响应（服务端已用 resetLimiter，前端不可泄露差异）

/reset-password       回答安全问题 → 显示新密码
  字段：安全答案、新密码、确认新密码（新密码由**用户自己输入**，不采用 New API 的服务端生成方案——
        那套适合运维者控制发件人的自建场景，khyos 有普通用户，密码强度策略应由用户掌控）
  提交：POST /api/password-reset/reset
  成功：直接跳 /login 并 toast「密码已更新，请使用新密码登录」。**不显示新密码**
        （新 API 把服务端生成的密码显示在只读 mono 输入框里并自动复制，那套的前提是用户从不输入密码）

/reset-password?invalid=1   失效链接的降级态：destructive Alert + 「返回登录」
                           不单独建路由，用查询参数区分，避免路由表膨胀

/profile 内的「设置安全问题」
  提交：POST /api/password-reset/set-security（需要 authMiddleware，已在）
  只在 /security 页出现，登录后才能设置
```

**同时补上改密码**：`POST /api/auth/change-password`（`routes/auth.js:679`，后端已有、前端 0 引用）放进 `/security`。这是与忘记密码页**不同**的功能——忘记密码是「进不来时」，改密码是「进得来时」。两者不能共用一个页面。

**必须新增的后端工作量**：`GET /api/auth/capabilities`（§5.1）。**忘记密码页本身零后端工作量**（A 方案），这是本方案里投入产出比最高的一块。

### 6.2 B 类：双服务端端点集不统一

6 个命名空间（workflow / marketplace / plugins / user-gateway / gui-eval / web-frontend-eval / proxy-egress，约 3,900 行视图）只在守护进程有。**必须先决策**：

- **方案 X：单体服务补齐这 7 组路由**（`server.js` 挂上 `routes/workflow.js` 等——部分文件已存在于 `routes/`：`guiEval.js`、`webFrontendEval.js`、`proxySubscription.js`、`market.js` 已在，需核对具体缺哪些）
- **方案 Y：文档化「这些页面需要守护进程」并让 UI 在探测到单体服务时隐藏这些入口**

**不建议两种都不做**——现状（生产静态服务 `dist/` 时整片功能 404 且无提示）是最差选项。方案 X 是正确终态；方案 Y 是过渡态。

**实测（2026-09-08）与裁定**：本节开头「6 个命名空间只在守护进程有」是**部分过期**的判断。逐文件核对后，单体 `services/backend/src/routes/` 已经有 `guiEval.js`（12 端点）、`webFrontendEval.js`（16）、`proxySubscription.js`（5）；真正只在守护进程的是 **`workflow`（19）+ `marketplace`（5）+ `plugins`（8）= 32 个端点**。32 ≫ §0.1 给方案 X 的 ≤10 阈值，因此**裁定方案 Y**：`src/api/daemonProbe.js` 探测两个命名空间根，只在明确的 404/405 时判定不可用（5xx / 网络错误 / 静态 `index.html` 兜底一律失败放行），`NAV` 条目用可选 `daemon` 字段声明依赖，`visibleNavGroups` 按可用性过滤，`Layout.vue` 挂载时探测。落地记录与残留（深链仍加载、由页面自身错误态报告）见 IMPL-RPT-048 §8.1。

另外两点实测修正：① 前端只有单一 `VITE_AI_API_BASE_URL`，没有按命名空间的分流，所以这些命名空间要么整体挂上、要么整体不可达，一次探测足够；② `/proxies` **不隐藏**——它的订阅半区 `/api/proxy-subscriptions` 在单体存在，出站半区 `/api/proxy-egress` 由 `useProxies.js` 自行降级，整项隐藏会连带藏掉能用的订阅管理。

1. **接线**：前端所有 REST 调用都有真实后端端点；任意端点失效时页面显示错误态而非空表格。
