[TOOLING-010] 维护成本可观测#

规则卡 · 格式依据 [MGMT-STD-008] §1（frontmatter 14 字段 + 六小节）。

字段真源是 docs/10_规范/registry/RULES-REGISTRY.json（GOV-TOOL-006 校验），
本文件由 node scripts/docs/gen-rules-cards.js 生成，禁止手改（同 [MGMT-STD-007] R6 对 .html 孪生件的约束）。
正文原文在 ssot 指向的位置：docs/03_DESIGN_设计/DESIGN-ARCH/[DESIGN-ARCH-127] khyos 可维护性诊断与减负方案.md。

约束#

四项读数必须可复现地取得，且每一项的判据必须由纯叶子计算（scripts/lib/touchCostProbe.js）而非在报告中手工填写：① 硬触点清单里每一项都必须附「为什么会红」的可复核机制名（守卫名或契约名），不得使用形容词；② required=false 的触点不得计入合计（虚高数字会污染优先级判断）；③ 波及面用 git grep 实测而非估计；④ gate 分布与永不执行条数直接从登记表派生。本规则只读、只报告，恒 exit 0，不阻断任何提交。

授予权力#

授权维护者用一条命令取得「维护成本」的客观读数，无须依赖印象或个别案例；授权把 M1–M5 的收益写进结论（落地前后各跑一次即可对比）；授权在减负方案评审时以本规则的输出作为「该先修哪个」的输入。边界：本规则不裁决任何措施应否落地、不自动改动任何文件、也不代替 [DESIGN-ARCH-127] 的规范判断。

提供福利#

使「khy-os 难以维护」从主观抱怨变为可复现数字，并防减负成果反弹：在没有读数之前，方案落地后无从判断「触点是否真的从 13 处降下来」，也没人记得原来的数字。实测初值：新增规则硬触点 13 处（其中 6 处为可派生生成物）、check-repo-layout 被 20 个文件引用、文档 md:html = 906:895、gate=advisory 的永不执行规则 15 条。这些数字此前不出现在仓库任何输出里。

反例#

见 ssot 指向的真源原文；本卡不复制反例，以免与真源漂移。

校验方式#

人工评审（该规则暂无机械守卫）

例外#

两类：① 探针依赖 git 命令，在非 git 环境（如解包后的发布产物）降级为基线事实部分为空，不报错；② 触点清单本身是声明式常量，允许人手工维护——因为「哪些触点会红」随守卫变化，无法自动推导，这是本规则刻意保留的人工输入点。
