# [DESIGN-STD-001] 软件文档标准映射规范

> **定位**：将国际软件文档标准（ISO/IEC/IEEE 15289:2019 + IEEE 1063 + ISO/IEC 26514）与中国国标（GB/T 8567-2006）映射到 khy-os 仓库，保证**清晰不啰嗦**——只保留与开源/AI 平台相关的类别。
> **与 [DESIGN-DOC-001] 的关系**：[DESIGN-DOC-001] 管「怎么命名」，本文管「文档内容该长什么样」。

---

- 数据要求规格说明书 → 已被架构设计吸收
- 模块开发卷宗 → 已在代码注释中体现
- 软件开发进度月报 → 由 Git 提交历史替代
- 项目改动报告 → 由 CHANGELOG + PR 替代

## 2. 文档元数据（ISO 15289 §6.1 强制）

每份文档**必须**在首行后包含以下元数据，缺一即不合规：

| 元数据 | khy-os 实现 | 说明 |
|---|---|---|
| 文档标识符 | `[STAGE-TYPE-NNN]` 编号 | 全局唯一，见 [DESIGN-DOC-001] §2 |
| 版本与日期 | 版本历史表格末行 | 必须含日期 |
| 适用范围 | `> **定位**：管什么 + 与哪篇真源的关系` | 一句话，禁止超 50 字 |
| 引用文档 | `## 相关文档` 章节（可选） | 引用编号 + 路径 |
| 术语与缩略语 | `## 术语` 章节（可选，按需） | 仅含本文首次出现的术语 |

> **判定**：缺少编号/版本/适用范围任一项 = 违规，必须补齐。

---

## 3. 文档内容模板（清晰版）

每篇文档**必须**包含以下 4 部分，不多不少：

```markdown
# [STAGE-TYPE-NNN] 中文标题

> **定位**：管什么 + 与哪篇真源的关系
> **结论**：核心要求（≤30 字）

## 1. 做什么

用 1-3 句说明本规范约束的对象和范围。禁止背景铺垫。

## 2. 怎么做

用表格或列表给出具体要求。每行必须可判定。

## 3. 破了怎么办

给出违规判定方式或替代方案。

## 4. 版本

| 版本 | 日期 | 变更 |
|------|------|------|
```

---

## 4. 清晰不啰嗦的三条纪律

1. **结论先行**：首段 `> **一句话结论**：...`，禁止先写 200 字背景再说结论；
2. **表格优于段落**：同一意思有 3 个以上要点 → 必须用表格，不用连续段落；
3. **一个概念一篇**：每个规范只讲一个概念。跨概念 → 拆子篇或引用相邻规范。

---

## 6. 文档生命周期（ISO 15289 §5）

| 阶段 | khy-os 实现 | 说明 |
|---|---|---|
| 创建 | AI 按骨架写 + 编号 | [DESIGN-DOC-001] §12 |
| 审查 | `npm run check:layout` + `check-gov-rules.js` | CI 守卫强制 |
| 发布 | Git commit + CHANGELOG 记录 | 版本号同步见 [DESIGN-SEMVER-001] |
| 维护 | 版本历史表格追加行 | 不删旧版，只追加 |
| 归档 | 移入 `11_报告/历史/` 或 `_deprecated/` | 不删除，保留追溯 |

> **判定**：文档无版本历史 = 不可追溯 = 违规。
