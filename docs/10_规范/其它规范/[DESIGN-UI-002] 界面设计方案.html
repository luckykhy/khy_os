[DESIGN-UI-002] 界面设计方案（提案）#

状态：提案（Proposal）—— 待评审后落地
定位：在 [DESIGN-FE-001] 前端页面规范 与 [DESIGN-UI-TEST-001] UI 设计验证测试规范
之上，定义 khy-os 前端视觉语言与信息架构的目标态，并给出可分批落地的路线。
不替代：[DESIGN-FE-001]（令牌/组件真源）、[DESIGN-A11Y-001]（可访问性真源）、
[DESIGN-LAY-005]（层级真源）。本方案只声明「目标态」，落地时改的真源仍是它们。
零新增依赖：全部基于 Vue 3 + Element Plus + 既有 --khy-* 令牌。

0.1 已具备的良好基础（不要推翻）#

  1. 令牌驱动的双主题体系已就位，html.dark 单类切换可贯穿全站。
  2. 三点式页面骨架已经沉淀并被复用：.khy-page 容器（52 处）、KhyPageHeader（128 处）、

KhyEmpty（34 处）。这套「容器 → 页头 → 空态」的一致性是极好的地基。

  1. 交互细节已被打磨：字段 focus 光环、按钮 1px 抬升、卡片头部字重、

prefers-reduced-motion 已覆盖 3 处动画。

  1. 导航真源单一：src/nav/index.js 是侧栏、路由鉴权元数据、页头标题三处的共同真源，

且有 nav.wiring.test.js 守护漂移。

0.2 真正的问题（按影响排序）#

P1 — 信息架构用「清单」而非「心智模型」

src/nav/index.js 的「用户中心」组把 12 项平铺：
用户首页 / AI 对话 / 功能索引 / 提示词库 / KHY OS 内核 / 我的网关 / 工作流 /
项目工作区 / 插件市场 / 代理管理 / 账户安全 / Markdown。

问题在于混合了三种不同性质的东西：

性质项目用户的心智
日常主任务AI 对话、工作流、项目工作区「我每天来干的事」
能力与资源功能索引、提示词库、插件市场、我的网关「我需要时来查/扩的」
系统与设置代理管理、账户安全、KHY OS 内核「配置一次就忘了」
异物Markdown（标注"无需登录"）与账户体系无关的独立小工具

12 项平铺的直接代价是每次找东西都要扫 12 行，且高频项（AI 对话）与低频项
（账户安全）视觉权重完全相同。nav/index.js 的 NAV 结构已经支持任意多分组，
所以这是纯数据改动，不需要动 AppShell 渲染逻辑。

P2 — 响应式断点不足

全站仅 max-width: 900px 与 max-width: 768px 两个断点，规范 M3 要求
768 / 1024 / 480 三档。缺失 1024px 档意味着平板横屏（1024×768、iPad 横屏）
落在桌面布局里——224px 的固定侧栏在 1024px 宽上占掉 22%，内容区被挤压。
缺失 480px 档意味着小屏手机没有专门适配。

P3 — 无障碍缺口集中在表单

<label> 元素 0 个、aria-* 仅 44 处、tabindex 仅 3 处。Element Plus 的
el-form-item 会自带 label 关联，所以不是全盘失效，但自研点击区域
（.chat-conv-item 这类 div 当按钮用）如果没补 role / tabindex / aria-*，
键盘用户就完全够不到。

注意：.chat-conv-item 在模板里是 <div> 承载点击（见 AIChat.vue
['chat-conv-item', { active: c.id === activeId }]），属于 W8 不变量
「交互元素键盘可达」的待核实风险点，落地第一步应逐处核查。

1. 视觉语言升级（Design Language）#

1.1 设计理念：Calm Density（冷静的密度）#

khy-os 是一个专业工具，不是消费级应用。它要同时满足两个看似矛盾的目标：
用户要看到大量信息（模型、令牌、用量、渠道、日志），但界面不能吵。

原则是：降低装饰密度，提高信息密度。

具体三条：

  1. 颜色只用于传达状态，不用于装饰。

当前 --khy-primary: #2563eb 蓝已在 901 处 el-button 上使用。
建议保持 —— 但主按钮不应在每张卡片里都出现。一屏内主按钮（type="primary"）
建议不超过 1 个，其余降为 text / plain。这让"下一步该做什么"唯一。

  1. 用间距而非边框做分组。

当前卡片 shadow="never" 与 shadow="hover" 混用。建议统一：
常规容器用 shadow="never" + 1px hairline 边框；仅浮层（dialog/drawer/悬浮球）用阴影。
理由：--khy-shadow 是 0 10px 28px rgba(15,23,42,.08)，10 张卡片同时带阴影时
页面会"浮"，而专业工具需要"实"。

  1. 状态用「点 + 文字」而非仅颜色。

.status-dot 已有 4 色实现，但纯颜色编码对色盲用户不可用。
建议 .status-dot 后必须跟文字标签（"正常 / 降级 / 异常"），
颜色是冗余编码而非唯一编码。

1.2 令牌补强（纯增量，不改既有语义）#

以下是对 newapi-theme.css 的增量补充，不修改任何既有令牌值，
因此不会波及 718 处引用。

:root {
  /* ① 断层补偿：内容宽度阶梯（当前只有 --khy-page-max: 1320px）*/
  --khy-page-max-wide: 1680px;   /* 数据密集型页面：监控/日志/看板 */
  --khy-page-max-read: 760px;    /* 阅读型内容：Markdown / 文档 */

  /* ② 结构化断点（补齐 M3 要求的 3 档）*/
  --khy-bp-sm: 480px;
  --khy-bp-md: 768px;
  --khy-bp-lg: 1024px;
  --khy-bp-xl: 1280px;

  /* ③ 状态语义色补全（当前 success/warning/danger 有，缺「中性/进行中」）*/
  --khy-info: #2563eb;
  --khy-neutral: #667085;
  --khy-running: #6d5efc;         /* 复用 --khy-accent，语义化为"执行中" */

  /* ④ 层级化阴影（当前只有 2 档，浮层与卡片区分不足）*/
  --khy-shadow-xs: 0 1px 2px rgba(15, 23, 42, 0.04);
  --khy-shadow-flat: none;         /* 常规卡片：刻意不加阴影 */

  /* ⑤ 交互反馈时长（当前散落在各组件）*/
  --khy-dur-fast: 120ms;
  --khy-dur-base: 200ms;
  --khy-dur-slow: 320ms;
  --khy-ease: cubic-bezier(0.4, 0, 0.2, 1);
}

五个 --khy-bp-* 只是文档化，CSS 的 @media 仍需写字面量
（@media (max-width: 768px) 是 CSS 语法限制）。这是有意为之：
令牌的价值在于集中声明"我们有哪些断点"，让新增代码不会随手写第 5 个断点值。

1.3 类型与间距（维持既有，仅明确纪律）#

现有类型阶梯已良好，不改动：

令牌值用途
--khy-text-xs12px徽标、辅助注释
--khy-text-sm13px表格、正文次级
--khy-text-md15px正文默认
--khy-text-lg17px卡片标题
--khy-text-xl20px区块标题
--khy-text-2xl24px页面主标题

新增纪律：正文不得小于 13px（移动端输入框不得小于 16px，此为 M2 不变量）。
实测需核查 --khy-text-xs: 12px 的使用场景，12px 只允许用于非关键辅助信息。

间距使用既有 4px 基数阶梯（4/8/12/16/20/24/32/40/48/64）。
新增纪律：页面级垂直节奏统一走 --khy-gap-page / --khy-gap-section /
--khy-gap-card 三个语义令牌，不要在视图里写 margin-bottom: 18px 这类字面量
（KhyPageHeader.vue:37 目前是 18px，属可收敛项）。

2. 信息架构重构（Information Architecture）#

这是本次方案收益最高、成本最低的部分 —— 因为 nav/index.js 已是纯数据，
且 visibleNavGroups() 已支持按 group 渲染。

2.1 目标态：用户中心从 1 组 12 项 → 4 组 12 项#

{

    { path: '/prompts',     label: '提示词库',   icon: Collection },
    { path: '/marketplace', label: '插件市场',   icon: Shop },

  items: [
    { path: '/markdown', label: 'Markdown', icon: Document },

},

为什么这样分：分组标题本身就是一句「什么时候来这儿」的说明。
用户不再需要读 12 个标签去判断，而是先判断自己在哪一类需求里，再看组内 3–4 项。

关于 /markdown：它标注「无需登录」，与账户体系无关。
单列成组显得组数为 4 而内容为 1，略突兀。两个选项：

  • 选项 A（保守）：单列为「工具」组。零风险，语义最准。
  • 选项 B（更优）：移出侧栏，改从用户首页的快捷入口卡片进入。

侧栏只放「注册用户的核心任务」，独立工具走首页与直接 URL。
代价：需要改 nav.wiring.test.js 之外的可见性测试，且它确实还占一个路由。

→ 建议先做 A，观察 /markdown 的实际点击量后再决定是否做 B。
不因"看起来更干净"而提前做无数据支撑的架构决策。

3. 页面级布局规范（Page Layout）#

3.1 三点式骨架（固化，禁止发明第四种）#

实测已有三种骨架混用，应固化为规范：

┌─ .khy-page ─────────────────────────────────┐
│  <KhyPageHeader title subtitle>             │  ← 页头：一句话说清这页干什么
│    <template #actions> 主操作 </template>    │
│  </KhyPageHeader>                            │
│                                              │
│  <正文区>                                    │  ← 唯一的主按钮在这里
│    · 数据型 → el-card 内 el-table           │
│    · 配置型 → el-card 内 el-form            │
│    · 对话型 → 全高 flex，无卡片包裹          │
│                                              │
│  <KhyEmpty>  ← 数据为空时                    │
└──────────────────────────────────────────────┘

纪律：

  • 页面根容器必须是 .khy-page（已有 52 处使用）。
  • 页面必须有 KhyPageHeader（已有 128 处使用）。
  • 空态必须用 KhyEmpty（已有 34 处使用）。
  • 一屏内 type="primary" 按钮 ≤ 1 个。

3.2 内容宽度分档（新增）#

.khy-page            { max-width: var(--khy-page-max); }       /* 1320px，默认 */
.khy-page--wide      { max-width: var(--khy-page-max-wide); }  /* 1680px，数据密集 */
.khy-page--read      { max-width: var(--khy-page-max-read); }  /* 760px，阅读型 */

适用：/admin/monitor、/admin/usage 用 --wide（表格列多）；
/markdown、文档类用 --read（行宽超 90 字符后阅读效率下降）。

3.3 对话页（AIChat）的特殊处理#

AIChat.vue 是唯一 4,781 行的异常组件（其余页面最大 1,110 行），
且布局是「左会话列表 + 右对话流」的全高应用式布局，与其它页面的
「滚动文档式布局」本质不同。

不建议本次动它，但应记录为技术债：

问题位置建议
单文件 4,781 行AIChat.vue拆为 ChatSidebar / ChatMessageList / ChatComposer / useChatStream
26 个 ref 无 watch同上状态无响应式派生，逻辑耦合
会话项用 <div> 点击同上补 role="button" + tabindex="0" + @keydown.enter（W8）

为什么本次不做：它是全站最高频页面，重构风险与收益都最大。
在没有对应测试覆盖前动它，违反仓库「修复先复现」的纪律（RUNTIME-007）。
应先补测试，再拆。

4. 响应式策略（补齐 M3 三档）#

4.1 断点定义#

档位宽度布局行为
sm≤480px侧栏收为抽屉；卡片单列；表格转卡片列表；触控目标 ≥44px
md≤768px侧栏收为 64px 图标条；卡片单列；表格横向滚动
lg≤1024px侧栏默认折叠（当前缺失档）；卡片双列
xl>1024px完整布局

4.2 关键修复：1024px 档#

当前 AppShell.vue:3 的侧栏宽度由 collapsed 状态单一控制，
没有基于视口的初始值。在 1024px 屏幕上展开态侧栏（224px）挤压内容区。

修复（AppShell.vue 内，不新增文件）：

// 侧栏初始折叠态跟随视口：<1024px 默认折叠，避免挤压内容区。
const collapsed = ref(window.matchMedia('(max-width: 1024px)').matches);

注意用 matchMedia 而非 innerWidth 的直接读取，以便复用同一断点定义，
并避免 resize 时的判定抖动。不需要监听变化（用户手动折叠后不应被 resize 重置）。

4.3 移动端触控目标（M1 不变量）#

当前仅有 .header-console-link 在 ≤768px 时提到 min-height: 44px
（newapi-theme.css:771-775）。需系统化：所有可点击元素在 ≤768px 时应满足 44px。

建议：在 newapi-theme.css 末尾增补一段移动端收敛块，一次性覆盖
el-button / el-menu-item / .chat-conv-item / .status-dot 容器等：

@media (max-width: 768px) {
  .el-button:not(.is-text):not(.is-link),
  .el-menu-item,
  .khy-clickable {
    min-height: 44px;
  }
}

5. 可访问性补齐（对齐 W8 / W9 / W10）#

不变量要求当前动作
W8交互元素键盘可达、focus 可见tabindex 仅 3 处自研点击区补 role + tabindex + keydown
W9状态变化区 aria-live，加载区 aria-busyaria-* 44 处对话流、任务看板、进度条补 aria-live
W10尊重 prefers-reduced-motion3 处已覆盖保持，新增动画必须带此媒体查询
W11正文对比度 ≥4.5:1未实测用工具核验 --khy-text-muted: #667085 on #f4f7fc

5.1 对比度预判（需实测确认）#

--khy-text-muted: #667085 在白底 #ffffff 上：约 4.9:1 → 达标。

7. 反模式（这条路别走）#

以下是本方案明确不建议的做法，并附理由：

反模式为什么别走
引入 Tailwind / UnoCSS仓库已有 790 行令牌体系 + 718 处引用。引入第二套样式方案会让「改一处令牌全站生效」失效，直接违反 W3/W4 不变量。收益是开发便捷，代价是全站一致性——对专业工具是亏的。
整体替换 Element Plus901 处 el-button、663 处 el-form、580 处 el-table。替换成本是数月，收益是"更好看"——但视觉差异可通过令牌层达成，不需要换组件库。
为美观重写页面结构违反仓库既有纪律（与软著三条红线同源：风格归一只做风格不做语义）。重写会破坏既有测试与语义，且无法回滚。
一次性全局改 --khy-primary该色已用在 901 处按钮上。改色号是全站重绘，需全量视觉回归。除非有明确品牌需求，否则不动。
给所有卡片加阴影见 §1.1 第 2 条。10 张卡片同时带 0 10px 28px 阴影，页面会"浮"起来，与专业工具的"实"相悖。
在 nav/index.js 里加新的可见性开关该文件曾有过 daemon 命名空间开关，导致「功能看起来被删了」的严重误读，已被显式移除（见文件内注释）。不要重新引入任何"后端不可用就隐藏菜单项"的机制。
