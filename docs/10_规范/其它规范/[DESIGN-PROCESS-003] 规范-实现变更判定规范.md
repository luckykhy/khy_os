# [DESIGN-PROCESS-003] 规范-实现变更判定规范

> **一句话定位**：当「规范写的」与「实现做的」不一致时，本规范回答**该改哪一边、什么时候必须改、按什么流程改、改完怎么验收**。
>
> **它不是**「怎么修订一条规则」的规范（那是元规则 `[MGMT-STD-008]` §4.3 的职责），也**不是**「新机制什么时候敢拦人」的规范（那是 `[DESIGN-PROCESS-002]` 的职责）。它补的是这三者之间的**空白格**：不一致被观测到之后，**在动任何一行代码或任何一段规范之前，先把「改哪边」裁掉**。

---

## 0. 为什么需要本规范（现状证据）

### 0.1 空白格的精确定位

仓库里已有三套处理「变动」的机制，但没有一套处理「**不一致**」：

| 已有机制 | 它回答的问题 | 它不回答的 |
|---|---|---|
| `[MGMT-STD-008]` §4.2 新增 | 想**加**一条规则，怎么走 | 已有规则与实现不符时怎么办 |
| `[MGMT-STD-008]` §4.3 修订 | 改一条规则要 bump 什么、要不要兼容期 | **什么信号**触发修订；改规范还是改实现 |
| `[MGMT-STD-008]` §4.5 复核节奏 | 每季度 / 每个大版本跑一次健康检查 | **事件驱动**的触发（时间驱动挡不住突发不一致） |
| `[DESIGN-PROCESS-002]` 四阶段 | 新拦截机制从 S1 到 S4 的**落地节奏** | 已落地机制与规范**语义**不一致时谁让步 |
| `[DESIGN-SOURCING-001]` B-L2 | 实现**已经决定**要迁移时，三步怎么走 | **决定要不要迁移**的前置判定 |
| `[DESIGN-QUAL-001]` QUAL-2 | 基线**只降不升**，上升走台账 | 基线上升**到底算改实现还是改规范** |
| `[DESIGN-ARCH-106]` §11 | 五步流程名（提案→讨论→批准→实施→验证） | 五步的**入口触发条件**与**分支判定** |

### 0.2 仓库里已经真实发生过的不一致

本规范不是纸上推演，以下四类不一致在本仓**都有既成事实**，且当时没有统一裁决依据：

| 类别 | 既成事实 | 当时的隐性处理 |
|---|---|---|
| **真源在实现侧** | 「版本三轨道」的权威是 `check-version-sync.js` 里写死的 9 个源路径，文档表述若与守卫不同则以守卫为准（`[MGMT-STD-008]` §2.4 裁决 X-002） | 单点裁决，**未推广为通用规则** |
| **真源在规范侧** | `[DESIGN-LAY-005]` 规定 L0–L6 与依赖白名单，`check:layout` 报出的存量跨层引用属**债务**（要改实现，不改规范） | 靠 QUAL-1 基线冻结，未说明「为何改实现」 |
| **规范声明与执行器漂移** | `PROCESS-006` 原文要求「四阶段毕业判据可校验」，登记表里却是 `gate=manual` 且无 `exec.script`；而 `PROCESS-008` 用 `check-rollout-stage.js` 执行同一份真源 | **同一份真源两个规则、一个有一个没有执行器**，无裁定路径 |
| **守卫范围与 `paths` 漂移** | `RUNTIME-001` 会扫到 `.github/**`，但其 `paths` 不含 `.github/` ⇒ 范围漂移误报 | 记为**闸缺陷**而非代码缺陷，但「该改守卫还是改 paths」无判据 |

### 0.3 结论

不一致只有四种归宿，而**仓库目前没有一份文档写清这四种怎么选**：改规范、改实现、双改、显式接受偏差。本规范就是这份判据。

## 1. 核心定义（先定词，再定规则）

| 术语 | 定义 |
|---|---|
| **规范** | 具名的约束性文本，至少含 `constraint`（约束）与 `scope`（适用范围）。本仓形态为：规则卡（`RULES-REGISTRY.json` 条目）、规范文档（`docs/10_规范/**`）、工程红线（`AGENTS.md` / `CLAUDE.md`）、协议契约（schema / 常量表）。 |
| **规范实现** | 使规范**真的生效**的载体，本仓共五种：① 守卫/检查器（`scripts/ci/*.js`）；② 真源登记表（`docs/10_规范/registry/*.json`）；③ 运行时闸门（`riskGate.js` / `toolCallingPermissions.js` 等）；④ 生成器（`gen-rules-cards.js` / `build_docs_site.js` 等）；⑤ 测试断言（`scripts/tests/**`）。 |
| **不一致（Divergence）** | 规范文本所描述的「应有行为」与实现实际产生的「实有行为」之间存在可观测差异。**注意**：`docs/` 文档与 `.html` 孪生件不同步、生成物与生成器不同步，属**产物过期**，不是不一致 —— 处置是「重跑生成器」，不走本规范。 |
| **真源（Authority）** | 在一处不一致中，**哪一边被裁定为权威**。裁决后的另一边即为「须修正方」。**真源不是永久属性**，它由本规范按场景裁决，并须登记。 |
| **偏差（Accepted Deviation）** | 经裁决**明确接受**的不一致，必须带：接受人、理由、到期日、收敛条件。**什么都不写的「暂时不管」不算偏差，算漏裁**。 |

## 2. 触发场景（四类，附判定标准）

> 触发场景决定**入口**，判定标准决定**改哪边**。两件事分开看，不要混在一句话里。

### T1 — 规范先行，实现未跟上（"规范空转"）

**信号**：规范文档/规则卡已 `status: active`，但其声明的执行载体缺失或未接线。

**机械判定标准**（任一命中即触发）：

| 编号 | 判定条件 | 判读入口 |
|---|---|---|
| T1-a | 规则 `exec.script` 为空且 `gate != manual` | `RULES-REGISTRY.json` |
| T1-b | `exec.script` 指向的文件不存在 | `check:rules`（GOV-TOOL-007 `enforcement` 存在性） |
| T1-c | 执行器存在但不在任何门表面（`check:debt-ledger` 显式要求「不得有明确允许残留的债务域」） | `check:wiring` 的 `declared-uwired` |
| T1-d | 规范 `scope` 声称覆盖 X，执行器实际不覆盖 X（**名不副实**） | 人工比对 `scope` 与执行器扫描根 |
| T1-e | 规范里写了「必须/禁止」，但**全文无任何**执行器提及该约束 | 人工检索 |

**⚠ 最容易犯的错**：把 T1 一律当「要建执行器」。**先问 §3 的 Q2** —— 有些约束本就该是 `manual`（如流程纪律、评审类），此时 T1 的正确处置可能是「**在规范里显式标注人工兜底**」而非造执行器。

### T2 — 实现先行，规范未覆盖（"实现越界"）

**信号**：代码里存在一条**事实上**在被执行的约束或权利，但规范侧没有对应条款。

**机械判定标准**（任一命中即触发）：

| 编号 | 判定条件 | 判读入口 |
|---|---|---|
| T2-a | 代码中出现 `khy-allow-<ID>` 抑制语法，但 `<ID>` 未在登记表登记 | `rules:gate` 输出 + 登记表比对 |
| T2-b | 守卫报出的 `finding` 名在登记表的 `exec.findings` 里查不到 | 守卫输出 vs 登记表 |
| T2-c | `package.json` 的 `check:*` 入口指向的执行器无任何规则认领 | `check:wiring`（`unregisteredCheckers`） |
| T2-d | 代码里存在硬编码阈值/枚举，规范文本未声明该阈值 | 人工检索（对照 `RUNTIME-001` 零硬编码精神） |

**⚠ 最容易犯的错**：把 T2 一律当「补规范」而放过实现。**先跑 §3 的 Q1** —— 若该实现是**新增能力**而非**既有规范的落地**，则它应先过 `[DESIGN-SOURCING-001]` B-P2（先提案后编码），此时 T2 的正确处置是「**补提案 + 补规范**」，而不是「给既成事实补一张规则卡」。

### T3 — 两边都在，但语义漂移（"双轨分叉"）

**信号**：规范与实现都在、都 active，但**语义已经不一致**（不是缺失，是矛盾）。

**机械判定标准**（任一命中即触发）：

| 编号 | 判定条件 | 判读入口 |
|---|---|---|
| T3-a | 守卫实现里的阈值/枚举 ≠ 规范文本里的阈值/枚举 | 人工比对（**本仓最高频的一类**） |
| T3-b | 守卫扫描根 ≠ 规则 `paths` | `check:layout --list=<id>` + 规则 `paths` |
| T3-c | 同一份 `ssot` 被两条以上规则引用，且各自声明的强度/阶段不同 | 登记表按 `ssot` 分组 |
| T3-d | 执行器内部 `severity` 与登记表 `severity` 不一致（如执行器写死 `warning` 而登记表按阶段应派生） | 执行器源码常量 vs 登记表 |
| T3-e | 阶段登记（`FEATURE-OWNERSHIP.json` 的 `rollout.mechanisms[].stage`）≠ 执行器源码常量（如 `GUARD_STAGE`） | `check-rollout-stage.js` 的 `rollout-stage-authority-drift` |

**⚠ 最容易犯的错**：默认「规范是权威，改实现」。**本仓至少有两类反例**（§3 Q3）：① 版本三轨道（X-002）权威在实现；② 当规范与实现不一致**且实现已被大量消费**时，强改实现会造成大面积返工，此时应改规范并给兼容期。

### T4 — 外部信号促使重审（"外部倒逼"）

**信号**：不一致不是内部发现的，而是外部条件变化暴露的。

**机械判定标准**（任一命中即触发）：

| 编号 | 判定条件 |
|---|---|
| T4-a | 上游/官方规范发新版（如 MCP / A2A 一致性套件），本仓实现或规范与之不符（`[DESIGN-QUAL-002]` 的接入面） |
| T4-b | 依赖大版本升级导致原有实现路径失效 |
| T4-c | 生产事故根因指向「规范允许但实现做不到」或「实现做了但规范没说」 |
| T4-d | 新贡献者/AI 代理**按规范字面执行却得到错误结果**（规范的**误导性**证据，比「规范被违反」更严重） |
| T4-e | 法务/合规/软著要求变化（`PROCESS-010` 面向的域） |

**⚠ 最容易犯的错**：T4-a 直接「跟着上游改本仓规范」。**先过 §3 Q4** —— 官方一致性套件的证据强度高于自审，但**采用范围**仍须裁决（全面采用 / 部分采用 / 只记录不采用）。

## 3. 决策规则（改哪一边）

### 3.1 四个问题，按序回答，不许跳

> 顺序是强制的：**Q1 不通过，后面的答案不成立**。

#### Q1 —— 这条约束「本该存在」吗？（合法性）

| 判断 | 依据 | 若否 |
|---|---|---|
| 该约束有明确的**受益方与理由**（`benefit` 非空且可复述） | 元规则 `[MGMT-STD-008]` §0 三元性 | 走 T2 的「补提案」路径，不得直接补规则卡 |
| 该约束在**本仓适用范围**内可执行（不是「理想很丰满」） | `scope` 可枚举 | 缩 `scope` 或降 `priority`，不建执行器 |
| 该约束不与更高优先级规则冲突 | §2.4 precedence 表 | 走 §2.3 升级处理 |

**产出**：`是该存在` / `不该存在 → 处置 = 撤规范`。

#### Q2 —— 它「可机械判定」吗？（可判定性）

| 判断 | 依据 | 若否 |
|---|---|---|
| 差异能用**确定性规则**表达（输入相同 ⇒ 输出相同） | 无 AI 自称、无概率判读 | 规范里**显式标注**「人工评审兜底」+ `gate=manual` |
| 判定不需要理解语义/意图 | 纯文本/结构/数值比对 | 同上 |
| 误报率可压到 <10%（观察期有样本） | `[DESIGN-PROCESS-002]` S2 毕业条件 | 先走 S1 观察期，**不得直接进门** |

**产出**：`可判定 → 处置 = 改实现（建/修守卫）` / `不可判定 → 处置 = 改规范（标注人工兜底）`。

> ⚠ **Q2 是本规范最容易被跳过的一步**。仓库现状里 `manual` 规则与「该有执行器却没建」是两种完全不同的状态，混为一谈会导致给流程纪律类规则硬造守卫（进 S1 攒样本、永远毕不了业，白白背债）。

#### Q3 —— 两边谁是**已被消费**的真源？（消费面）

| 判断 | 依据 | 裁决 |
|---|---|---|
| 实现侧的真源（常量表/配置/守卫）已被 ≥2 处代码消费 | 检索调用点 | 裁决倾向「**规范向实现收敛**」（改规范），并给弃用/兼容期 |
| 规范侧的真源已被 ≥2 份文档/规则引用 | 反向检索引用 | 裁决倾向「**实现向规范收敛**」（改实现），走 B-L2 三步 |
| 两边都被大量消费 | 消费面相当 | **禁止单边改**，走 §3.3 「双改 + 兼容期」 |
| 实现侧真源**无文档背书**且无外部消费 | 无引用 | 可收窄/删除实现，但须过安全闸（`RUNTIME-009` 精神） |

> **先例锚点**：`[MGMT-STD-008]` §2.4「版本轨道真源 = 代码 > 任何文档表述」正是「实现已被消费 ⇒ 规范向实现收敛」的一个具体实例（裁决 X-002）。本规范把该单点先例**推广为 Q3 的通用判据**。

#### Q4 —— 差异的**强度**是多少？（严重度）

| 强度 | 定义 | 处置倾向 | 时限 |
|---|---|---|---|
| **S-高** | 会**误伤**用户数据/安全，或让贡献者按规范执行**必然出错** | 必改，不得接受为偏差 | 立即（红线级） |
| **S-中** | 会导致守卫误报/漏报，但不直接造成损失 | 必改或显式偏差（带到期日） | 一个迭代内 |
| **S-低** | 措辞、命名、注释层面的不一致 | 可排期或合并到常规维护 | 无强制时限 |

### 3.2 决策矩阵（Q2 × Q3 二维）

> Q1 = 是（约束该存在）的前提下，看 Q2 与 Q3。

| | **实现已被消费** | **规范已被消费** | **两边都轻/无消费** |
|---|---|---|---|
| **可机械判定** | **改规范**（收敛到实现）+ 给弃用期 | **改实现**（收敛到规范），走 B-L2 三步 | **改实现**（规范先行是新规则默认姿态） |
| **不可机械判定** | **改规范**：删掉机械口径，改写为「人工评审」+ 明确判据 | **改规范**：标注人工兜底（除非可实现化） | **改规范**：标注 `gate=manual` + 人工评审清单 |

**矩阵的两个角必须记牢**：

- **左下角**（不可判定 + 实现已被消费）是**最反直觉**的格：此时实现事实上就是权威（因为它已在跑），规范应改写为**描述性 + 人工兜底**，而不是硬造一个不可能机械判定的守卫。仓库里 `PROCESS-006`（四阶段毕业判据，整体靠人工评审，而 `PROCESS-008` 只机械覆盖「阶段登记」这一子集）就是这一格的实例。
- **右上角**（不可判定 + 规范已被消费）是**最容易做成「假守卫」**的格：为了「让规范有执行器」而写一个模糊检查器，会在 S1 阶段长期攒不够有效样本，最终变成永久债务。**此格应优先考虑把约束改写成可判定的形式**（缩窄到可机械化的子集），而不是伪造守卫。

### 3.3 四种归宿与必须留下的痕迹

| 归宿 | 何时选 | 必须留下 |
|---|---|---|
| **改实现** | 矩阵中「改实现」格 | B-L2 三步（标记 → 迁调用方 → 删旧），每步独立可回滚；`rollback` 字段；守卫新旧两侧各跑一次 |
| **改规范** | 矩阵中「改规范」格 | 元规则 §4.3 全套（版本 bump + 版本记录 + 破坏性修订含兼容期 + 权力缩减须说明替代路径）；**并登记「为何改规范而非改实现」**（引用 Q3 的消费面证据） |
| **双改** | 两边消费面相当，或语义需重新切分 | 同上两者之并；**必须先定目标态再动任何一边**，禁止「改一半看效果」 |
| **接受偏差** | Q4 = S-中/S-低，且改造成本 > 收益 | `deviation` 条目：接受人 / 理由 / 到期日 / 收敛条件 / 复查责任人。**到期未收敛 ⇒ 自动升级为 Q4=S-高** |

**⚠ 处置禁忌（每条都是本仓实际踩过的坑）**：

1. **禁止「改实现就顺手改规范措辞」**——两件事必须可分步、可回滚。`[DESIGN-SOURCING-001]` B-L3「决策只追加不改写」的精神适用于此。
2. **禁止把偏差写成「暂无计划」**——无到期日的偏差等同漏裁，必须在 §5 的检查清单里被拦下。
3. **禁止用「改文档表述使其与实现一致」掩盖实现缺陷**——Q3 判「实现已被消费」是**前提条件**，不是免责理由。若实现本身有 bug，属 T3 但走 **改实现 + 修 bug**，不是改规范。

## 4. 处理流程

### 4.1 主流程（七步，每步有退出条件）

| 步骤 | 动作 | 退出条件（不满足则回上一步） |
|---|---|---|
| **P1 记录** | 把不一致写成**可复现**的最小证据：`<文件:行>\` + 期望 vs 实际 + 复现命令 | 证据可被第三人复现 |
| **P2 归类** | 判 T1/T2/T3/T4（§2） | 类别唯一；跨类时按「最严重」归一类 |
| **P3 定级** | 判 Q1 → Q2 → Q3 → Q4（§3.1，顺序不可跳） | 四问都有明确答案 |
| **P4 定归宿** | 查 §3.2 矩阵，得四归宿之一 | 归宿唯一 |
| **P5 定证据** | 实现侧改动先写**失败用例/探针**（RED），规范侧改动先写**版本记录草稿** | RED 可复现 |
| **P6 实施** | 走 §4.2 的**分支流程**（改实现 / 改规范 / 双改 / 偏差各有流程） | 分支流程全部退出条件满足 |
| **P7 验收** | 跑 §5 验收清单 + 反例矩阵 | 全部通过；有豁免必须写理由 |

> **P3 强调顺序**：Q1 不通过（约束不该存在）却继续问 Q2/Q3 是无效劳动；Q2 不通过（不可判定）却继续问 Q3 会导致「给流程纪律硬造守卫」这一类错误。

### 4.2 四条分支流程

#### 分支 A — 改实现（最常见）

1. **锁定期望**：把规范条文转成**一条或多条**可测断言（放 `scripts/tests/**`）。
2. **取证 RED**：先让断言失败，存证到 `.khyos/diag/<case>.txt`（`RUNTIME-007` 修复先复现）。
3. **迁移实施**：按 `[DESIGN-SOURCING-001]` B-L2 三步：① 标记旧实现（`@deprecated` + 指向新位置）→ ② 迁调用方 → ③ 删旧实现。**每步单独可回滚**。
4. **双向验证**：守卫在「改动前快照」与「改动后」各跑一次，确认**只有目标 finding 变化**。
5. **接 CP-3 四件事**（若同时动了规范文本）：命名 / 回写索引 / 生成孪生件 / 重生成规则卡。

#### 分支 B — 改规范

1. **定目标态**：写清「规范改成什么」——不是删掉约束，而是**换成准确的约束**（含新的 `scope`）。
2. **走元规则 §4.3 全套**：版本号 bump（§4.4 语义）+ 追加版本记录（**追加，不覆盖**）+ 破坏性修订须含兼容期 + **权力缩减必须说明替代路径**。
3. **登记裁决理由**：在规范正文写明「**为何改规范而非改实现**」，引用 Q3 的消费面证据（哪些代码在消费实现侧真源）。**这一条是本规范的强制项**，否则将来无法复核。
4. **同步实现侧的「让路」动作**：若规范收紧/放宽导致守卫 `paths`/阈值须跟随，一并改，并跑 `check:rules` 双向可达。
5. **重生成规则卡**：`npm run docs:rules-cards`（**卡禁止手改**）。

#### 分支 C — 双改

1. **先冻结目标态**：写出「目标规范条文 + 目标实现行为」两句话，**两者都不许在实施中漂移**。
2. **定顺序**：默认 **规范先（带兼容期）→ 实现跟上 → 兼容期结束删旧**。若实现侧是真源（Q3），则顺序反转。
3. **兼容期必须有到期条件**（不是到期日）：写成「当 X 指标归零时删除旧路径」，避免「到期了但没人检查」。
4. **验收 = 两边同时绿**：规范侧 `check:rules` 绿 + 实现侧目标测试绿 + 无新增 finding。

#### 分支 D — 接受偏差

1. **写 `deviation` 条目**（五字段：接受人 / 理由 / 到期日 / 收敛条件 / 复查责任人）。落点：就近 `registry/*.json` 的对应段，或 `[DESIGN-GOV-001]` §11 未决冲突表风格的表。
2. **必须写明「为何不改」的成本证据**（改动量估算/影响面），禁令式措辞（「暂不处理」）不接受。
3. **到期自动升级**：到期未收敛 ⇒ 按 Q4 升一级；连续两次未收敛 ⇒ 升级为 S-高，不得再展期。
4. **偏差总数须可见**：每季度健康检查（`[MGMT-STD-008]` §4.5）必须报出**未收敛偏差数**，与 `rules:coverage` 同屏看。

### 4.3 与既有流程的接线点

| 触点 | 已有机制 | 本规范如何接 |
|---|---|---|
| 规则**修订**的具体做法 | `[MGMT-STD-008]` §4.3 | 本规范只给**触发与裁决**；落地动作一律引用元规则，不另立一套 |
| 实现**迁移**的步骤 | `[DESIGN-SOURCING-001]` B-L2 | 分支 A 步骤 3 直接调用，不重写 |
| 机制的**落地节奏** | `[DESIGN-PROCESS-002]` 四阶段 | T1 若要新建执行器，**必须先过四阶段**（禁止直进 S3）；本规范不豁免 |
| **基线**上升 | `[DESIGN-QUAL-001]` QUAL-2 | 「改实现」使基线下降属正常；若判定必须让基线上**升**，须同时在本规范登记偏差 |
| **官方一致性**证据 | `[DESIGN-QUAL-002]` | T4-a 的场景流程 = 本规范 §4.2 分支 C（双改） |

## 5. 适用范围

### 5.1 适用（落入本规范）

| 维度 | 范围 |
|---|---|
| **对象** | 一切「声明了约束」的文本 × 一切「使约束生效」的实现，**包括但不限于**：规则卡 / 规范文档 / 工程红线 / 协议契约 / 常量表 |
| **实现载体** | 守卫/检查器、真源登记表、运行时闸门、生成器、测试断言（五种，见 §1） |
| **触发时机** | 日常开发发现、守卫输出、季度健康检查、上游变更、生产事故复盘中任一 |
| **主体** | 人类维护者与 AI 代理（**AI 代理不得自行裁决归宿**，见 §6 约束 5） |

### 5.2 不适用（明确划出）

| 不适用项 | 归谁 | 为什么不是本规范 |
|---|---|---|
| 规范**新增**（无既有条款） | `[MGMT-STD-008]` §4.2 | 没有「不一致」可言 |
| 规范**废弃**（整条作废） | `[MGMT-STD-008]` §4.4 | 是生命周期动作，非裁决动作 |
| 新**机制**从写出到敢拦人 | `[DESIGN-PROCESS-002]` | 是**节奏**问题，不是**方向**问题 |
| 新**能力**从提案到实现 | `[DESIGN-SOURCING-001]` | 是**准入**问题 |
| 文档与 `.html` 孪生件不同步 | `build_docs_site.js` / `docs:verify` | 产物过期 ≠ 语义不一致 |
| 生成物与生成器不一致 | 重跑生成器 | 同上 |
| 存量**债务**的清零排期 | `[DESIGN-QUAL-001]` 债务台账 | 债务是「已知且已接受」的偏差的**载体**，本规范只负责**裁定它算不算可接受偏差** |
| 代码风格/格式类差异 | 对应 DESIGN-* 规范 | 不具备「规范 vs 实现」二元结构 |

### 5.3 边界示意图（文字版）

```
   发现问题
      │
      ├─ 是「该不该存在」的问题？ ────→ [MGMT-STD-008] §4.2 新增 / §4.4 废弃
      │
      ├─ 是「什么时候敢拦人」的问题？ ─→ [DESIGN-PROCESS-002] 四阶段
      │
      ├─ 是「该不该进这个仓/谁实现」？ ─→ [DESIGN-SOURCING-001]
      │
      ├─ 是「产物过期」？ ─────────────→ 重跑生成器
      │
      └─ 是「规范说 X、实现做 Y」？ ───→ ★ 本规范 ★
                                          ├ Q1 该存在吗
                                          ├ Q2 可判定吗
                                          ├ Q3 谁被消费
                                          ├ Q4 多严重
                                          └ → 四归宿：改规范/改实现/双改/接受偏差
```

## 6. 关键约束（防呆铁律）

> 每条都设计为**可自动或可人工快速判定**。违反即视为本次变更未完成。

| 编号 | 铁律 | 判定方式 |
|---|---|---|
| **C-1** | **禁止在未跑 P3 四问之前改动任何一边** | 变更说明里必须出现 Q1–Q4 的答案；缺失即驳回 |
| **C-2** | **裁决归宿必须留下可复核依据** | 「改规范」必须有 Q3 消费面证据；「接受偏差」必须有五字段；「改实现」必须有 RED 证据 |
| **C-3** | **偏差必须有到期日，且到期自动升级** | `deviation` 条目缺任一字段 ⇒ 视为漏裁；到期未收敛 ⇒ 升一级 |
| **C-4** | **禁止用改文档掩盖实现缺陷** | 若差异根因是实现 bug，归宿只能是「改实现」，不得选「改规范」 |
| **C-5** | **AI 代理不得自行裁决归宿，也不得自行选择「接受偏差」** | 交互类判据：默认只做 P1–P4 的**取证与建议**，裁决权交人类（`SECURITY-001`/`PROCESS-009` 一脉的「不接受 AI 自称」原则） |
| **C-6** | **禁止以「规范未写明」为由放过已在运行的约束**（T2 反向） | 出现 T2-a/T2-b/T2-c 信号时，必须走 P3，不得直接声称「规范没规定」 |
| **C-7** | **同一份 `ssot` 上的不一致必须一次裁完** | 按 `ssot` 分组，同一 `ssot` 下的所有不一致在同一个裁决里处理，避免「改一半」 |
| **C-8** | **T3-e 类（阶段/常量漂移）优先级最高** | 阶段登记与执行器常量不一致会导致「守卫静默失效」，属 S-高，立即处置 |

## 7. 可落地的执行步骤

### 7.1 一次性落地（把本规范接进仓库）

> 按顺序执行；每步有验收命令。

| 步骤 | 动作 | 验收 |
|---|---|---|
| 1 | 落盘本规范文档 + `.html` 孪生件 | `docs:verify` 不报本文件 |
| 2 | 登记规则 `PROCESS-011` 进 `RULES-REGISTRY.json`（含三元字段、`gate=manual`、同步 `meta.ruleCount`） | `npm run check:rules` 绿 |
| 3 | 本文件第 3 行附近的 `<!-- RULES-REGISTRY: PROCESS-011 -->` 标记行与登记表 `ssot` **双向可达** | `npm run check:rules` 绿 |
| 4 | 治理总纲 `[DESIGN-GOV-001]` §8 GOV-PROCESS 板块补一行（指路，不复制正文） | `node scripts/ci/check-gov-rules.js` 绿 |
| 5 | 回写 `docs/10_规范/其它规范/00_INDEX_其它规范-总目录.md` | `check:layout` 的 `docs-index-complete` 绿 |
| 6 | 重生成规则卡 `npm run docs:rules-cards` | `npm run check:rules` 绿（卡与登记表逐字节一致） |

### 7.2 日常使用（发现不一致时）

**最小操作序列**（人类维护者）：

```powershell
# P1 取证：把不一致写成可复现的一行
npm run rules:apply -- <你怀疑的规范/实现文件>   # 查「改这个文件适用哪些规则」
npm run rules:coverage                            # 看 P0 覆盖率与死指针
npm run rules:manifest                            # 看每条规则的执行器与接线状态
```

**AI 代理被要求处理不一致时**：

1. 只做 **P1 记录 + P2 归类 + P3 四问取证 + P4 建议**；
2. 输出**结构化裁决建议**（类别 / Q1–Q4 答案 / 建议归宿 / 依据），**明确标注「待人类裁决」**；
3. **不动任何代码或规范**，除非人类明确指令选定了归宿；
4. 若人类选定「改实现」，再按 §4.2 分支 A 执行；
5. 若人类选定「改规范」，按 §4.2 分支 B 执行（注意元规则 §4.3 的版本记录必须**追加**）。

### 7.3 定期体检（接入既有节奏）

并入 `[MGMT-STD-008]` §4.5 的季度健康检查，**新增三项必报数字**：

| 指标 | 采集方式 | 健康线 |
|---|---|---|
| **未收敛偏差数** | 扫 §4.2 分支 D 的 `deviation` 条目 | 0 视为健康；>0 须有到期日 |
| **T1 类残留**（规范 active 但无执行器且非 manual） | `rules:manifest` 里 `gate != manual` 且无 `exec.script` | 0 |
| **T3-e 类漂移**（阶段登记 vs 执行器常量） | `check-rollout-stage.js` 的 `rollout-stage-authority-drift` | 0 |

> ⚠ 采集这三项时**必须同时看** `rules:coverage` 的 `unenforced` / `orphans` / `unregisteredCheckers` / `externalRules` 四组数字 —— 覆盖率全绿 ≠ 覆盖率健康（覆盖率的 `coverageCode()` 只认 `redLines` + `registry.errors`）。

## 8. 验证与反例清单

### 8.1 应拦截（正例）

| 场景 | 期望 |
|---|---|
| 有人提议「规范与实现不一致，直接改实现」但答不出 Q3 消费面 | 被 C-2 拦下，要求补证据 |
| 有人提交 `deviation` 条目但无到期日 | 被 C-3 拦下 |
| AI 代理自行决定「这条规范先接受偏差」 | 被 C-5 拦下 |
| 差异根因是守卫误报（实现 bug），却选了「改规范让表述迁就」 | 被 C-4 拦下 |
| 发现 `khy-allow-XXX` 里的 XXX 未登记 | 命中 T2-a，必须走 P3 |

### 8.2 应放行（反例，防空转断言）

| 场景 | 期望 |
|---|---|
| 规范新增一条全新约束，实现尚未跟上 | **不是**不一致，走 `[MGMT-STD-008]` §4.2，**不触发**本规范 |
| 规范废弃整条 | 走 §4.4，**不触发** |
| 规范文本与 `.html` 孪生件不同步 | 属产物过期，**不触发** |
| 新机制已有执行器但停在 S1 观察期 | 走 `[DESIGN-PROCESS-002]`，**不触发**（S1 本来就是「记录不拦截」） |
| 债务台账里 `status=open` 的存量债务 | 走 `[DESIGN-QUAL-001]`，**不触发**（除非要把它从 `open` 改成 `closed`） |

> **⚠ 反例清单的存在意义**：`check:layout` 的 `cross-layer-require` 类陷阱说明，任何判据都必须自证「**该红时真红、该绿时真绿**」。若本规范将来实现为守卫，必须用上表双向各跑一次（防「空转断言」——永远绿的断言比没有断言更危险）。
