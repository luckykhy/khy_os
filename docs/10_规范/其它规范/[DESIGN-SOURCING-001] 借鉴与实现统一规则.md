# [DESIGN-SOURCING-001] 借鉴与实现统一规则

<!-- RULES-REGISTRY: SOURCING-001, SOURCING-002, SOURCING-003, SOURCING-004, SOURCING-005, SOURCING-006 -->


> **本文件是「借鉴什么 / 怎么借鉴 / 同一功能由谁实现」的单一真源。**
> 违反即视为 PR 返工，理由与 [DESIGN-GOV-001] 治理总纲同级。
>
> **一句话原则**：**借鉴结论可移植，借鉴过程不可移植，借鉴位置必须唯一。**
>
> 本规则回应两个已发生的问题：
> 1. **盲目借鉴**——参考了 A 的交互、B 的数据结构、C 的目录布局，拼出功能不协调的「四不像」；
> 2. **重复实现**——同一能力出现多种写法，各执己见，反复修改同一处代码。
>
> 本文件是 [DESIGN-ARCH-061]（更新包学习：绝不自动整包合并）的**流程上位规则**：
> 061 规定「拿到上游压缩包时该读什么、绝不自动合并」，本文件规定「读完之后，
> 允许以哪种方式落地、落在哪、由谁裁决」。二者不重叠，061 仍是拷贝红线的原始出处。

## 0. 规则索引与执行方式

规则编号 `B-<组>-<序号>`。**组语义**：

| 组 | 范围 | 强制级别 |
|----|------|---------|
| `B-S` | Scope：可借鉴范围与禁止项 | 红线，无条件 |
| `B-M` | Method：借鉴方式判定 | 红线，无条件 |
| `B-P` | Process：借鉴流程 | 红线，无提案不落地 |
| `B-U` | Uniqueness：实现唯一性与裁决 | 红线，无登记不新增 |
| `B-L` | Lifecycle：存量治理与防回退 | 强制 |
| `B-G` | Guard：自动化门 | 建设项（分阶段） |

**执行方式分三级**（与 `check-agent-rules.js` 的判定惯例一致）：
- `ERROR` —— 挡回 CI / 挡回 PR；
- `WARN` —— 记录并提示，`--strict-warnings` 时挡回；
- `人工` —— 无机器信号可判，由评审按判断标准兜底（必须在看板/PR 里留下判断依据）。

## 一、B-S：可借鉴范围与判定标准

### B-S1 可借鉴的四类内容（白名单）

只有这四类允许进入 khyos 代码库：

| # | 类别 | 例子 | 落库形式 |
|---|------|------|---------|
| 1 | **算法与协议形态** | 退避策略、租约过期判定、消息信封字段、握手次序 | 重新实现，逐字改写 |
| 2 | **接口/数据形状** | 适配器 `generate()` 签名、工具 `input` schema、错误信封结构 | 保留字段语义，命名对齐本仓约定 |
| 3 | **交互与体验流程** | 步骤编号、审批闸门、状态文本「动作+目标+进度」 | 只移植行为，不搬运文案与 UI 结构 |
| 4 | **测试与验证策略** | 黄金样例、属性断言、契约测试写法 | 按本仓测试栈改写 |

**判定口诀**：能被一句话抽象成「它解决了什么问题」的东西，才能借；
只能靠「它恰好是这样写的」才能理解的代码，不能借（那是照抄，见 B-S3）。

### B-S2 不可借鉴的五类内容（黑名单）

以下五类**永远不进入 khyos 代码库**，即使上游写得更好：

| # | 禁止项 | 理由 | 若确实需要 |
|---|--------|------|-----------|
| 1 | 上游的**内部约定**（目录布局、模块分层、命名风格、错误码空间） | khyos 的分层真源是 [DESIGN-LAY-005]，上游分层照搬即制造双标准 | 提出层级规范变更，走 B-P2 提案 |
| 2 | 上游的**构建/发布/CI 系统** | khyos 有独立的 pip+npm 双轨版本同步（6 真源） | 仅借鉴思路，写入本仓自己的脚本 |
| 3 | 上游的**运行时数据目录与状态文件格式**（`.xxx/` 布局、db schema、env 键名） | 破坏 `~/.khyquant/` 与 `.khy/` 既有消费者 | 只借信息模型，落本仓自己的路径 |
| 4 | 上游的**治理/决策文档**（CONTRIBUTING、AGENTS、设计规则） | 治理必须内源，见 B-S5 | 提炼原则，重写成本仓条款 |
| 5 | 上游的**许可证文件、NOTICE、CHANGELOG、README、品牌素材**（logo/图标/名称） | 法律与品牌资产，搬运即侵权 | 见 B-M2 归因规范 |

### B-S3 拷贝代码的绝对红线

**不得将上游源码文件复制进 khyos 源码目录**（`services/`、`apps/`、`platform/`、
`software/`、`kernel/`、`tools/`、`scripts/`），无论上游许可证是什么。

唯一例外见 B-M1 的 `vendored` 档，且**必须同时满足** B-M1 的全部条件。
该红线与 [DESIGN-ARCH-061]「绝不自动整包合并」同向，本条把它扩展到手工操作。

### B-S4 许可证分级（决定借鉴方式的硬门槛）

khyos 以 `LicenseRef-Source-Available` 分发，且**同时经 PyPI 与 npm 分发**——
这意味着许可证条款对 khyos 的约束比「仅自用」严格。分级如下：

| 上游许可证 | 可借鉴级别 | 允许的操作 |
|-----------|-----------|-----------|
| MIT / BSD-2 / BSD-3 | `verbatim`（见 B-M1） | 可逐字拷贝，必须保留版权头与 LICENSE |
| Apache-2.0 | `verbatim` | 可逐字拷贝，必须保留版权头与 LICENSE，并**声明第三方依赖** |
| ISC | `verbatim` | 同 MIT |
| MPL-2.0 | `reference` | 仅逐字改写，不保留原文件（MPL 的文件级 copyleft 会使整文件受约束） |
| LGPL / GPL-2/3 / AGPL | `idea` 或 `adapter` | 禁止进入源码目录；只能通过外部进程调用其**官方分发版本** |

**红线 B-S4.1**：任何许可证无法在仓库内确认的文件，按**最严格档（`idea`）**处理，
不因为「大概是 MIT」放行。许可证缺失 ≠ 许可证宽松。

**已知缺口（本文件登记）**：仓库根目录当前**没有 LICENSE 文件**，
`services/backend/package.json` 与 `packaging/npm/package.json` 声明
`LicenseRef-Source-Available` 但无对应的许可文本载体。
在补齐之前，`verbatim` 档的判定**必须同时附上 khyos 自身许可的书面确认**
（谁确认、何时确认，写入 B-P2 提案），否则一律降级为 `reference`。

### B-S5 治理与规则的「借鉴≠搬运」条款

治理类内容（目录规范、检查脚本、贡献流程、工程红线）允许**借鉴思路、禁止搬运文本**：
引用其决策，不复用其条款。评审识别方式：khyos 的治理文档中若出现与上游文档
**连续 12 个中文字以上完全相同**的段落，视为搬运，判 ERROR。

## 二、B-M：借鉴方式判定

### B-M0 五种借鉴方式

| 代号 | 名称 | 定义 | 代码去向 |
|------|------|------|---------|
| `idea` | 只取结论 | 记录上游结论与本仓理据，本仓从零实现 | 本仓自写，不留上游痕迹 |
| `reference` | 参考实现 | 保留结构语义，逐字改写命名/接口/错误处理 | 本仓自写，登记 `source` 出处 |
| `adapter` | 适配器桥接 | 不搬代码，只调上游的官方分发版本或外部进程 | 只有薄壳，无上游逻辑 |
| `vendored` | 整包保留 | 上游文件原样入库，只读不改 | 独立目录 + 上游 LICENSE |
| `fork` | 分叉维护 | 本仓长期维护一份上游副本 | **默认禁止**，见 B-M3 |

### B-M1 `vendored` 的全部前置条件（缺一即降为 `reference`）

1. 上游许可证为 MIT / BSD / Apache-2.0 / ISC 之一，且许可证文本可核实；
2. 该依赖**无官方 npm/pip 包可用**（若有官方包，必须走 `adapter` 或正常依赖安装，
   不得为「省事」而 vendored）；
3. 落地目录为**独立、可整删**的目录，且该目录列入 `B-U4` 的 `ownedLayers` 之外；
4. 目录内**同路径保留上游 LICENSE**（仓库内已有先例：`tools/deepseek-eyes/LICENSE`）；
5. 保留上游的**原始文件头与版权声明**，不重写、不合并注释；
6. 在 `FEATURE-OWNERSHIP.json` 登记，`method` 为 `vendored`，并写明依赖版本与上游 commit。

**vendored 目录内的修改禁令**：任何对 vendored 文件的改动，PR 必须在描述中
写明「为什么必须改」与「下一次上游同步时的冲突面」；无法说明即拆出为本仓自己的文件
（改为 `reference`）。

### B-M2 归因规范（所有档适用）

- 借鉴**必须可追溯**：`FEATURE-OWNERSHIP.json` 的 `source` 字段记录
  `项目名 + 版本/commit + 借鉴内容一句话`，无 `source` 的借鉴视为未登记（B-U1）；
- 逐字拷贝的文件**保留原作者版权头**；本仓 AI 协作者尾注
  （`gitCoAuthorTrailer.js` 的 `Co-Authored-By`）不得覆盖上游版权头；
- 借鉴记录**不得被后续重构删除**——它是法律与决策的溯源链（B-L3）。

### B-M3 `fork` 的准入条件（默认禁止）

`fork` 会制造「上游更新了怎么办」的永久义务，是本仓历史重复劳动的主要来源之一。
仅在**同时**满足以下三点时才允许：

1. 上游已停止维护，或维护方向与本仓需求明确冲突（书面记录）；
2. 没有可行的 `adapter` 替代路径（已评估并记录，见 B-P2 提案第 6 字段）；
3. 明确写出**同步策略**：多久同步一次、由谁同步、冲突时以谁为准。

未满足以上任一条而实施的 `fork`，判 ERROR 并要求改回 `adapter`。

## 三、B-P：借鉴流程规范

### B-P1 流程入口（什么时候必须走提案）

**只要改动引入了「本仓此前不存在的能力域」**，就必须走 B-P2 提案。
判定标准（任一命中即算新能力域）：

- 新增了一个此前没有的顶层概念（新的工具、新的服务、新的命令、新的 UI 视图族）；
- 新增了一个此前不存在的对外契约（新 API 端点、新协议消息、新配置键、新 env 变量）；
- 首次引入某个上游项目的实现方式（`FEATURE-OWNERSHIP.json` 中 `source` 为新值）。

**豁免**：对已登记能力域的**行为修正**（bugfix、补字段、文案调整）不需要提案。
豁免的判定依据是该能力域已在注册表中存在且有 `canonical` 路径。

### B-P2 借鉴提案（六字段模板，缺一不落地）

提案可以是一段 PR 描述、一条看板卡片，或一段提交信息正文；**不必单独开文件**，
但六个字段必须齐全且可检索。

```
【借鉴提案】
1. 借鉴对象：项目名 + 版本/commit
2. 借鉴内容：一句话，说清借的是结论、结构、行为还是测试
3. 解决的问题：khyos 当前的具体缺口（指向现有文件/命令/现象），不是「上游有这个」
4. 许可证与代码性质：上游许可证名 + 核实位置（文件路径/链接）；无法核实即按 B-S4.1 从严
5. 借鉴方式：idea | reference | adapter | vendored | fork（按 B-M 判定，写明判定依据）
6. 落点与现有实现对比：
   a. 落点：目标文件路径（必须已存在于注册表，或本提案新增）
   b. 现有同类实现：搜索结论（搜索过哪些词、在哪些目录），若已有实现则说明本提案是
      「扩展既有 canonical」而非新增并行实现；若无既有实现则说明为何不复用任何现有件
7. 验收方式：可复现的一条命令或一次操作，说明「怎么算做成了」
```

**B-P2.1 强制顺序**：**先提案、后编码**。以「先写出来再补提案」的方式提交，
即使实现已完成，也必须被标记为违规并要求补充六字段，评审不得以「反正都写好了」放行。
理由：提案的价值在于**决策发生在写代码之前**，事后补写无法阻止盲目借鉴。

### B-P3 决策权限与裁决人

| 借鉴方式 | 决策人 | 备注 |
|---------|--------|------|
| `idea` / `reference` | 作者自评 + 任一评审 | 六字段齐全即可 |
| `adapter` | 作者自评 + 任一评审 | 需说明调用边界与降级路径 |
| `vendored` | 维护者（仓库 owner）显式批准 | 许可证 + 无官方包 + 可整删，三点必须复核 |
| `fork` | 维护者显式批准 + 写入同步策略 | 见 B-M3 |
| 触及 B-S2 黑名单或 B-S3 红线 | 无决策权，直接拒绝 | 不接受「特批」 |

**裁决人不得同时是唯一实现者**：`vendored` / `fork` 档的批准人必须是除作者之外的角色。

### B-P4 借鉴证据的保留与存放

- **不保存上游源码**：提案只记录结论与理据，不把上游代码片段贴进文档（避免把
  B-S3 红线搬进文档层）。确需引用时，最多引用**签名/字段名**级别的结构描述；
- **上游压缩包的学习结果**：走 [DESIGN-ARCH-061] 的 `upstreamStudy` 工具产出策展清单，
  清单属临时产物，不得直接进 `docs/` 作为依据存档；
- **理据文档**：若某次借鉴改变了架构，须在提案之外补一篇设计文档，按 [DESIGN-LAY-005]
  归入 `docs/03_DESIGN_设计/`，编号递增。

## 四、B-U：同一功能的实现统一与决策机制

### B-U1 归属登记表（单一真源）

**`docs/10_规范/registry/FEATURE-OWNERSHIP.json`** 是「能力域 → 唯一实现位置」的唯一真源。
schema（字段全量）：

```jsonc
{
  "version": 1,
  "updated": "2026-09-15",
  "status": "seeded",                         // seeded | baseline | gate（对应 B-G1 阶段）
  "capabilities": [
    {
      "domain": "ai-gateway",                 // 能力域名：kebab-case，稳定不变，禁止复用旧名
      "summary": "多供应商 AI 调用的统一入口",  // 一句话职责
      "canonical": "services/backend/src/services/gateway/aiGateway.js",
      "ownedLayers": ["L2"],                  // 只允许这些层实现，见 [DESIGN-LAY-005]
      "pattern": "Adapter",                   // 取值必须来自 docs/16_设计模式/registry/模式注册表.json 的既有值
      "method": "self-developed",             // self-developed | idea | reference | adapter | vendored | fork
      "source": null,                         // method 非 self-developed 时必填："项目名@版本 — 借鉴了什么"
      "aliases": ["aiGateway", "AI 网关", "多供应商 AI 调用"],  // 检索别名（中文必须收录）
      "forbidden": ["services/ai-backend/src/services/gateway/aiGateway.js"],  // 已知重复实现，命中即 ERROR
      "status": "active",                     // active | deprecated
      "notes": "新增供应商必须走适配器模式，不得新增并行调用入口"
    }
  ]
}
```

**当前状态**：文件已建，`status` 为 `seeded`，含 3 个已核实的种子能力域
（`ai-gateway`、`token-usage`、`cli-router`）。其中 `ai-gateway` 与 `token-usage`
各自已核实存在**两份同名服务**（`services/backend/` 与 `services/ai-backend/` 各一份），
并已写入 `forbidden` —— 这是本文件规则要解决的重复实现的**第一批实证样本**。
两份实现同处 L2 层，`check:layout` 无法捕获，只能靠本登记表 + `check:duplication` 兜底，
这也是 B-G1 新守卫的首要动因。

**字段语义**：
- `canonical` —— 该能力域的**唯一实现入口**。新代码必须从这里扩展，不得新开入口；
- `forbidden` —— 已知存在的**重复/并行实现**（历史遗留）。命中即判 ERROR；
- `aliases` —— 让人和 AI 都能搜到该能力域，是防「换名字造轮子」的关键字段。

### B-U2 四步检索规约（写新代码前必做）

写任何「本仓第一次出现的能力」之前，必须完成并留下这四步的检索结论：

1. **检索别名**：在 `FEATURE-OWNERSHIP.json` 中搜 `aliases` / `summary` / `domain`
   （中文词也要搜——AI 常用中文描述能力）；
2. **检索符号**：`grep` 候选符号名与相近命名（如想写 `RetryHelper`，先搜 `retry`）；
3. **检索模式**：在 `docs/16_设计模式/registry/模式注册表.json` 中确认该能力的实现模式是否已有登记；
4. **检索层**：按 [DESIGN-LAY-005] 判断该能力该落在哪一层，
   若目标层已有同类实现则一律扩展它。

**B-U2.1 结论留痕**：检索结论必须写进 PR 描述或提交信息（B-P2 第 6b 字段）。
无法证明做过检索的「新实现」，评审直接要求补检索或改为扩展既有实现。

### B-U3 「同一功能」的判定标准（人工兜底）

机器无法判定「这两个东西算不算同一功能」，因此给出可操作的判定标准。
满足以下**任意一条**，即视为同一功能，必须共用 `canonical`：

1. **输入输出同型**：接收同类输入、产出同类输出（例：两个都「把用户输入变成给模型的提示词」）；
2. **职责动词相同**：抽象后是同一个动词 + 同一类对象（例：「重试网络请求」出现两次）；
3. **可互相替换**：任一调用方可以在不改变自身行为的前提下改用另一个；
4. **上游同源**：都源自同一个上游项目的同一处实现（哪怕写法不同）；
5. **重复度信号**：`check-duplication` 报出 ≥3 行相同的克隆类（见 B-G1）。

**B-U3.1 分歧处置**：两位作者对「是否同一功能」有分歧时，**不投票、不各写一份**——
提交到维护者裁决一次，裁决结论写入注册表的 `notes` 字段，此后不再重开讨论。
同一分歧第二次出现即视为流程失败，需补检索规约而不是补代码。

### B-U4 层级与命名统一（避免「四不像」的落地约束）

拼凑出不协调的实现，根源是各层各写一套。三条硬约束：

1. **单一实现层**：一个能力域只允许在一个 L 层实现（`ownedLayers` 只填一个值）。
   跨层出现即判 ERROR——除非该层是 [DESIGN-LAY-005] 允许的**调用方**而非实现方；
2. **命名单一真源**：同一概念只允许一个公开名称。新名称出现前必须先检索
   （B-U2 第 2 步），已存在的名称不得被「更准确的同义词」替换而并存两套；
3. **模式单一登记**：实现模式名必须来自 `docs/16_设计模式/registry/模式注册表.json` 的既有取值，
   新增模式须先登记该文件，不得在代码里自造模式名。

### B-U5 改已存在功能的路径（唯一合法路径）

要改一个已存在的功能，只允许：

1. 打开注册表找到该能力域的 `canonical`；
2. 在 `canonical` 处扩展；
3. 若现有实现确实不合适，走 **B-L2 迁移**流程（加标记 → 迁调用方 → 删旧实现），
   不得新建并行实现「先跑起来再说」。

**B-U5.1 禁止项**：以「旧实现有 bug，我新写一个」为由新增并行实现，判 ERROR。
bug 在旧实现上修，或在 B-L2 迁移里换，不允许两条路并存。

## 五、B-L：存量治理与防回退

### B-L1 存量重复的处置优先级

已存在的重复实现（本仓已知：`aiGateway` 等在 L2 与 ai-backend 各有一份）**不做一次性大重构**。
按以下优先级排序，逐域消化：

1. **P0**：会造成用户可见行为分歧的（两处实现给出不同结果）；
2. **P1**：两处都在被维护、都在被修改的（持续产生重复劳动）；
3. **P2**：其中一处已事实上停用但仍存在的（可整删）；
4. **P3**：仅结构相似但无调用方分歧的（记录在 `forbidden`，不强制合并）。

**禁止 P3 级一次性批量合并**——批量合并的回归风险远大于收益，这是「反复修改」的来源。

### B-L2 迁移流程（三步，每步独立可回滚）

```
步骤 1/3：标记 —— 在注册表中把目标标记为 deprecated，写清替代路径与预计删除日期
步骤 2/3：迁调用方 —— 逐个把调用方改到 canonical，每迁一个可独立提交
步骤 3/3：删旧实现 —— 调用方归零后删除；删除 PR 不得夹带其他改动
```

**每步都必须有回滚点**：任何一步出回归，可以单独 revert 该步而不影响其他步。
不允许「一次 PR 同时标记 + 迁移 + 删除」——那会让回滚无从下手。

### B-L3 决策不可回退（决策日志）

架构决策一旦记录，**只能追加新的取代决策，不能原地改写或删除旧决策**：

- 决策记录写在注册表 `notes`、设计文档或提案正文中；
- 撤销一个决策时，保留原决策 + 写明「被哪条新决策取代、何时、为什么」；
- 禁止把已有决策「悄悄改掉措辞」来让其看起来像是原本就如此。

这条是为了防止历史反复：同一个决定被改三次，等于从未决定过。

### B-L4 无谓改动的阻断清单

以下改动**默认不受理**，除非附 B-P2 提案并说明为何不能走 B-U5：

| # | 无谓改动类型 | 判定信号 |
|---|------------|---------|
| 1 | 纯重命名/纯换措辞（不改变行为） | diff 中只有标识符或字符串变化 |
| 2 | 重复实现「已存在的能力」 | B-U1 检索命中 `canonical` |
| 3 | 换实现范式重做已有功能（改语言/改模式/换目录） | `method` 或 `pattern` 字段变化 |
| 4 | 借上游新结构重写本仓同功能模块 | 提案第 6b 字段为空或「无既有实现」不实 |
| 5 | 只改格式/只调注释的「顺手清理」 | 与本次功能无关的格式化 diff |
