[DESIGN-PROCESS-002] 新机制落地四阶段流程#

定位：本文件回答一个问题——一条新机制（hook / 规则 / 门禁 / 预算）从「写出来」
到「敢让它拦人」，中间必须经过哪几步、每步的毕业条件是什么。

边界（与相邻规范谁管什么）：

  • 本文件管落地节奏（先观测后管控的顺序与毕业判据）；

[DESIGN-PROCESS-001] 管委派准入（谁做）；[DESIGN-CICD-001] 管门禁的实现。

  • 本文件不定义任何具体机制，只定义「把机制接进生产」的过程。

规则 ID：PROCESS-006。登记见 docs/10_规范/registry/RULES-REGISTRY.json。
上游依据：[DESIGN-ARCH-121] §K-11（Headless CI 四阶段）+ §K-05（Token 判据卡）。

1. 红线#

#必须 / 禁止判据
PP-1新拦截型机制必须先过 S1 观测阶段，禁止直接进 S3 门禁见 §2
PP-2阶段毕业以样本量计，禁止以时间计（「跑两周」不是判据）§3 每阶段样本阈值
PP-3S1/S2 阶段必须旁路记录，禁止阻断主流程观测不得改变行为
PP-4每个阶段必须有明确的回退动作，且回退不依赖未提交的代码见 §4
PP-5机制禁止在有争议样本未裁决时升阶争议须先收敛
PP-6同一机制禁止同时升两个阶段一次一阶，出问题可归因

2. 四阶段（以样本量替代书的时间口径）#

书侧（ch05 Headless CI）用「观察者 → 顾问 → 门禁 → 主动修复」四阶段，
但毕业条件是时间（2–4 周）。khyos 不采用时间口径——理由：

  • khyos 是单机单用户，无「团队接受度」维度，时间不产生新信息；
  • 时间口径会让「两天跑一次」和「一天跑两千次」获得同样的毕业资格；
  • 样本量才是判据质量的真变量。
阶段名称行为毕业条件（样本量）
S1观察者只记录，不拦截、不提示≥200 条相关事件，且无解释不了的样本
S2顾问记录 + 提示，但仍不拦截≥50 条提示后，误报率 <10%
S3门禁拦截，可豁免拦截生效后 ≥20 次真实拦截，豁免率 <20%
S4主动修复拦截 + 自动给出修法（或自动修）需要独立的回滚验证

为什么 S1 是 200 条：这是个能覆盖常见分支的量级。
低于它，误报率的分母太小，10% 的估计不可信。

为什么 S2 的误报率阈值是 10%：提示的代价是注意力。
误报率高于 10% 时，用户会开始忽略提示，机制退化成一个吵人的日志。

3. 各阶段的接线方式（khyos 落点）#

阶段推荐落点为什么
S1PostToolUse hook，matcher:"*"，写审计日志只观测，不干预；全量覆盖
S2PreToolUse hook，返回放行但附提示有干预能力但不用
S3PreToolUse hook 返回 permissionDecision + 静态 patternRules双层：动态看语义、静态看命令
S4S3 + 自动修复脚本风险最高，需独立回滚

双层防线（书 §5.6 的核心）：静态 patternRules（permissionStore.js）
管能写成前缀的命令；动态 PreToolUse hook 管静态规则表达不了的语义
（管道、重定向、命令替换——这些 pattern 规则永远不命中，见 [DESIGN-SKILL-001] §3 与
[DESIGN-ARCH-123] 修正 5）。两者不可互相替代。

4. 回退动作（PP-4）#

khyos 的 .khy/ 被 .gitignore:54 排除，不进版本控制——
故所有机制改动必须在动手前备份：

cp -r .khy/{skills,agents,hooks.json,permissions.json,settings.json} .khy/backups/$(date +%F)/
阶段回退动作是否依赖未提交代码
S1删 hook 条目 / 关开关否（纯配置）
S2同上否
S3同上 + 清 patternRules否
S4还原备份目录是——须先确认脚本已入库

S4 是唯一「回退依赖代码」的阶段，故其准入最严：脚本必须先 commit，
才能开启自动修复。

5. Token 经济学判据卡（K-05 本地化）#

书侧（ch10 §10.1）给出委派收益算例：输入 >> 输出 时才值得委派，
书中算例收益 6.8%，Prompt Caching 下回落到 1–2%。

khyos 的修正——收益优先级重排（书把成本排第一，khyos 不）：

优先级收益为什么 khyos 这样排
1上下文窗口保护khyos 的窗口是硬约束（charBudget = clamp(1% × window × 4, 500, 8000)）。委派省下的窗口能换回更多可用的对话轮次——这是书里没有的维度
2响应质量子智能体有独立上下文，不被主对话的噪声污染
3成本书的 6.8% 会被 khyos 的多供应商价差与 Prompt Caching 稀释到 1–2%，不足以单独支撑决策

判据（三问，任一为「是」即可委派）：

  1. 这一步的中间过程会吃掉超过 20% 的剩余窗口吗？
  2. 这个子任务需要与主对话不同的上下文吗？
  3. 它会产出被丢弃的中间产物（搜索结果、文件列表、长 diff）吗？

若三问皆「否」——不要委派。委派的固定开销（报文往返 + 上下文重建）
会超过收益。这与 [DESIGN-PROCESS-001] 的「默认自做」是同一结论的两个视角。

阶段登记位置（已落地）#

「当前各机制处于哪个阶段」登记在 FEATURE-OWNERSHIP.json 的 rollout.mechanisms[]
（该表已有能力域 → 实现位置的单一真源结构），字段：stage / previousStage /
samples.observed / rollback / executorStage。已登记两个机制：

机制阶段样本规则
agent-feedback-contract（三模态反馈契约）S168 / 200RUNTIME-007~009
rollout-stage-guard（本守卫自身）S10 / 200PROCESS-008

⚠ 判「S1/S2 有没有在拦」要复算，不要读字面值。守卫按 ruleguard 的 gateStrength()
派生强度：未声明 severity 时 P0/P1 会派生成 blocking。只看 severity 字段的
字面值会漏掉「没写 severity」这类——它和「写了 advisory」字面不同、效果可能一样。

⚠ 登记表的 stage 必须与执行器源码里的阶段常量一致（executorStage.constant），
漂移报 rollout-stage-authority-drift。这防的是「登记说 S1、代码其实在拦」：
那看起来一切正常，其他守卫还全绿。
