# [DESIGN-PROCESS-001] 委派边界决策矩阵（第六通道：外部智能体）

<!-- RULES-REGISTRY: PROCESS-004 -->

> **定位**：本文件回答一个问题——**一件活，什么时候 khy 自己做，什么时候才允许派给外部智能体**
> （Claude Code / Codex / OpenCode 等）。
>
> **与 `[DESIGN-ARCH-071]` 的关系**：071 管「一次读取 / 一次操作走哪条通道」（CH-1 直接读状态 →
> CH-5 看屏幕），前提是**活已经由 khy 自己在做**。本文件补它前面缺失的一问：**这活谁做**。
> 071 的五问是 CH-1..CH-5 的**内部**判定；CH-6（外部智能体委派）的准入由本文件在五问之前先行判定。
> 两者不重叠：本文件**不新增读写通道**，只定义执行主体的准入。
>
> **元规则依据**：`[MGMT-STD-008]` §3.2「正文只做指针+摘要，语义真源另存」。
> **规则 ID**：`PROCESS-004`（委派边界）。登记见 `docs/10_规范/registry/RULES-REGISTRY.json`。

## 0. 问题：委派没有边界，所以活会被甩出去

khy-os 的能力越来越强，外部智能体的接入越来越顺——问题不在「能不能委派」，而在
**没有任何一条规则说清楚「什么时候不许委派」**。实测（2026-09-16）三条委派面各自的洞：

| 委派面 | 入口 | 实缺口 |
|---|---|---|
| 认知层（提示词） | `services/backend/src/services/externalAgentDirective.js` → `buildExternalAgentDirective()` 注入 coding profile | 注入文案是**开放式授权**：准入条件写成「用户点名，**或某任务更适合交给一个完整的外部 agent 独立完成时**」。后半句把准入权交给了模型的临场感觉——「更适合」不可核验，等于没有准入。**这是「莫名其妙甩活」的直接来源。** |
| 路由层（工具） | `services/backend/src/tools/AgentTool/index.js` 对 `subagent_type:'claude'/'codex'/'opencode'` 真 spawn 外部 CLI | `claudeDelegation.js` 的 auto 启发式按「重构 / 多文件 / 迁移 / 端到端」等关键词判定「适合委派」——而这些**恰恰是 khy 自己的核心能力**。auto 路径目前被 feature flag 关着（默认 off），风险暂时被压制，不是被规则排除。 |
| 规划层（协作） | `services/backend/src/services/domain/collab/proactiveCollaboration/delegationPlanner.js` | 无准入概念。 |

**结论**：缺的不是执行链（早已成熟）、不是适配器（claude/codex/opencode 都是网关内一等公民），
缺的是**一条把「默认自做」写死的准入规则**。本文件即该规则的语义真源。

## 1. 第六通道定义与真源

| 通道 | 名称 | 入口 / 真源 | 前置条件 |
|---|---|---|---|
| CH-6 外部智能体委派 | 把任务交给外部编码 CLI agent 执行 | 路由 `services/backend/src/tools/AgentTool/index.js`（可委派项 `subagent_type:'claude'/'codex'/'opencode'`）；认知 `services/backend/src/services/externalAgentDirective.js`（`EXTERNAL_AGENTS` 注册表）；顶层会话 `khy <agent>`（`agentLauncherRegistry`，不可经 subagent_type 委派） | **本文件第 3 节的 G1 / G2 / G3 三闸门至少一者成立**；缺则一律 khy 自做 |

逐项含 `delegatable` 判定）。可委派项与顶层会话项的划分以该注册表为准，本文件不重复列举。

## 2. 判定顺序（第 0 问：谁做，自上而下首个命中即停）

> 本判定在 `[DESIGN-ARCH-071]` 的五问**之前**执行。

| 序 | 问 | 命中 → 处置 |
|---|---|---|
| 0.1 | 用户在本轮消息里**显式点名**某外部智能体、并要求它做这件事？ | → CH-6 委派，闸门记 **G1** |
| 0.2 | khy 本地能力**确实缺失**，且能指出缺的是哪一项？ | → CH-6 委派，闸门记 **G2** |
| 0.3 | 任务**必须在隔离的外部环境**里执行（本地执行无法产生可信证据，或会污染工作区）？ | → CH-6 委派，闸门记 **G3** |
| 0.4 | 其余一切 | → **khy 自做**（默认档），随后按 071 的五问选择读写通道 |

**默认档是自做，不是委派。** 这一条是本节的全部要点：委派是**例外**，需要主动举证；
自做是**常态**，不需要任何理由。

### 2.1 明确属于「khy 自做」的工作（列举非穷尽，用于堵住「更适合外部 agent」的口子）

多文件重构、跨文件改动、大规模实现、迁移、端到端实现、长任务编排、代码库理解、方案设计、
调研与检索、文档撰写、数据分析、结果验收。

> 上列工作**恰好是 auto 启发式判定「适合委派给 Claude Code」的那一类**。本表存在的意义就是
> 把这条判定反过来：命中这些关键词**不构成委派理由**，而是「khy 自己干」的强信号。

## 3. 三闸门（准入）

委派前必须命中且**只能命中**下列三闸门之一，并携带可核验的证据。

| 闸门 | 判据（可核验） | 必须携带的证据 | 反例（不成立） |
|---|---|---|---|
| **G1 用户点名** | 本轮用户消息同时出现「某外部 agent 的别名」+「驱动动词」。**确定性识别**由 `detectExternalAgentRequest()` 承担（两命中闸门，零假阳性：单出现 `claude` 而无驱动动词不接管，避免误伤「clause」类子串） | 无需额外证据——用户原话即证据 | 用户只是**提到**某 agent（「claude code 的架构是怎样的」）→ 那是调研任务，khy 自做 |
| **G2 能力缺失** | khy 本地**确实没有**完成该任务的工具 / 服务 / 技能 / 适配器，且调用方能**指名缺哪一项** | 缺失能力清单（一到数条，可被复查）。**且必须已在本地能力面检索过**（`src/tools/` 工具注册表、`skills/`、`src/services/gateway/adapters/`） | 「它更快」/「它更强」/「更省事」/「我可能做不好」——**均不构成能力缺失**，判 deny |
| **G3 隔离要求** | 任务产出**必须在外部环境内产生**，或本地执行会污染、破坏工作区 | isolation 说明：为什么本地做不到 / 为什么必须在外面 | 「顺手丢给外面跑」——无隔离必要即 deny |

> **三闸门都不成立时，唯一的正确处置是 khy 自做**，并在需要时向用户说明缺口，
> 由用户决定是否改变需求——不是自行改判为委派。

## 4. 委派契约（缺项即越权）

一次合法的委派必须同时携带下列四项；任何一项缺失，准入判定必须返回 **deny**：

| # | 项 | 内容 | 缺失时 |
|---|---|---|---|
| 4.1 | `gate` | `G1` / `G2` / `G3` 之一 | deny（`no-gate`） |
| 4.2 | `reason` | 一句话可核验理由。**禁止**出现「更适合 / 更强 / 更快 / 更省事 / suits / better suited」这类不可核验措辞 | deny（`vague-reason`） |
| 4.3 | `gap` 或 `isolation` | G2 ⇒ 缺失能力清单；G3 ⇒ 隔离原因 | deny（`missing-evidence`） |
| 4.4 | `prompt` | 自包含：目标 + 涉及文件的绝对路径 + 约束 + 期望产出（外部 agent **看不到**本次对话历史） | 拒绝发起调用 |

代码真源：`services/backend/src/services/externalAgentDirective.js` 的
`evaluateDelegationAdmission()`（纯叶子：确定性、零 I/O、绝不抛；无法判定时**一律 deny**）。
调用方若已声明 `selfCapable: true`（本地能覆盖），无论闸门如何**一律 deny**（`self-capable`）。

---

## 5. 禁止项（硬红线，不分闸门）

- **5.1 理解不可外包。** 需求理解、任务拆解、方案裁决、结果验收，必须由 khy 自己做。
  禁止写出「基于你的发现去修 bug」「按你的判断实现」这类把**综合**推给外部 agent 的提示词。
  委派的是**执行**，不是**判断**。
- **5.2 本地已覆盖时禁止委派。** khy 自有工具 / 服务 / 技能能完成时不得委派——**哪怕外部
  agent 更快**。第 2.1 节列出的工作类型即是本条的常见命中共性。
- **5.3 禁止「模型自认为更适合」。** 委派理由必须是**可核验的事实**（点名原话 / 缺失能力清单 /
  隔离要求），不得是模型的临场感觉。开放式授权措辞（「或某任务更适合交给外部 agent 时」）
  **禁止出现在任何注入给模型的文案里**。
- **5.4 禁止把委派当失败兜底。** 本地执行失败、超时、结果不满意，**不等于**准入成立——
  仍须走三闸门。禁止在委派失败后自动改派另一个外部 agent（级联甩锅）。
- **5.5 禁止无留痕委派。** 见第 6 节。

---

## 6. 留痕与回报

1. **留痕**：每次进入 CH-6 必须留下可复查记录——闸门 id、理由、目标 agent、任务摘要、
   结果处置。落点沿用既有轨迹 / 审计机制（`[DESIGN-ARCH-047]` 轨迹溯源、`.khy/audit-trajectory/`），
   **不新造存储目录**。
2. **回报**：向用户汇报时必须**显式声明**「已交给 X，闸门 Gn，理由 …」，不得静默转手。
   静默委派等同于把用户排除在决策之外。
3. **验收**：外部 agent 的产出**必须由 khy 自己验收**后才能作为结论交付；不得原样转述为
   「任务已完成」。验收判据沿用 `PROCESS-003`（验收门禁）。

## 7. 降级与回退

| 情形 | 处置 |
|---|---|
| 外部 agent CLI 不可用 / 未安装 | **先回自做档**；说明缺什么，由用户决定是否改变需求。**不得**自动改派另一个外部 agent |
| 委派超时 / 执行失败 | 回自做或向用户请示；**不得**级联改派（5.4） |
| 准入判定自身异常 | fail-closed：判 deny，走自做（`evaluateDelegationAdmission` 的失败语义） |
| 用户显式点名但该 agent 是顶层会话项（`delegatable: false`） | 不得经 subagent_type 硬转；提示用户 `khy <agent>` 启动，同时说明该任务也可由 khy 自做或交给可委派项 |

## 8. 反模式（命中即返工）

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 「这个大重构交给 claude code 更快」 | 多文件重构是 khy 的核心能力（2.1），且理由是「更快」——不可核验 | khy 自做；若用户确实想要外部 agent，等用户点名（G1） |
| 「先扔给 opencode 试试，不行我再上」 | 5.4：委派不是失败兜底；先委派再自做把成本翻倍 | 直接自做 |
| nudge 文案逼模型「立即调用 Agent 工具」而不管闸门 | 认知层只教了「可以委派」没教「何时不可以」 | 注入文案同时给默认档 + 三闸门 + 禁止项（本文件 §2–§5） |
| 委派后把外部输出原样贴给用户 | 理解与验收被外包（5.1 / §6.3） | 自己验收后交付，并声明闸门与理由 |
| 在 auto 路径里按关键词自行决定委派 | 关键词命中 ≠ 闸门成立（2.1 恰好是反例） | auto 路径必须经准入判定；无闸门即 deny |

## 10. 规则登记映射与执行器

| 规则 | ID | 档位 | 执行器 |
|---|---|---|---|
| 委派边界（默认自做 + 三闸门 + 禁止项 + 契约 + 留痕） | `PROCESS-004` | `pr` | `scripts/ci/check-delegation-boundary.js` |

执行器**静态**校验（确定性、零依赖）：

1. 代码 SSOT 的闸门集合（id + key）与本文件 §3 表格**双向一致**（防漂移）。
2. 注入文案必须含「默认自做」标记与三闸门 id；**不得**含开放式授权黑名单措辞。
3. 委派 nudge 必须携带闸门要求。
4. `claudeDelegation.js` 必须经 `evaluateDelegationAdmission()` 判定（静态断言 require + 调用）。
5. 外部 CLI 名（claude / codex / opencode）的进程拉起点必须收敛在白名单目录内，
   禁止在别处旁路 spawn。

行为侧的运行时断言（`evaluateDelegationAdmission` 的语义）由 `services/backend` 的单测承担。
