## 2. 四阶段（以样本量替代书的时间口径）

书侧（ch05 Headless CI）用「观察者 → 顾问 → 门禁 → 主动修复」四阶段，
但毕业条件是**时间**（2–4 周）。**khyos 不采用时间口径**——理由：

- khyos 是**单机单用户**，无「团队接受度」维度，时间不产生新信息；
- 时间口径会让「两天跑一次」和「一天跑两千次」获得同样的毕业资格；
- **样本量**才是判据质量的真变量。

| 阶段 | 名称 | 行为 | 毕业条件（**样本量**） |
| --- | --- | --- | --- |
| **S1** | 观察者 | 只记录，不拦截、不提示 | **≥200** 条相关事件，且无解释不了的样本 |
| **S2** | 顾问 | 记录 + 提示，但仍不拦截 | **≥50** 条提示后，误报率 **<10%** |
| **S3** | 门禁 | 拦截，可豁免 | 拦截生效后 **≥20** 次真实拦截，豁免率 **<20%** |
| **S4** | 主动修复 | 拦截 + 自动给出修法（或自动修） | 需要独立的回滚验证 |

> **为什么 S1 是 200 条**：这是个能覆盖常见分支的量级。
> 低于它，误报率的分母太小，10% 的估计不可信。
>
> **为什么 S2 的误报率阈值是 10%**：提示的代价是注意力。
> 误报率高于 10% 时，用户会开始忽略提示，机制退化成一个吵人的日志。

## 3. 各阶段的接线方式（khyos 落点）

| 阶段 | 推荐落点 | 为什么 |
| --- | --- | --- |
| S1 | `PostToolUse` hook，`matcher:"*"`，写审计日志 | 只观测，不干预；全量覆盖 |
| S2 | `PreToolUse` hook，**返回放行但附提示** | 有干预能力但不用 |
| S3 | `PreToolUse` hook 返回 `permissionDecision` + 静态 `patternRules` | 双层：动态看语义、静态看命令 |
| S4 | S3 + 自动修复脚本 | 风险最高，需独立回滚 |

> **双层防线**（书 §5.6 的核心）：静态 `patternRules`（`permissionStore.js`）
> 管**能写成前缀的命令**；动态 `PreToolUse` hook 管**静态规则表达不了的语义**
> （管道、重定向、命令替换——这些 pattern 规则**永远不命中**，见 `[DESIGN-SKILL-001]` §3 与
> `[DESIGN-ARCH-123]` 修正 5）。**两者不可互相替代。**

## 4. 回退动作（PP-4）

khyos 的 `.khy/` 被 `.gitignore:54` 排除，**不进版本控制**——
故所有机制改动**必须在动手前备份**：

```bash
cp -r .khy/{skills,agents,hooks.json,permissions.json,settings.json} .khy/backups/$(date +%F)/
```

| 阶段 | 回退动作 | 是否依赖未提交代码 |
| --- | --- | --- |
| S1 | 删 hook 条目 / 关开关 | 否（纯配置） |
| S2 | 同上 | 否 |
| S3 | 同上 + 清 `patternRules` | 否 |
| S4 | 还原备份目录 | **是**——须先确认脚本已入库 |

> **S4 是唯一「回退依赖代码」的阶段**，故其准入最严：脚本必须先 commit，
> 才能开启自动修复。

## 5. Token 经济学判据卡（K-05 本地化）

书侧（ch10 §10.1）给出委派收益算例：**输入 >> 输出** 时才值得委派，
书中算例收益 **6.8%**，Prompt Caching 下回落到 **1–2%**。

**khyos 的修正——收益优先级重排**（书把成本排第一，khyos 不）：

| 优先级 | 收益 | 为什么 khyos 这样排 |
| --- | --- | --- |
| **1** | **上下文窗口保护** | khyos 的窗口是**硬约束**（`charBudget = clamp(1% × window × 4, 500, 8000)`）。委派省下的窗口能换回**更多可用的对话轮次**——这是书里没有的维度 |
| **2** | **响应质量** | 子智能体有独立上下文，不被主对话的噪声污染 |
| **3** | **成本** | 书的 6.8% 会被 khyos 的多供应商价差与 Prompt Caching 稀释到 **1–2%**，不足以单独支撑决策 |

**判据（三问，任一为「是」即可委派）**：

1. 这一步的中间过程会**吃掉超过 20% 的剩余窗口**吗？
2. 这个子任务需要**与主对话不同的上下文**吗？
3. 它会产出**被丢弃的中间产物**（搜索结果、文件列表、长 diff）吗？

> 若三问皆「否」——**不要委派**。委派的固定开销（报文往返 + 上下文重建）
> 会超过收益。这与 `[DESIGN-PROCESS-001]` 的「默认自做」是同一结论的两个视角。
