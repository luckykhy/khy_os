# [PROCESS-102] 下一步最该做什么决策标准

> **域**：PROCESS（分支 / 提交 / 发布 / 评审 / 版本同步）
> **状态**：draft — PR 合并后置 active（元规则 §4.2）。
> **元规则**：`[MGMT-STD-008]` §1 规则卡格式；机器侧实现见 `services/backend/src/cli/hqStore.js` 的瀑布选取。

## 为什么需要这条规则

「我的 khy-os 现在最该做什么」此前没有可执行标准：`khy hq next` 只按 P0-P3 排序，
**同优先级靠登记先后顺序任取其一**；`ROADMAP.md` 的排期原则是散文，机器不读。
登记顺序是历史偶然，不是优先级——用它决胜等于把「没有标准」伪装成「有标准」。

## 调研与选型（2026-09-18）

| 框架 | 结论 |
|------|------|
| RICE（Reach×Impact×Confidence÷Effort） | 弃用 Reach 维度：个人项目无用户量数据，会产生伪精确分数 |
| MoSCoW | 只解决「要不要做」，桶内无序，解决不了「今天做哪个」 |
| ICE | 纯主观打分易漂，只保留其「整数轻评分」形式 |
| WSJF（延迟成本÷工量） | 采纳为核心：「风险消除」维度让排障/技术债能与功能公平竞标 |
| 约束理论 | 采纳为分档结构：永远先给系统瓶颈（未闭环的验收）解锁 |

最终形态：**五档瀑布定类，档内轻评分决胜，算不出就问**。

## 决策标准：五档瀑布

自上而下逐档执行，**首个能产出唯一赢家的档即答案**；任何一档并列则先试评分（见下），仍平局进 G4。

| 档 | 名称 | 命中条件（机判） | 建议动作 |
|----|------|------------------|----------|
| G0 | 健康 · 瓶颈解锁 | `status=review` 的任务；`status=pending_verify` 的 Bug；`doing`/`in_progress` 且租约已过期 | 验收 / 释放占用。只报清单与命令，**不渲染新活**（`--skip-health` 可显式跳过） |
| G1 | 救火 | `open` Bug，按严重度 P0→P3 | 修复（租约存活者跳过） |
| G2 | 要事 | `todo` 任务，priority P0/P1 | 领一条开工 |
| G3 | 次事 | `todo` 任务，priority P2/P3 | 领一条开工 |
| G4 | 疑问 | 上述任一档内多候选且评分无法决胜 | **停下来问人**，禁止代猜 |

### 档内评分（WSJF 简化制，整数锚点）

`得分 = cod × conf ÷ sizeWeight`，仅在**该档全部候选都有字段**时启用；任一缺字段直接 G4。

- `cod` 延迟成本 1-5：1=晚一周无所谓；3=晚一周明显拖体验；5=阻塞其他任务或红线敞口（安全/数据丢失）
- `conf` 把握 1-3：1=方案没验证过；2=有把握有细节待定；3=照着验收标准做完即可
- `size` 工量 S/M/L → 权重 1/2/3：S=半天内；M=一两天；L=一周级或跨端

字段登记在 PROGRESS.json 任务条目上（`cod`/`conf`/`size`，可选，`hq verify` 校验取值）；
`khy hq task note <ID> --cod 4 --conf 3 --size M` 可补登。**新任务登记时应顺手填**——
不填的代价是该任务永远只能靠 G4 被问起，而不是被系统推荐。

## 对 AI 回答的约束（本规则的主要消费者）

被问「现在最该做什么 / 下一步干嘛」时：

1. 读同一数据源：`khy hq next --json`（CH-3），不得凭印象或聊天记录回答；
2. 回答必须含**档位 + 证据计数 + 建议 ID**，模板：
   `第 X 档命中：{开放Bug n 条 / 待验收 m 条 / P1 待办 k 条} → 建议 <ID>「<标题>」，依据 <评分或严重度>`；
3. 机器返回 `action:"ask"`（G4）时，AI 同样**反问用户**「今天想动哪个方向」，
   列出候选与各自一句话理由；回答与选定结果应回写登记（补字段或直接开工）；
4. 不得推荐未登记在 PROGRESS.json/BUGS.json 的任务——先走登记再排程。

## 反例

```
❌ 「我觉得最近该搞一下 APK 那边」——无档位、无证据、来源是印象
❌ 两条 P1 并列时 next 推登记更早的 T-013——顺序不是优先级
❌ 有 6 个 Bug 卡在 pending_verify 却继续推荐新开工任务——闭环未合又开新口
```

```
✅ 「G0 命中：3 个 review 任务 + 6 个待验收 Bug + 1 个过期租约。先验收 T-023
   （密钥中心，P1）：khy hq next --task T-023。清完后才是 APK/同步之争」
✅ G4：「P1 待办并列 2 条：T-022 四端同步（无评分字段）、T-XXX…——今天想动哪个方向？
   或给它们补 cod/conf/size：khy hq task note T-022 --cod 4 --conf 2 --size L」
```

## 授予权力

见 frontmatter `grants`：G4 反问权 + 人的显式指定权（`--task` / `--verify` / `--skip-health`）。

## 提供福利

见 frontmatter `benefit`：答案自带证据；平局显性化为提问。

## 校验方式

- 机器侧：`services/backend/tests/cli/hqStore.test.js` 覆盖五档与平局行为；
- 登记侧：`node scripts/ci/check-gov-rules.js`（字段齐全 + 幂律配对）、
  `npm run check:rules`（登记表↔本文标记行双向可达）。

## 例外

- 用户本轮点名做什么：直接执行，不走瀑布；
- 现场故障（用户正被阻塞）：按 G1 处理，即使 Bug 尚未登记——先修，登记随后续。
