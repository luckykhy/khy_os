[DESIGN-DOC-001] 文档结构规范#

本文档定义 khy-os 项目的文档结构标准，包括命名、分类、存储等。

1. 文档概述#

1.1 设计原则#

  1. 唯一性：每个文档有唯一的编号
  2. 分类清晰：文档按类别分类存储
  3. 命名规范：统一的命名格式
  4. 版本控制：所有文档纳入版本控制

1.2 文档分类#

类别编号前缀说明
立项INIT项目立项文档
概念CONCEPTS概念入门文档
设计DESIGN设计文档
实现IMPL实现文档
测试TEST测试文档
部署DEPLOY部署文档
运维OPS运维文档
管理MGMT项目管理文档
故事STORY学AI/故事文档

2. 文件命名规范#

2.1 格式#

[STAGE-TYPE-NUMBER] 中文标题.md

标题用中文（符合读者习惯），编号与文件名结构遵循国际化规范（ISO/IEC/IEEE 15289 §6.1）。

2.2 字段说明#

字段说明示例
STAGE阶段（英文缩写）INIT, CONCEPTS, DESIGN, IMPL, TEST, DEPLOY, OPS, MGMT, STORY
TYPE类型（英文缩写）ARCH, DOC, RPT, MAN, STD, PLAN, OTHER, PERF, SIZE
NUMBER编号（三位数字）001, 002, 003...
中文标题文档标题仓库层级板块规范、API设计规范

2.3 国际化约束#

约束面向新写与修订的文档；存量文档中的历史命名沿用旧例，不追溯。

约束说明违规判定
编号仅用 ASCII[STAGE-TYPE-NUMBER] 部分全英文+数字+方括号编号含中文 = 违规
标题不含文件系统特殊字符禁止 `/ \ : * ? " < >`
编号与标题间单个空格[ARCH-068] 仓库规范 非 [ARCH-068] 仓库规范双空格 = 违规
标题 ≤15 个中文字符保证可检索性（存量超长标题修订时逐步缩短）新文件超 15 字 = 违规
标题用 CJK 基本区字符不用罕见 Unicode 变体含生僻字 = 违规
文件扩展名小写.md 非 .MD大写扩展名 = 违规
全局唯一编号不重复、标题不重复重号/重名 = 违规

2.4 示例#

[DESIGN-LAY-005] 仓库层级板块规范.md
[OPS-MAN-173] MCP工具接入快速上手.md
[IMPL-RPT-015] 修复记录时间线.md
[DESIGN-DB-001] 数据库规范.md

5. 文档编号管理#

5.1 编号分配规则#

  1. 唯一性：每个编号只能使用一次
  2. 连续性：编号按顺序分配
  3. 预留空间：每个类型预留足够空间

5.2 编号范围#

类型编号范围说明
ARCH001-099架构文档
DOC001-099文档规范
RPT001-099报告文档
MAN001-099手册文档
STD001-099标准文档
PLAN001-099计划文档
OTHER001-099其他文档
PERF001-099性能文档
SIZE001-099体积文档

规范族用域字母轴：[DESIGN-<域>-NNN]，域 = 规范主题（API/ACP/DB/FE/SEC/TEST/…），
与 ARCH（设计血缘）正交；全量域清单见 [DESIGN-LAY-005] §3.1 与 10_规范/00_INDEX_规范-总目录 §3。编号由 AI 感知目录既有惯例动态分配
（[MGMT-STD-001] 第 2.4 条：删除后不回收，历史断档保留）。

5.3 编号冲突处理#

禁止：多个文档使用相同编号

解决：

  1. 保留先创建的文档编号
  2. 为新文档分配新编号
  3. 更新索引文件

6. HTML 文档管理#

结论：.html 孪生件纳入版本控制，与 .md 成对提交。条文真源是 [OPS-MAN-169] 第 2.5 条。

6.1 原则#

  • Markdown 为源：所有文档以 .md 为唯一手写源文件，不手写 .html
  • HTML 为孪生件：每个参与构建的 .md 必须有同名 .html，与 .md 同目录，由 npm run docs:build 生成
  • 纳入版本控制：.html 与 .md 一起提交。仓库 .gitignore 中不存在任何 html 忽略条目，git 已跟踪 461 个 docs/ 下的 .html

6.2 生成与校验#

npm run docs:build     # 生成同名 .html 孪生（含 mermaid 内联与链接重写）
npm run docs:verify    # 硬门：缺孪生 / 链接不可解析 / 离线资产缺失 → 非零退出

无 .md 源的孤儿 .html 由 scripts/docs/cleanup-orphan-html.js 清理（单向：只删孤儿，不反向补建缺失孪生）。

2026-09-15 修正：本节旧版称「HTML 为导出格式，不纳入版本控制」并给出 docs/**/*.html 的 gitignore 片段，与实际状态（无该忽略条目、孪生件被跟踪、verify_docs_site.js 硬门要求孪生齐全）完全相反，已按 [DESIGN-LAY-002] 第 8 节①裁决改写。

12. 规范骨架（新写规范必遵，2026-09-10 起；存量不追溯）#

目的：规范是约束不是散文——读者要的是「该怎么做、破了怎么办」，不是背景故事。
新规范一律按此骨架写；存量规范修订时逐步靠拢，不强制整篇重写，新增条目按骨架追加（§4 版本历史后补 §12 结构）。
本节同时定义 Markdown 源文档的中文阅读习惯排版约束（另见 [DESIGN-ARCH-023]）。

# [DESIGN-<域>-NNN] 标题

> **定位**：一句话（管什么 + 与哪篇真源的关系）
> **结论**：三句话说清核心要求（结论先行）

## 1. 红线          ← 必须/禁止，表格式，一行一条，可直接判违规
## 2. 反例 → 正例   ← 成对给出（❌/✅ 或 反例列 + 修法列）
## 3. 校验（守卫）  ← 哪条守卫管它（脚本名）；暂无守卫则写「待工具化 + 登记在 070 哪条」
## 4. 版本历史       ← 一行一变更；被 070 等引用的章节改号前先查入站引用

三条写法约束：

  1. 全文 ≤ 150 行（含表格）；超出的细则拆子篇或移实现记录；
  2. 每句「必须/禁止」必须可判定（能写成守卫断言或评审 checklist 项），删不掉的形容词；
  3. 定位行必须说清边界（与相邻规范谁管什么，防止两篇说各话）。

13. 中文阅读习惯排版约束（2026-09-12 起）#

依据：中文技术文档读者平均段落容忍度 ≤ 15 行，过长段落需拆分；标题层级 ≤ 3 级；关键信息前置。
本节约束适用于所有 .md 源文档（含 10_规范/、03_DESIGN_设计/、08_MGMT_项目管理/ 等）。

【scope 裁决 2026-09-17】 本节是「.md 源文档中文排版习惯」的唯一真源
（依据 [MGMT-STD-008] §2.2「重叠即违规」——同域同 subject 必须合并，不靠优先级覆盖）。
[DESIGN-ARCH-023] §13 曾与本节逐条重复，现降为指针：排版习惯看本节，
「怎么渲染出 docx」看 [DESIGN-ARCH-023] §1–§12 的工具链设计。

13.1 段落长度#

  • 每段 ≤ 15 行非空内容；超过 15 行必须拆成多段，或用表格/列表重构；
  • 连续 3 段以上相同句式 → 改为表格；
  • 论证段落与结论段落之间留 1 个空行。

13.2 标题层级#

  • 全文不超过 3 级标题（##、###、####）；禁止出现 #####；
  • 同级标题下内容结构应一致（不要一个 ### 下只有 1 行，另一个下有 20 行）；
  • ## 标题用于章节（概述/红线/版本历史等）；### 用于子节；#### 仅用于表格前的引导语。

13.3 关键信息前置#

  • 每节首段用 > **结论**：... 引用块写出核心要点；
  • 表格前必须有 1-2 句说明文字（不要裸表格）；
  • 红线表格每行必须包含「触发条件」和「违规后果」两列。

13.4 留白与分隔#

  • 章节之间留 2 个空行（--- 分隔线除外）；
  • 表格前后各留 1 个空行；
  • 代码块前后各留 1 个空行；
  • 列表 ≤ 5 项时用 - 列表；> 5 项时改用表格或拆成子节。

13.5 引用块使用#

  • > 引用块用于：结论、警告、注意、与相邻规范的边界说明；
  • 禁止连续 2 个以上引用块无正文分隔；
  • 引用块内不要放代码（以防 Markdown 渲染歧义）。

13.6 表格规范#

  • 表格列数 ≤ 5 列；超过 5 列必须拆分；
  • 表头必须加粗（**表头**）；
  • 表格内容不超过 20 字/格；超长内容移至正文或子节；
  • 表格必须有「说明」列或表前引言。
