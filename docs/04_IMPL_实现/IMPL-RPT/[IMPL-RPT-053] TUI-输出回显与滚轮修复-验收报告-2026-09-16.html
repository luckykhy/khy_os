TUI「输出回显不可见」+「滚轮回溯历史」修复 · 验收报告#

  • 日期：2026-09-16
  • 范围：services/backend/src/cli/tui/**
  • 门控回退：KHY_INLINE_TRANSCRIPT=0 KHY_MOUSE_WHEEL=0 khy（逐字节回到修前行为）

一、结论#

问题状态判据
最大化 / 小窗口下输出回显看不见已修8 尺寸 × 逐帧实测：无 h>=rows 帧、无清屏帧
滚轮用于滚内容区，输入框固定底部已修滚轮优先 onWheel(dir)；输入框在 Viewport 之外，不参与滚动
视口贴底（显示最新内容）已修末帧含最新消息 + 仅 ↑ 指示器

二、四个根因（全部经无头 harness 实证，非推断）#

A. 转录被 ink 的 fullscreen 清屏抹掉，且会自锁#

ink.js:320 的 isFullscreen = stdout.isTTY && outputHeight >= stdout.rows 只是判定；
真正决定清屏的是 this.lastOutputHeight >= this.options.stdout.rows —— 上一帧的高度。

一旦某帧高度 ≥ rows，lastOutputHeight 就永远 ≥ rows，此后每帧都清屏。
在备用缓冲区（\x1b[?1049h，无回滚缓冲）下，清屏 = 转录整片消失。

  • 实证：legacy 100×24 忙态帧 = 24 行 = rows → 每帧 clear=true
  • 根因：spinnerH 记成 1 行，实际渲染 3 行

（ink 的边框语义是「设了 borderStyle 就四边全画」，只写 borderBottom 不会关掉其余三边）

  • 修后：23 行，clear=false

B. chrome 账本漏计三项（Preview 布局）#

_viewportHeight 的账本没扣：忙态 spinner 的真实 3 行、Preview 独有的标题栏 1 行 + 底部分隔线 1 行。

  • 实证：preview 130×40 忙态帧 = 45 行 > 40
  • 修后：38 行，clear=false
  • 同时把 previewLayoutMode 的判定前移到 _viewportHeight 之前 —— 账本必须知道本帧走哪套 chrome

C. 视口永远停在顶部#

历史判据 scroll >= maxScroll 判「之前在底部」，但调用方 state 初值是 0。
内容一旦长过视口，0 >= maxScroll 恒假 → 视口永远显示最早那几行。

  • 修法：引入贴底哨兵 —— null / undefined / 负数 = 追随最新内容；数字 = 固定偏移；

滚回最底时回写 null 自动恢复跟随（不需要额外 sticky 标志位）

  • 真源落在 ink-components/Viewport.js 的 resolveViewportOffset / applyStickyViewportAction（纯叶子、可单测），

App 里不再另抄一份

D. 滚轮被终端合成为 ↑/↓#

备用缓冲区下终端把滚轮事件变成 ↑/↓ 字节送进 stdin，被 arrowRouting 绑成
history:previous / history:next → 表现为「滚一下召回一条输入历史」。

  • 修法：接管 SGR 鼠标协议（滚轮 = 按钮 64/65，修饰位 shift/meta/ctrl 加在低位 → button & ~28 剥掉），

在应用内消化滚轮，终端一个字节都收不到，方向键无从合成

7.3 好消息：损坏是可读的，我已核过语义冲突#

损坏只吃了两类东西：① expect(X).toBe(Y) 里的 )（GBK 解码吞掉一个字节）；
② CJK 字符串。断言语义完整可辨。

其中 scrollActions.test.js 明确锁了：

expect(applyScroll('lineUp', { ...D, offset: -5 })).toBe(0);   // 负数 → 顶

而我在 Viewport.resolveViewportOffset 里把负数定义成贴底 —— 表面看是冲突。

核验结论：不冲突。 三点理由：

  1. 两者是不同的叶子模块：tui/scrollActions.js vs ink-components/Viewport.js
  2. applyStickyViewportAction 先经 resolveViewportOffset 把哨兵归一成数字，

负数永远不会裸进 applyScroll

  1. 所有 applyScroll / applyViewportScroll 调用点传入的 state 初值都是 0，

没有任何路径把 null 喂进去：

  • App.js:4427 ← transcriptScroll（useState(0)）
  • App.js:4941 ← previewSidebarScroll（useState(0)，且调用处已写 Number(s) || 0）
  • CcTranscriptView.js:99/106/112/116 ← scrollOffset（useState(0)）

9.2 方法#

  1. git show HEAD:<path> 取回损坏原件；
  2. 逐条把 expect(f(x).toBe(y) 的括号还原，按当前 src/ 核对断言语义

（这一步是关键 —— 原件编码的是历史行为，不能照抄）；

  1. 改写为 node:test 风格（expect(x).toBe(y) → assert.equal(x, y)，

.toBeTruthy() → assert.ok，.not.toThrow() → assert.doesNotThrow）；

  1. require 路径按 §三 A 的口径重算为 ../../../src/cli/tui/<module>

（原件的 ./<module> 深度本来就是错的）。

transcriptLines.test.js 是例外：它的 CJK 字面量整段丢失（不像另外 3 个只丢 )），
期望行无法恢复，只能从当前源码反推。已在文件头注明。

十、环境坑（本轮新踩，记下来省时间）#

  1. node .khyos/diag/headless-frames.js <cols> <rows> 的第 4 个参数（消息条数）不起作用 ——
