## 一、先把「不一致」拆成三个具体错位

页脚那一行本身就有两个字段，加上报错，共三处数据，来自三个互不联动的源：

| # | 显示位置 | 显示值 | 数据源 | 语义 |
|---|---------|--------|--------|------|
| ① | 页脚 `[...]` 模型名 | `agnes-3.0-flash` | `gateway.getActiveAdapter().activeModel` | 「我**打算**用谁」 |
| ② | 页脚 `[...]` 通道 | （截图中被裁切） | `process.env.GATEWAY_PREFERRED_ADAPTER` | 「环境变量**声明**用谁」 |
| ③ | 报错正文 | `windsurf [unavailable]` | `aiGatewayGenerateMethod` 的 `allAttempts` | 「我**实际去连**了谁，失败」 |

### 错位 A：① 显示 agnes，③ 实际连 windsurf

**根因**：`getActiveAdapter()` 的 Tier 2 分支。

`aiGatewayModelMethods.js:430-530` 的解析顺序是：

```
Tier 1  GATEWAY_PREFERRED_ADAPTER（env 显式钉选）
Tier 2  lastVerifiedModelStore（上次成功的 model+adapter）
Tier 3  getDefaultRouteRecommendation()
Tier 4  按优先级取第一个 available
```

当前 env 里 `GATEWAY_PREFERRED_ADAPTER=windsurf`，但本机：
- `~/AppData/Roaming/Windsurf/User/globalStorage/storage.json` → **不存在**
- `AppData/Local/Programs/Windsurf` → **不存在**

于是 `windsurfAdapter.detect()` 返回 `false`，**Tier 1 被跳过**，落到 **Tier 2**：

```js
const lastVerified = this._getLastVerifiedActiveAdapter();
if (lastVerified) { return lastVerified; }   // ← 这里返回了 api / agnes-3.0-flash
```

`.khy/last_verified_model.json` 里存的正是 `{model: agnes-3.0-flash, adapter: api}`。

**但 Tier 1 的「跳过」只发生在 `getActiveAdapter()` 这个只读展示函数里，不影响真正的请求寻路。** 真正的寻路走 `aiGatewayGenerateMethod.js:4026`：

```js
if (strictPreferredOnly && entry.key === preferredAdapter) {
  return finishResult({ ... errorType: 'unavailable' }, ...);   // 直接返回，不回退
}
```

`GATEWAY_PREFERRED_STRICT=true` → `strictPreferredOnly=true` → 请求被**硬钉在 windsurf 上直接失败**。

> **一句话**：`getActiveAdapter()` 会**聪明地绕开**不可用的钉选通道，而 `generate()` 会**死板地死在**那个通道上。同一个 `GATEWAY_PREFERRED_ADAPTER`，两个消费点的容错策略完全相反 —— 这是错位 A 的全部原因。

### 错位 B：② 页脚通道字段显示错误

`App.js:737`：

```js
adapter: process.env.GATEWAY_PREFERRED_ADAPTER || active?.name || f.adapter || 'auto',
```

这里**优先读 env**，而不是读 `active?.key`。env 是 `windsurf`，所以页脚通道段会显示 windsurf，**而实际活动适配器是 api**。这一行把「声明」写进了「实际」的位置。

### 错位 C：失败时页脚不刷新

`refreshFooter()` 的触发条件（`App.js:3714-3728`）：

```js
const _querySettled = query.status === 'idle' || query.status === 'done';
React.useEffect(() => { refreshFooter(); }, [refreshFooter, query.adapterInfo, _querySettled]);
```

只在 `adapterInfo` 变化或 turn 落到 `idle`/`done` 时触发。**失败路径既不更新 `adapterInfo` 也不进入 `done`**，因此页脚停留在失败前的乐观值 —— 用户看到 agnes 一直挂着，而实际每次都在 windsurf 上撞墙。

## 二、要修的不是「显示」，是「口径」

**核心问题**：现在没有任何一个对象同时掌握「用户想要什么 / 实际用了什么 / 结果如何」。

三处各自推导，必然漂移。修复方向不是把三处改成同一个字符串（治标），而是**建立一个单一真源的「路由事实」对象**，三处都只读它。

### 设计：`RouteFact`（路由事实快照）

每次 `generate()` 结束时（无论成败）产出一个事实快照，字段语义必须唯一：

```js
{
  requested:   { adapter: 'windsurf', model: 'claude-3.5-sonnet' },  // 用户/环境声明的意图
  resolved:    { adapter: 'api',      model: 'agnes-3.0-flash'  },  // 网关解析后的选路
  attempted:   { adapter: 'windsurf', model: 'claude-3.5-sonnet' },  // 实际发出的第一个请求
  served:      { adapter: 'api',      model: 'agnes-3.0-flash'  },  // 成功的那个（失败则为 null）
  outcome:     'failed',                                             // ok | failed | partial
  strictPinned: true,                                                // 是否被 strict 硬钉
  reason:      'windsurf unavailable',
  at: 1789...
}
```

**字段语义是唯一的**，不允许任何消费点自行推导。这是全部修复的地基。

## 三、修复清单（按依赖顺序，5 步）

### Step 1｜建立 `RouteFact`（地基，必须最先做）

- **新增**：`services/backend/src/services/gateway/routeFact.js`（纯叶子，零 IO）
- 提供 `buildRouteFact(result, options)` 与 `createEmptyRouteFact()`
- **接线点**：`aiGatewayGenerateMethod.js` 的 `finishResult()` —— 所有成功/失败出口都汇聚于此，是唯一不需要改 N 处的挂载点
- **不改**任何既有返回字段（`actualAdapter` / `attempts` 全部保留），只**追加** `routeFact`

> 落点选择理由：`finishResult` 已是现有收敛点，避开在 20+ 个 `return` 语句处逐个埋点。

### Step 2｜修错位 A：`getActiveAdapter()` 与 `generate()` 口径统一

两个选项，需你裁决：

| 选项 | 做法 | 影响 |
|------|------|------|
| **A1（推荐）** | `getActiveAdapter()` 增加 `strictPinned` 标记；检测到「Tier 1 因不可用被跳过」时，回落到 Tier 1 通道的**失败态**而非 Tier 2 的成功态 | 页脚会显示 `windsurf (不可用)`，与报错一致 —— **诚实但难看** |
| **A2** | 保持 `getActiveAdapter()` 现行为，但页脚在 `strictPinned && 实际失败` 时叠加告警标记 | 页脚显示 `agnes-3.0-flash ⚠ 钉选通道 windsurf 不可用` —— **信息更全，但需新增渲染逻辑** |

两者都能做到一致；A1 改后端语义，A2 改前端展示。**建议 A2**，因为 agnes 确实是「打算用它」的那个，抹掉它反而丢失信息。

### Step 3｜修错位 B：页脚通道字段改读实际值

`App.js:737` 改为：

```js
adapter: active?.key || process.env.GATEWAY_PREFERRED_ADAPTER || f.adapter || 'auto',
```

即**实际优先，声明兜底**。同时在页脚新增「意图 ≠ 实际」的视觉区分（如 `windsurf→api`）。

### Step 4｜修错位 C：失败路径也刷新页脚

`App.js:3714` 的依赖数组加入失败信号：

```js
const _querySettled = query.status === 'idle' || query.status === 'done';
React.useEffect(() => { refreshFooter(); },
  [refreshFooter, query.adapterInfo, _querySettled, query.lastErrorAt]);  // ← 新增
```

需在 query bridge 侧暴露 `lastErrorAt`（失败时递增的时间戳）。

### Step 5｜修配置（消除现场，非代码问题）

`services/backend/.env:19-20` 当前值与文件内 09-14 注释自相矛盾 —— 注释明确写了「改用 auto」，值却是 `windsurf` + `strict=true`：

```
GATEWAY_PREFERRED_ADAPTER=windsurf     # 注释说该改 auto，实际没改
GATEWAY_PREFERRED_STRICT=true          # strict 抑制回退 → 硬失败
```

这正是 `.env:12-18` 记录过的 **codex 事故的第二次复发**（上次钉 codex，这次钉 windsurf，机制完全相同）。建议：
- `GATEWAY_PREFERRED_ADAPTER=auto`
- 或钉到真实可用的 `api`（模型需带池前缀 `agnes:agnes-3.0-flash`）
- 清理 `RELAY_API_KEY=quality-gate-windsurf-access-token-fixture`（测试夹具值，导致 relay 通道必然 404，已实测留存于 `relay_api_runtime_diagnostics.json`）

## 七、实施记录（2026-09-17）

### 7.1 新增：`gateway/routeFact.js`（纯叶子）

零 IO、零 require、不读 env、绝不抛。导出 `createEmptyRouteFact` / `buildRouteFact` /
`formatRouteFactLabel` / `isPinnedAdapter` / `isStrictPinned` / `_assertCoherent`。

字段语义唯一：`requested`（意图）/ `resolved`（解析）/ `attempted`（实发）/ `served`（成功者）/
`outcome` / `strictPinned` / `pinnedUnavailable`。

三条一致性不变式由 `_assertCoherent` 校验（返回违规清单，**不抛** —— 诊断设施不该成为故障源）：
- `outcome==='ok'` ⟺ `served` 非空
- `outcome==='failed'` → `served === null`
- `strictPinned && pinnedUnavailable` → 必为 `failed`

**接线点**：`aiGatewayGenerateMethod.js` 的 `finishResult()`。它是全部出口（成功 + 20 余处失败 return）
的既有收敛点，在此**追加** `routeFact` 字段，既有 `attempts`/`actualAdapter`/`errorType` 逐字节不变。

### 7.2 统一选路口径：`aiGatewayModelMethods.js`

`getActiveAdapter()` 在 Tier1 落空时记下 `pinnedSkipped = {active, adapter, strict}`，
挂到后续分支返回的 status 对象上。**不改选路行为**（仍会回落到可用通道），
只让「我绕开了一个钉选通道」这件事可被观测。

### 7.3 页脚三处修复

| 文件 | 改动 |
|------|------|
| `App.js` | 通道字段改 `active?.key \|\| env \|\| ...`（**实际优先**，原来反了）；失败时叠加 `modelStatus` 告警 |
| `App.js` | `refreshFooter` 依赖数组加入 `query.turnFailureAt` |
| `useQueryBridge.js` | 新增 `turnFailureAt` state，非中断失败时递增 |
| `footerStability.js` | 新增 `FOOTER_VALUE_KEYS`（`modelStatus`/`pinnedSkip`）按**值**比较 |
| `FooterBar.js` | 新增 `pinnedSkipSeg`：strict 时红字硬预警，非 strict 时黄字回退提示 |

**`footerStability` 这处是实施中发现的隐藏陷阱**：`modelStatus` 每次都是新对象字面量，
若用 `!==` 比较会永远判不等（守卫失效 → 渲染风暴复发）；若完全不比较，告警就不会重绘
（等于没修）。故必须做**稳定摘要的按值比较**，并显式按 key 排序以免疫键序差异。

### 7.4 防第三次复发：`baseSelfCheckService.js`

原方案把这条列为「附带建议」，实施时升级为必做 —— 因为这是同一 bug 的**第二次**复发
（codex 09-14 → windsurf 09-17），不加固必会有第三次。
