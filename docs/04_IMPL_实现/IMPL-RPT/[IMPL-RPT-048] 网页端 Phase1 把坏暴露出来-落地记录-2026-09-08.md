## 2. A 类余项：三项决策

计划 §7.1.4 说「逐项二选一，不留第三种」。三项真的做了二选一，另外三项是计划里的诊断错了，另三项明确延后。

**① 挂载 `routes/configSync.js`（已修）**

计划的描述是「两个服务端都没挂载」。更准确的说法：`node_modules/khy-ai-backend/server.js:96` **有**挂载，所以 npm 安装的生产版一直在跑；缺的是 `services/backend/server.js`。而 `src/cli/configSyncClient.js` 只调 `${BACKEND_PORT}`（Express），于是源码 checkout 起的服务全部 404，而客户端的 `catch {}` 静默降级本地——四端同步在开发环境里从未真正执行过，代码里也没有任何「这里断了」的痕迹。路由自带 `authMiddleware` + `KHY_CONFIG_SYNC` 门控，加一行挂载即可。

**② `/api/password-reset/send-code`、`/verify-code`（保留现状 + 文档化）**

这两条端点确实不存在，但 CLI 侧不是静默失败：`cliAuthService.js:798-800` 返回的文案是「验证码发送功能需要后端服务支持。请确保服务已启动，或使用密保问题找回密码」，`routerDispatchTail.js:1293-1295` 用 `printError` 打出来然后 `return true` 停住流程。已满足规则 2.2 的「问题 + 修复」，所以没有为了对称而补一个空端点。真正做的是把分叉变成机器可查的：`/api/auth/capabilities` 的 `passwordReset.mode` 现在明确报 `security-question`，并且 `auth.capabilities.test.js` 有一条漂移守卫断言 `defaultAdminAvailable === false` 时路由栈里不得出现 `default-admin`。

**③ `/api/md-workbench/*`（保留现状 + 提升错误文案）**

计划说「建三个端点，或砍掉服务端半区」。实际上这个端点命名全仓只出现 3 次，**全都在 `Markdown.vue`**（`:553` `:574` `:595`）——没有第三个消费者需要一起砍。而页面其实**已经**把失败浮出来了：每个 catch 都写 `serverError.value = serverErr(e, '无法列出服务器文件')` 或 `setStatus('保存失败：' + serverErr(e, ...), 'err')`。唯一的问题是兜底文案会把 404 读成「服务器上没文件」。所以只在 `serverErr` 里加了一个 404 分支，改走 `describeLoadError` 的「问题 + 识别码 + 修复」口径，并写明服务端尚未提供该接口。

**未动（明确延后）**：`configSyncClient` 的 `EventSource` 凭证查询串、`useConfigSync.js:217` 的凭证查询串（Phase 4）、`md-workbench` 端点要不要真建（需单独评审）、`/reset-password` token 页（Phase 3.1）。

## 3. 计划里被实测推翻的 4 处判断

这些是实施过程中被实测推翻的。留在这里是为了不让下一轮再走一遍弯路。

### 3.1 「第三控制面的 token 参数是白拿的凭证泄露」

`scripts/ai-manage-daemon.js:555-560` 在**任何路径分发之前**就校验 token：

```js
const urlObj = new URL(req.url, 'http://127.0.0.1');
const pathname = urlObj.pathname;
const token = readAuthToken(req, urlObj);
if (token !== controlToken) {
  return sendJson(res, 401, { ok: false, error: 'unauthorized' });
}
```

所以 `/open`、`/ping`、`/close` **都要** token。我一度删掉了 `?token=`，那会让三个 POST 全部 401 → `failureCount` 打到 `maxFailures = 3` → `disableBridge()`，会话桥（守护进程据此统计还开着几个标签页）静默死亡。已回退。

真正可以换掉 URL 查询串的理由是另一条：`readAuthToken` 优先读 `X-Khy-Token`，而 `sendJson` 已经把 `Access-Control-Allow-Headers` 放行了 `X-Khy-Token`，OPTIONS 也有独立处理（`:551-553`）。所以 header 方案在这个端点上**技术上可行**——只是它属于「凭证不进 URL」这类后续改造，需要在守护进程侧做而不是在页面侧删参数。

### 3.2 「`useProxies.egress.wiring.test.js` 永远不可能通过」

实测 11/11 通过。根因是计划把「wiring 测试通过」误读成「端点可用」：源级断言只检查函数名、URL 字符串和模板绑定，不发起请求。`/api/proxy-egress` 的后端在 `src/services/aiManagementServer.js:2361-2368`，处理器来自叶子 `aiManagementProxyEgress.js`——它一直存在，只是在**另一个**服务端（9090 守护进程）上。所以 `/proxies` 的两半是**分属两个后端**，不是「一半有后端一半没有」。

由此新增一条归属守卫（`tests/routes/p1MountWiring.test.js`）：`proxy-egress` 不允许出现在 Express 的 `server.js` 里，且守护进程侧的三路分派与处理器引入必须同时在位。


---

### 3.3 Phase 1.3 的机制选错了

计划说「删除 `request` 的 `catch {}` 空吞」。实测 `src/api/request.js` 的响应拦截器是全应用唯一正确的那份：401 跳登录、非 `silent` 的错误集中 toast、GET/HEAD/OPTIONS 网络重试、统一 30s 超时。它本身没有空吞。

真正空吞的是**页面层**：6 个用量/定价读取函数 catch 掉异常后返回旧默认值，页面就渲染出一张空表。所以修法不是动 `request`，而是在页面侧把失败落到一个可渲染的 ref 上。`src/api/loadError.js` 提供 `useLoadError` / `describeLoadError` / `loadInto` 三件套，文案口径统一走规则 2.2。

---

### 3.4 一个预存的测试在验证格式而不是接线

`tests/aiManagementProxyEgress.wiring.test.js` 原本把三条分派断言写成单行：

```js
assert.match(SERVER_SRC, /pathname === '\/api\/proxy-egress'\) return handleGetProxyEgressStatus/);
```

源码按仓库 2 空格缩进风格是 `if (...) { \n return handleX(req, res); }`，所以这条断言**从来不匹配**——它红的时候不会有人去查接线，只会去改格式，正好是「给盲点重新画地图」的测试版。已改为归一化空白后匹配，断言的是「条件与处理器成对存在」而不是它们的排版。同一件事我在新增的 `p1MountWiring.test.js` 里一开始也犯了，已用同样方式修掉。

## 8. Phase 2「IA 与路由收口」落地记录-2026-09-08

### 8.1 D1 裁定：32 个端点，超出方案 X 的阈值，走方案 Y

§0.1 给方案 X 的门槛是「端点数 ≤ 10」。实测不是 6~7 个，而是**三个命名空间、32 个端点**：

| 命名空间 | 端点数 | 单体 `services/backend` | 守护进程 `services/ai-backend` |
|---|---:|---|---|
| `/api/workflow/*` | 19 | 无 | 有 |
| `/api/marketplace/*` | 5 | 无 | 有 |
| `/api/plugins/*` | 8 | 无 | 有 |
| `/api/gui-eval/*` | 12 | **已有** | — |
| `/api/web-frontend-eval/*` | 16 | **已有** | — |
| `/api/proxy-subscriptions/*` | 5 | **已有** | — |

设计文档 §6.2 说「6 个命名空间只在守护进程有」是**部分过期**的：`routes/guiEval.js`、`routes/webFrontendEval.js`、`routes/proxySubscription.js` 三个文件单体早就挂上了。真正缺的只有 workflow / marketplace / plugins。32 ≫ 10，方案 X 不成立，按 §6.2「不建议两种都不做」落到方案 Y：探测到不可用时隐藏入口，而不是让生产静态服务 `dist/` 时整片 404 且无提示。

前端只有**一个** `VITE_AI_API_BASE_URL`（`request.js:13`），不存在按命名空间分流，所以这些命名空间要么整体挂上、要么整体不可达——一次探测足够，不需要逐命名空间路由。

落地：

- `src/api/daemonProbe.js`（新）：探测 `/api/workflow`、`/api/marketplace` 两个命名空间根。**只在明确的 404/405 时判定不可用**；5xx、网络错误、静态 `index.html` 兜底一律**失败放行**——藏掉一个还能用的功能比留一个 404 更糟。请求带 `silent: true`，探测本身不弹 toast。结果写 `sessionStorage`，每会话只探一次；`clearDaemonProbeCache()` 供改后端地址后清。
- `src/nav/index.js`：条目可选 `daemon` 字段，`visibleNavGroups(user, daemon)` 按角色 **且** 按命名空间可用性过滤。`/workflows` → `workflow`，`/marketplace` → `marketplace`。
- `src/views/Layout.vue`：`onMounted` 里探测，结果灌进 `daemonCaps`。`navGroups` 依赖它，所以 `visibleMenuItems` 变更会自动重跑 `prefetchViewsIdle`——探测本身不碰侧栏。未就绪前 `daemonCaps` 为空，侧栏失败放行。
- **`/proxies` 故意不隐藏**：它的订阅半区 `/api/proxy-subscriptions` 在单体存在，出站半区 `/api/proxy-egress` 由 `useProxies.js:112` 自己降级。这是一个混合项，整项隐藏会把能用的订阅管理一起藏掉。

残留（已登记，未做）：深链到被隐藏的页面**仍会加载**，由页面自身的错误态报告 404，而不是被守卫重定向。守卫不重复检查探测结果，因为被重定向的用户会失去自己已经打进地址栏的路径。

`nav.wiring.test.js` 增加 4 条断言钉住这套约定：角色闸门独立于探测状态；只在 `false` 时隐藏；混合项保留；`daemon` 标记恰好是那两个条目。

### 8.2 单一真源：新增一个页面只改一处

Phase 2 的出口标准是「新增一个页面只改一处（`NAV`）」。原来路由表里有 25 个手写 `meta: { requiresAdmin: true }`，加一页要同时改 NAV 和路由表两处。

现在 `router/index.js` 从 NAV 派生 `requiresAdmin`：NAV 管理组（`requiredRole >= ROLE.ADMIN`）的路径 + `EXTRA_ADMIN_PATHS`，再用前缀规则覆盖它们下面的详情页（eval 的 tasks/runs 钻取、`/admin/channel-apis/:id`）。手写标记一个不留，`EXTRA_ADMIN_PATHS` 只剩 `['/agents', '/traffic']` 两条——它们是详情页而非侧栏条目，NAV 不该列它们；它们和 NAV 是**仅有的两个**决定管理员访问的地方。

改完不是「等价性靠眼观」：`.zcode/tmp/p22compare.js` 把剥离前的路由表（`router-index.bak.js`）和派生结果逐条比对，**25 条对 25 条，零放宽、零收紧**。这一步是把「删掉 25 个安全标记」变成可验证操作的关键——比对不出问题才敢删。

### 8.3 四个状态页与重定向链

- `/401`（`NotAuthenticated.vue`）：匿名访问受保护页的落点。守卫用 `unauthTarget(to)` 把原目标带在 `?redirect=` 里，页面显示「登录成功后会回到 {目标}」，`去登录` 把它传给 `/login?redirect=`。
- `/403`：非管理员访问 `requiresAdmin` 路由。守卫在 `resolveAuthGuard` **之前**先判 `requiresAdmin && !userStore.isAdmin`，所以拿不到 admin 的人先落到 `/403`；`/403` 是 `requiresAuth: false`，不会二次进入 admin 检查。
- `/500`：`router.onError` 的落点，取代「进度条转着、路由空白」。用 `isNavigationFailure(error)` 过滤 abort/cancel/duplicate——否则快速双击一个导航项（被自己的新导航取代）也会掉到 500 页。
- **`/403` 和 `/500` 故意不是 guest 路由**：两者都是这个守卫的重定向目标，若把 guest 判定放进去，非管理员从 `/403` 会被直接弹回首页，错误页根本看不到。`/401` 可以放进 guest 列表，因为没有别的检查重定向到它。
- 重定向目标统一走 `src/utils/safeRedirect.js` 的 `safeRedirectPath`：守卫、`/401` 页、`Login.vue` 三处都过它，堵住开放重定向。控制字符/空白字节先剥掉——浏览器会把 `/\t//evil.com` 归一化成 `//evil.com`，裸的 `startsWith('//')` 拦不住。

### 10.6 三处对设计文档的更正

1. **§5.2 的 `/reset-password` 不建路由。** 文档写「`/forgot-password` 取回问题 → 进 `/reset-password?token=`」，但后端不发任何 token。拆两页只有两条路：要么给 `get-question` 加 token 存储（超出「忘记密码页零后端工作量」的约束），要么把密保问题放进 URL——会泄漏到浏览器历史、代理日志与 `Referer`。两条都不走，改为单页两阶段；`/reset-password` 注册为到 `/forgot-password` 的重定向，让文档里的路径解析而不是 404。取舍写在路由注释里。
