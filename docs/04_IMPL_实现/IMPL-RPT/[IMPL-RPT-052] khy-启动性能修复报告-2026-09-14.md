# khy 启动性能修复报告

> 日期：2026-09-14
> 触发：用户反馈 `khy` 启动太慢（截图停在 `登录 mfplg075` 后长时间无响应）
> 工作树版本：1.1.15
> 结论：定位到 **3 处阻塞启动路径的真凶**，全部修复并实测验证，启动路径解锁点 **1696ms → ~300ms**

---

## 一、症状与诊断路径

截图里 `  登录  mfplg075` 来自 `bin/khy.js:678`（`ensureAuthenticated()` 快速路径：本地会话有效，直接放行）。
这行之后还剩 `setup()` + `require('../src/cli/repl')` + `import('ink')` + 首帧渲染——用户感知的"卡住"就在这里。

诊断用了 4 个手段（可复用）：

| 手段 | 用途 |
|---|---|
| `STARTUP_PROFILE=1` + `startupProfiler` 检查点 | 拿到阶段时间线。注意 `process.exit()` 会跳过 `.finally()` 里的 `printSummary()`，需外层 wrapper + `process.on('exit')` 兜住 |
| 包一层 `Module._load` 统计**自耗时**（父减子） | 证明 420+ 模块是"千刀万剐"型，无单点热点 |
| `--cpu-prof` + 自写脚本按 `callFrame` 聚合 self time 并回溯祖先栈 | 抓出 `spawnSync` 475ms 的调用栈 |
| 包一层 `child_process.*Sync` 打印慢派生调用栈 | 定位到 `chcp.com` |

---

## 二、三处真凶

### ① `init.js` 的 DB 体检是"假延后"（~1100ms）

`services/backend/src/bootstrap/init.js` 原为：

```js
_dbHealthInitPromise = Promise.resolve().then(_initDbHealth);
```

注释写着"后台跑"，但 **微任务会在调用方 `await init()` 的续体之前排空**。`dbHealthService.init()`
内部的 `PRAGMA quick_check` 是 better-sqlite3 同步调用（28MB `sessions.db` 单次 450–850ms），
于是它照样卡在 `init:done → main:start` 之间。

检查点时间线实测（修复前）：

```
 599.4ms    +76.6ms  init:dbHealth:start
 604.2ms     +4.9ms  init:done
1696.1ms  +1091.8ms  main:start     ← 这 1.1s 白等
```

**修复**：改用宏任务定时器，默认延迟 2500ms（`KHY_DB_HEALTH_DEFER_MS` 可调，`0` = 下一个宏任务），
定时器 `unref()`，使一次性命令（`khy status`）仍能立即退出。`KHY_DB_HEALTH_DEFER=0` 保留旧的阻塞语义。

### ② 同一个 28MB 文件被体检了两遍（~500ms）

`dbHealthService._discoverDatabases()` 同时收集：

- `.khy/sessions.db`
- `khy-Trajectory/sessions.db`

但 `khy-Trajectory` 是 `utils/dataHome._ensureVisibleAlias` **每次启动重建的可见别名**
（junction/symlink），实测两者 **同 inode（3377699720646302）、同 realpath** —— 是同一个物理文件。

**修复**：新增 `_dedupeByRealPath()`，按 realpath 去重（Windows 转小写，解析失败退化为字面路径保守保留），
导出供测试。修复后体检清单从 3 条降到 2 条：

```
[DB Health] Starting integrity check for 2 databases {"databases":["sessions.db","taskboard.db"]}
```

### ③ 顶层同步 spawn `chcp.com`（230–475ms）

`services/backend/bin/khy.js:308` 在**模块顶层**执行：

```js
require('child_process').execFileSync(_chcpDirect, ['65001'], { stdio: 'pipe', windowsHide: true });
```

控制台代码页是**控制台属性、进程共享**的，而 Python 启动器 `platform/khy_platform/cli.py:2452`
早已用 `SetConsoleOutputCP(65001)` + `SetConsoleCP(65001)` 设过一遍。这次 `CreateProcess` 纯属重复，
且是同步的，发生在 `main()` 之前。

**修复**：`cli.py` 成功设置后导出 `KHY_CONSOLE_CP=65001` 握手；`khy.js` 见到握手就跳过。
直连 `node bin/khy.js`（前面没有启动器）时保留旧派生，行为逐字节不变。

## 三、实测收益

| 指标 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| `main:start`（启动路径解锁点） | ~1696ms | **~260–330ms** | **−1.4s** |
| `init()` 自身返回耗时 | 1471ms | **127ms** | **−1.34s** |
| `--no-server` 整进程（直接 node） | 2720–3166ms | 1441–1626ms | −1.3s |
| `--no-server` 整进程（启动器路径，含握手） | 2720–3166ms | **1202–1289ms** | **−1.6s** |

净收益约 **1.5–1.9s**。

## 五、仍未解决 / 后续建议

1. **延后体检在 +2.5s 仍会阻塞事件循环约 0.9s**。`better-sqlite3` 是同步的，`quick_check` 无法分片。
   彻底解法是丢到 worker thread / 子进程，但 `dbHealthService.init()` 同时要注册 shutdown hook 与
   6 小时周期 WAL checkpoint，改动面较大，本次未做。可用 `KHY_DB_HEALTH_DEFER_MS` 自行调时机。
2. **剩余大头（未动）**：`require('../src/cli/repl')` 约 1.1–1.6s（420+ 模块，无单点热点）+ `import('ink')`
   约 1.4s。这正是 `docs/03_DESIGN_设计/[DESIGN-PERF-001]` 的**卡点 A**，方案是 esbuild 单文件 bundle。
   > 顺带勘误：该文档 §卡点 C 与附录表把 `KHY_DB_HEALTH_DEFER=1` 记为"已后台跑，不阻塞"——
   > 实测并非如此，本次才真正修好。
3. **`NODE_COMPILE_CACHE` 实测无稳定收益**（冷启 27s 填充、热启在噪声区间内），且 `khy.js:51-55`
   已因开发期陈旧字节码问题主动禁用，不建议重新启用。
4. **环境债（与本次改动无关，但拖慢每次启动）**：`khy_os.egg-info/PKG-INFO` 与已安装元数据停在
   **1.1.11**，源码树是 **1.1.15**。后果：`khy --version` 报错版本；每次启动 `_check_version_upgrade`
   都判定"版本升级"→ 打印「token 缓存将强制刷新」。建议刷新 editable 安装元数据
   （`pip install -e .` 或清掉陈旧的 `khy_os.egg-info`）。
5. 未写 CHANGELOG：该仓库 CHANGELOG 最新只到 1.1.14（版本已是 1.1.15），形态上是发布时统一写，
   避免与待发布条目冲突，留给发布流程处理。
