[IMPL-RPT-047] 六道治理债清理与密钥轮换 — 实施记录#

日期：2026-09-08
范围：CI 门禁真空与路由白名单（前端）、6 个 error 级真 bug、check:layout 5 项预存 error、后端 jest 基线归因、渠道 API Key 密钥轮换
上游任务：IMPL-RPT-046（渠道 API 文档板块）收尾时提出的 6 项建议后续
一句话结论：6 项里 5 项已落地并有可复现的验证数据；第 6 项（密钥轮换）已实现完整机制，但轮换本身尚未在生产执行，且 jest 基线的真正阻塞项（被删源码）超出本轮可做范围。

一、设计要点#

1. 门禁要能「只减不增」，而不是「全绿」#

前端 lint 存量是 1690 个 warning（其中 1661 个是 vue/attributes-order 纯格式项）。
一次性 --fix 能清掉，但会在约 50 个文件的模板里重排属性，产生一个巨大的无关 diff。
因此沿用仓库既有的基线预算模式：error 硬 0，warning 记录实测值并只允许下降。
这样门禁立刻生效（新增 error 立即失败），而格式债被显式登记、不阻塞功能改动。

2. 判定逻辑必须可脱离框架单测#

detectRouterBase() 的旧实现靠 IN_APP_ADMIN_SEGMENTS 白名单排除站内 /admin/* 页面。
每加一个站内页就要补一段白名单，漏补就整站 404 且无报错。
把「已注册路由优先匹配」抽成无依赖的纯函数（src/router/adminBase.js），
routes 只在调用点注入，于是能用 node --test 直接测，不需要 Vue / vue-router / 浏览器。

3. 密钥轮换的正确形态是「密钥环 + 增量重包」，不是「换一把锁」#

换 env 会让旧 KEK 包封的 DEK 永久解不开，等于静默丢 Key。
单纯的双层 envelope 并不解决这个问题——DEK 还是被同一个 KEK 包着的。
真正解开的两点：

  • 密钥环：主 KEK + 退役 KEK 有序列表，解密按序尝试。轮换过渡期新旧密文都读得通，

老数据不需要迁移即可上线。

  • DEK 按记录独立：正是为了让「重包」可以一条记录一条地做，而不是停机全库重加密。

两者缺一不可：只有环则永远清不掉退役 KEK；只有 envelope 则换 env 照样丢数据。

4. 迁移留下的兼容性缺口要如实报告，不能靠测试侧硬改#

src/services/domain/** 迁移把 139 个服务目录清空成只剩 barrel index.js。
barrel 只做了属性级兼容，深路径全断。测试侧 556 处深导入中招。
其中 372 处能从 barrel 的 exports.x = require('<新路径>') 反推正确目标并机械改写；
另 193 处指向全树不存在的模块（barrel 是空壳、basename 检索无命中）——
这些源文件被删除且未迁移，改测试无用，必须先恢复源码。

文件动作

实现中的一个真 bug 是自查发现的：DEK 是 32 字节随机二进制，不是合法 UTF-8，
若经 utf8 字符串搬运会被替换字符破坏字节——解包「成功」却拿到错误的 DEK。
已改为 _gcmOpenBuf() 返回 Buffer，DEK 走二进制路径，明文走字符串路径。
