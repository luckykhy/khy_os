# 长任务提示词库（给人看）

> **这份文件解决什么问题**：khy-os 内置了一整套长任务可靠性基础设施（断点、空闲超时、错误分类、熔断、Receipt）。
> 但 AI 默认不知道这些东西存在——它会自己发明一套「我记一下进度」「我再试三次」的土办法，
> 和底层机制各干各的，最后两边都不可靠。
>
> 下面每条提示词的作用是**把 AI 接到既有机制上**，而不是让它另起炉灶。
> 所有数字、环境变量、命令都已对照源码核实（核实清单见文末）。

---

## 零、先认清你手上有什么

粘提示词之前，先知道这些机制客观存在、且 AI 用得上：

| 机制 | 在哪 | AI 该怎么用 |
|------|------|-------------|
| **Boulder 断点** | `services/backend/src/services/boulderState.js` | 长任务自动存档；`khy resume tasks` 看，`khy resume <taskId>` 续 |
| **Watchdog 空闲滑动超时** | `services/backend/src/services/resourceGuard.js` | 有进度就 `.touch()` 续命，不是硬砍（AGENTS.md 规则 3） |
| **错误分类引擎** | `services/backend/src/services/retryWithBackoff.js` | `classifyError(err)` 先定性，再决定重试还是收手 |
| **差异化重试表** | 同上，`ERROR_KIND_STRATEGIES` | 8 类错误 8 套退避参数，不是统一「重试 3 次」 |
| **熔断与冷却** | `services/backend/src/services/circuitBreaker.js` | 连续失败 5 次开断路，30s 后放 1 个探针 |
| **死循环检测** | `services/backend/src/services/toolLoopDetector.js` | 同签名无进展 3 次警告 / 5 次判定卡死 |
| **可靠性协议七大约束** | `docs/03_DESIGN_设计/RELIABILITY-PROTOCOL.md` | 收尾自查的硬标准 |
| **8 个现成 skill** | `docs/_AI协作预设包/skills/` | 已经沉淀好的流程，别重复造 |

## 一、长任务启动

### 1. 大任务开工（带断点意识）

**何时用**：预计要跑几十分钟以上、会连续调很多工具的任务。开工第一条消息就粘。

```
接下来是一个长任务，可能中途被打断（Ctrl+C / 会话超时 / 我关掉终端）。

khy-os 有 Boulder 断点机制（services/backend/src/services/boulderState.js），
agenticHarness 会按轮自动存档到 SQLite，默认保留 24 小时。你不需要自己发明进度文件。
你要做的是配合它：

1. 开工前先跑 `khy resume tasks`，确认没有同目录的未完成检查点。
   有的话先问我是续跑还是丢弃，不要直接开新的。
2. 把任务拆成「每步都能独立验证」的粒度。断点存的是对话状态，
   不是你脑子里的计划——一步做完就要有可观察的产物（文件改了 / 测试过了 / 命令输出了）。
3. 每完成一步，明确说清楚：改了哪个文件、验证方式是什么、下一步做什么。
   这句话会进检查点，是将来你自己续跑时唯一的线索。
4. 不要把「读了一堆文件在心里建了个模型」当成一步。断点恢复不回来那个模型。

任务是：<在这里写具体任务>
```

**它挂在哪**：`agenticHarnessService.js` 的 `onCheckpoint` 回调 → `saveBoulderState(cwd, state)`。
检查点带 512KB 硬上限，超了会截断——所以「产物要可观察」不是风格建议，是存储约束。

### 2. 无人值守模式启动

**何时用**：过夜跑、CI 里跑、你人不在旁边。

```
这次是无人值守运行，我不在旁边，中途不会有人回答你的提问。

先做三件事，做完再开工：

1. 确认持久重试已开：环境变量 KHY_UNATTENDED_RETRY=true。
   注意它的作用域很窄——只对 429 / 529 / overloaded_error 生效，
   单次退避封顶 5 分钟、总时长硬上限 6 小时、每 30 秒打一次心跳。
   认证失败、上下文超长、代码报错都不在它管辖内，那些必须直接停。

2. 确认自动应答的状态：KHY_UNATTENDED_AUTOANSWER 默认是关的。
   如果我没显式打开，你遇到需要我确认的岔路口就必须停下并写清楚卡在哪，
   不许自己替我选。如果它开着，KHY_UNATTENDED_AUTOANSWER_INTENT_GUARD
   （默认开）会做意图匹配；这个 guard 一旦被关掉就会退化成盲选第 0 项——
   发现是这个组合，直接告诉我配置有问题，不要开跑。

3. 设好边界：KHY_TOKEN_BUDGET（预算）、KHY_TOOL_LOOP_ABSOLUTE_TIMEOUT_MS（绝对时限）。
   没设的话按我给的时间窗自己收敛，宁可做完一半交付得清清楚楚，
   也不要在最后一步崩掉、什么都没留下。

运行期间的纪律：
- 每完成一个可验证的步骤就存一次档（让 harness 存，别自己写进度文件）。
- 任何失败先跑 classifyError 定性，不可重试的类别立刻停，不要空转。
- 结束时无论成败都要给完整交接：做完了什么、没做什么、卡在哪、下一步谁该做什么。

参考 docs/07_OPS_运维/[OPS-MAN-072] 目标连续多日运行不中断的底气自检.md 的自检项。

任务是：<在这里写具体任务>
```

**它挂在哪**：`isPersistentRetryEnabled()` 读 `KHY_UNATTENDED_RETRY`，只认 `'true'` / `'1'`。
`PERSISTENT_MAX_BACKOFF_MS = 5min`、`PERSISTENT_ABSOLUTE_CAP_MS = 6h`、`HEARTBEAT_INTERVAL_MS = 30s` 三个常量都在 `retryWithBackoff.js` 顶部。

> ⚠️ 这条提示词里关于 `KHY_UNATTENDED_AUTOANSWER_INTENT_GUARD` 的警告不是虚构的：
> guard 关掉后确实退化为按索引 0 盲选。这是个「默认安全、但可以手动作死」的开关，值得让 AI 替你盯着。

## 二、维持与续跑

### 3. 从断点恢复

**何时用**：昨天的任务被打断了，今天回来接着做。

```
上次的任务被打断了，现在续跑。

按这个顺序来，不要跳步：

1. 跑 `khy resume tasks` 列出可恢复的检查点。
   输出里有 taskId、状态（in_progress / interrupted）、已跑轮数、多久以前。
   挑对那个——同一个目录可能有多个。

2. `khy resume <taskId>` 恢复。恢复时 boulderState 会做文件系统漂移检测，
   如果打印了「⚠ Workspace drift detected」，**先停下来读完这行再动手**：
   它说明检查点存档之后工作区变过（文件被改、有新提交）。
   你上次的判断可能已经过期了，必须重新确认再继续，不能直接接着写。

3. 检查点默认只留 24 小时（KHY_BOULDER_TTL_HOURS 可调）。
   如果 `resume tasks` 是空的，说明已经过期清掉了——那就别猜上次做到哪，
   直接从工作区现状重建认知：git status / git diff / 跑一遍测试，
   用事实说话，而不是"我记得上次好像……"。

4. 恢复后第一件事是**汇报你的理解**：上次做到哪、当前工作区是什么状态、
   接下来第一步是什么。等我确认了再动手改文件。
```

**它挂在哪**：`router.js` 的 `resume` 分支 → `boulder.listResumableTasks()` / `boulder.rearmForResume(token)`。
漂移检测是 `diffFilesystemSnapshot()`，会检查文件哈希与新增提交。

### 4. 防卡死自检（循环检测）

**何时用**：感觉 AI 在原地打转，或者预防性地在长任务中期插一条。

```
停一下，做一次卡死自检。

khy-os 有 toolLoopDetector，判定标准是客观的，你照着自查：
- 同一个 (工具, 参数, 结果哈希) 连续出现 3 次 → 警告级，说明你在无进展重复
- 连续 5 次 → 判定为卡死，会被斩断

现在回答我四个问题，用事实回答，不要用感觉：
1. 你最近 5 次工具调用分别是什么？其中有几次的参数几乎相同？
2. 这些调用产生的输出，和上一次比有变化吗？没变化就是无进展。
3. 你现在这一步的**验收标准**是什么？说得出来吗？说不出来就是没目标在乱试。
4. 距离上一次「工作区真的发生了变化」（文件被改 / 测试状态变了）过了几步？

如果自查下来确实在打转，不许再试同样的方法。选一条：
(a) 换一条完全不同的路径（换工具、换切入点、换假设）
(b) 把当前的死结、你试过什么、为什么不通，写清楚交给我

明确说明你选了哪条以及为什么。「我再试一次」不是选项。
```

**它挂在哪**：`toolLoopDetector.js` 的 `DEFAULT_CONFIG`：`noProgressWarning: 3`、`noProgressCritical: 5`。
另有 `KHY_TOOL_CIRCUIT_BREAKER_THRESHOLD` / `KHY_TOOL_STAGNATION_THRESHOLD` 两组可调阈值。

### 5. 进度透明（规则 2 合规）

**何时用**：AI 只说「正在处理」不说到哪了。也适合开工时预先约定。

```
从现在开始，你的每条进度汇报都必须满足 AGENTS.md 强制规则 2：
「动作 + 目标 + 进度」三要素齐全，缺一不可。

规则 2 认可的进度信号只有这些形式：
  n/m、百分比、「第 n 次」、attempt/retry、:端口、主机/端口、
  字节数（bytes/kb/mb/gb）、节点数/记录数/条目数

反例（都不合规，别写）：
  ✗「正在处理...」          —— 三要素全缺
  ✗「正在扫描文件」          —— 有动作有目标，没进度
  ✗「快好了」               —— 什么都没有

正例：
  ✓「扫描依赖 services/backend/src 42/180 个文件」
  ✓「重试 API 调用 第 2 次，退避 4s」
  ✓「慢请求 POST /api/backtest 耗时 8.2s，超阈值 3.0s，今日第 4 次」

超过 30 秒没有输出的操作，必须先说清楚你在等什么、预计多久。
沉默是最贵的——我无法区分"在跑"和"卡死了"。
```

**它挂在哪**：`scripts/ci/check-agent-rules.js --changed` 在 CI 里强制校验规则 2。
这条提示词让 AI 的口头汇报和 CI 的代码检查用同一把尺子。

## 三、错误诊断与恢复

### 6. 错误分类先行

**何时用**：一出错就粘。这是最该常备的一条。

```
报错了。**先分类，再动手**——不要凭直觉猜。

khy-os 的 classifyError()（services/backend/src/services/retryWithBackoff.js）
是 11 级优先级管线，覆盖 17 种 FailoverReason，优先级从高到低：

  billing → auth → rate_limit → overloaded → context_overflow → model_not_found
  → thinking_signature → timeout → network → server_error → provider_policy
  → （兜底 unknown）

分类之后按这张表决定怎么办，**不要自己拍脑袋定重试次数**：

| 类别 | 最大尝试 | 退避区间 | 抖动 | 特殊动作 |
|------|---------|---------|------|---------|
| rate_limit | 5 | 30s–120s | 0.5 | 优先读 Retry-After |
| overloaded | 3 | 2s–30s | 1.0 | 最后一次触发模型 fallback |
| network | 3 | 1s–15s | 0.8 | |
| server_error | 2 | 1s–10s | 0.8 | |
| timeout | 2 | 500ms–3s | 0.3 | |
| unknown | 2 | 1s–10s | 0.5 | |
| **context_length** | **1（不重试）** | — | — | 触发 compact 压缩上下文 |
| **auth** | **1（不重试）** | — | — | 需要换凭据，重试无意义 |

最后两类是重点：**重试它们是纯浪费**。上下文超长要压缩，认证失败要换 key，
重试一百次也不会变好。

ClassifiedError 还会给出 recoveryHints，是固定的令牌，按序执行：
  compress_context / rotate_credential / fallback_model / wait_<n>ms / retry_with_backoff

现在告诉我：
1. 分类结果是什么（哪一类、依据是状态码还是消息匹配）
2. 对应策略是什么（几次、什么退避）
3. recoveryHints 给了什么
4. 你打算怎么做

报错内容：<粘报错>
```

**它挂在哪**：`ERROR_KIND_STRATEGIES` 表逐行核实自源码。
注意 `classifyError()` 的 JSDoc 里写的是「8 阶段」——那是过期注释，函数体实际标到 Stage 11。以函数体为准。

### 7. 系统性故障排查

**何时用**：反复失败、不是单点错误、怀疑是环境或架构问题。

```
这个问题反复出现，不是单次偶发。按 khy-os 的五类分诊法定位，
别一头扎进代码里 debug。

分类（见 docs/_AI协作预设包/给AI看/错误自查手册.md，也就是 /khy-troubleshoot skill）：
  P 类 —— 流程问题（步骤做漏了、顺序错了、前置条件没满足）
  W 类 —— 小模型能力问题（模型没读懂、幻觉、指令跟随失败）
  B 类 —— 代码缺陷原型（真的是 bug）
  G 类 —— 网关问题（provider、限流、模型不可用）
  E 类 —— 环境问题（依赖、版本、路径、权限、Windows 特有）

排查纪律：
1. 先看证据再提假设。可用的证据源：
   - `khy doctor` —— 环境诊断
   - `.khy/receipts/<sessionId>/RCPT-*.json` —— 完整工具调用轨迹
   - eventLog / audit.jsonl —— 事件与审计
   - `/monitor slow` —— 慢请求排行（需 KHY_SLOW_REQUEST_ENABLED=1）
2. 一次只改一个变量。同时改两处，你就永远不知道是哪处起的作用。
3. 每个假设都要说清楚**怎么证伪**。证伪不了的假设不叫假设，叫猜测。
4. 排除掉的假设要留记录，不要绕回来重试同一条。

先给我：分类 + 三条最可能的假设 + 每条的验证方法。
不要在我确认之前开始改代码。
```

**它挂在哪**：`/khy-troubleshoot` skill（别名 `/khy-debug`、`/排错`）已经封装了这套分诊法。
如果 skill 已安装，直接敲 `/排错` 比粘这段更省事——这段是给没装 skill 的场景兜底的。

### 8. 失败后的诚实收尾

**何时用**：任务没做完、部分失败、或者你要终止它。这条最重要，也最容易被跳过。

```
这次任务没有完全成功。现在做诚实收尾——不许粉饰，不许含糊。

按 RELIABILITY-PROTOCOL 的七大约束逐条对照
（docs/03_DESIGN_设计/RELIABILITY-PROTOCOL.md §1.2）：

  1. 永不静默失败 —— 每个失败都有可审计痕迹了吗（日志/receipt/audit）？
  2. 终态必达   —— 任务落到终态了吗？有没有卡在 running？
  3. 超时必设   —— 阻塞操作都有超时保护吗？
  4. 中断必响   —— 我按的 ESC 传播到实际执行点了吗？
  5. 轨迹必全   —— Receipt 从 start 到 finalize 闭合了吗？
  6. 幂等必保   —— 重试操作带幂等 Key 了吗？
  7. 资源必释   —— Watchdog / timer / interval 都清理了吗？

然后给我一份交接，四段，一段都不能少：

【做完了什么】—— 具体到文件和验证方式。「改好了」不算，
                「改了 X 文件，跑了 Y 测试，Z 个通过」才算。
【没做完什么】—— 明确列出。不要用"基本完成""大体上"糊过去。
【为什么失败】—— 用第 6 条的分类结果说话，不是"可能是环境问题"。
【下一步建议】—— 具体到谁该做什么、从哪个文件开始、需要什么前置条件。

特别强调：
- 没验证过的改动，明说"未验证"。不要写"应该可以"。
- 跑失败的测试，把失败输出贴出来，不要只说"有几个测试失败"。
- 猜测和事实分开写。分不清的，标"待确认"。
```

**它挂在哪**：七大约束逐字取自 `RELIABILITY-PROTOCOL.md` 的 §1.2 表格。
`/khy-honest-closure` skill（别名 `/khy-closure`、`/收尾`）是这条的成品版。

### 9. 重试纪律（防失控）

**何时用**：AI 已经开始「再试一次」循环了，或者预防性地在启动时约定。

```
重试纪律，从现在起严格执行：

**硬性上限**（不是建议，是上限）：
- 同一个操作，同样的参数，最多 3 次。第 3 次还失败就必须换路子或者停。
- 三次之间必须有指数退避，不许连着打。
- 每次重试前必须说明：这次和上次**改了什么**。什么都没改的重试是纯浪费。

**熔断意识**：
khy-os 的 circuitBreaker 是三态的（closed / open / half_open）：
  连续失败 5 次 → 开断路，之后所有请求直接快速失败，不再打服务
  30 秒后 → 放 1 个探针请求试水
  探针连续成功 2 次 → 才恢复 closed

你的行为要和它同构：连着失败就该停下来判断，而不是加大火力。
断路器开着的时候还硬重试，是在给一个已知故障的服务继续施压。

**不可重试的类别，一次都不许重试**：
  auth（认证失败——换凭据前重试无意义）
  context_length（上下文超长——要压缩，不是重试）
  billing（账单/配额——重试改变不了余额）
  model_not_found（模型不存在——要 fallback）
  provider_policy_blocked（策略拦截——重试只会再被拦一次）

**汇报格式**（规则 2）：
  ✓「重试 API 调用 第 2/3 次，退避 4s，本次改动：换用 fallback 模型」
  ✗「再试一次」

三次用尽还没成，走第 8 条的诚实收尾，不要静默放弃、也不要无限循环。
```

**它挂在哪**：`circuitBreaker.js` 的 `DEFAULT_OPTS`：`failureThreshold: 5`、`resetTimeoutMs: 30000`、`halfOpenMaxProbes: 1`、`successThreshold: 2`。
不可重试类别取自 `classifyError()` 中 `retryable: false` 的分支。

## 四、组合用法

| 场景 | 组合 | 说明 |
|------|------|------|
| **日常长任务** | 1 → 5 → 6 | 开工时粘 1+5，出错时补 6 |
| **过夜 / CI 无人值守** | 2 + 9 | 配 `KHY_UNATTENDED_RETRY=true`；9 必须一起给，否则持久重试会变成无限重试 |
| **中断后回来** | 3 | 疑似卡死过，加 4 |
| **反复失败** | 7 → 3 → 8 | 先定位，再从断点重来，还不行就诚实收尾 |
| **交给弱模型跑** | 5 + 9 + `/khy-weak-model-guardrails` | 弱模型最容易死在「不报进度」和「无限重试」这两点上 |

**一条经验**：第 8 条（诚实收尾）不要等失败了才粘。开工时就说清楚「失败了要按这个格式交接」，
AI 才会在过程中留下够用的痕迹。事后补，很多信息已经丢了。

## 五、沉淀为 skill

上面某条你反复在用，就把它做成 skill，以后一个斜杠命令搞定。

**目录结构**（放 `~/.khy/skills/<name>/` 用户级，或 `<项目>/.khy/skills/<name>/` 项目级）：

```
~/.khy/skills/khy-long-task/
├── manifest.json
└── prompt.md
```

**manifest.json**（字段照抄 `khy-troubleshoot` 的真实结构）：

```json
{
  "name": "khy-long-task",
  "description": "长任务开工协议：接上 Boulder 断点、规则 2 进度汇报、重试纪律。开始预计超过 30 分钟的连续任务时激活。",
  "user_invocable": true,
  "trigger": "/khy-long-task",
  "aliases": ["/长任务", "/开工"],
  "category": "khy-guidance",
  "tags": ["khy-os", "long-task", "checkpoint", "reliability"],
  "platforms": ["khy-os"],
  "when_to_use": "开始预计超过 30 分钟、会连续调用大量工具、可能中途被打断的任务时。",
  "context": "inline"
}
```

`prompt.md` 就是上面对应那条提示词的正文。

**安装**：

```bash
node services/backend/bin/khy.js skill import ~/.khy/skills/khy-long-task
# 或者直接把目录放进 ~/.khy/skills/，重启后自动加载
```

**可以直接抄的现成样板**（都在 `docs/_AI协作预设包/skills/`）：

| skill | 学它什么 |
|-------|---------|
| `khy-weak-model-guardrails` | 怎么写「约束型」提示词——给硬性上限而不是建议 |
| `khy-troubleshoot` | 怎么写「分诊型」提示词——先分类后动手 |
| `khy-honest-closure` | 怎么写「收尾型」提示词——固定四段式交接 |
