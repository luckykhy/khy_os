## 一、结论摘要

| 指标 | 数值 |
|------|------|
| 磁盘总占用 | **7.89 GB**（8,080 MB，含目录链接重复计数） |
| git 真实跟踪内容 | **≈ 96 MB**（8,752 个文件，占 1.2%） |
| 与源码无关的占用 | **98.8%** |
| 可回收空间 | **≈ 6.0 GB**，瘦身后约 1.9 GB |

**核心结论：这不是「代码仓库太大」的问题。** git 真正跟踪的源码与文档合计仅约 96 MB，7.88 GB 中的 98.8% 是**从未进入版本库的本地产物**——构建输出、依赖目录、git 历史副本、运行时临时数据。瘦身几乎不触碰任何源码或文档，风险极低、收益极高。

**附带隐患：** 当前 `git status` 有 **2,476 条**待处理条目，其中 `.research-tmp/`、`apps/khy-mobile/release/`、`apps/khy-os-client-app/release/`、`_产物/`、`.opencode/`、`.zcode/` **未被 `.gitignore` 覆盖**。这与 `.gitignore` 注释中记载的历史事故（`tools/deepseek-eyes`、`platform/packages/shared/logs` 导致双机同步 `--clean-only` 门禁无法触发）属于**同一类故障**。

## 三、根因定位

### 根因 1｜Flutter/Android 构建产物长期未清理 —— 3.78 GB，占 47.9%

单一目录 `apps/khy-os-client-app/build/` 占 **2.83 GB**，是最大空间黑洞。冗余度高：Gradle 为 `arm64-v8a`、`x86_64`、`armeabi-v7a` 三个 ABI 各存一份 `libflutter.so`（377 + 372 + 333 MB）；同一份 `kernel_blob.bin`（67 MB）在 `intermediates/flutter/`、`intermediates/assets/` 与 `.dart_tool/` 存在 **3 份副本**；`app-debug.apk`（179 MB）在 `apk/` 与 `flutter-apk/` 下各一份。全部可再生，积累原因是 debug 与 release 产物并存且从未执行 `flutter clean`。

### 根因 2｜git 对象库含大量不可达对象与松散对象 —— 可回收约 670 MB

| 成分 | 体积 | 诊断 |
|------|------|------|
| pack 文件 | 617 MB | 内含 **1,830 个不可达对象**；5 个最大对象（177.7 / 103.9 / 37 / 19.3 / 10 MB，合计 **348 MB**）经 `git log --all --find-object` 验证**不被任何可达提交引用** |
| 松散对象 | 280 MB | 2,001 个对象散落未打包，无法享受 delta 压缩 |
| garbage | 24 MB | `git count-objects` 已明确报出 `size-garbage: 24.07 MiB` |

另有 `.git-backup-20260913/`（720 MB）已被 `.gitignore` 正确忽略，但仍占工作区磁盘。两份历史合计 1.64 GB，占 20.3%。

### 根因 3｜两套 Electron 运行时并存 —— 冗余 266 MB

`node_modules/.pnpm/` 下同时存在 `electron@44.2.0`（369 MB）与 `electron@32.3.3`（266 MB），各携带完整 `electron.exe`（235 / 178 MB）。大版本跨度如此之大，通常意味着旧版本已无引用方。

### 根因 4｜产物归档散落于仓库内且未被忽略 —— 约 855 MB

`apps/khy-mobile/release/`（489 MB）、`apps/khy-os-client-app/release/`（57 MB）、`.research-tmp/repos/`（280 MB）、`.zcode/tmp/`（28 MB）等**既不在 `.gitignore` 覆盖内，也不是仓库交付物**。

### 根因 5｜目录链接造成重复计数 —— 246 MB

`khy-Trajectory/` 是指向 `.khy/` 的 NTFS junction（`LinkType=Junction`）。并非两份数据，但按目录递归统计（含本次测量）会计两次。`.gitignore` 中已有两条相关规则，说明它本就不该存在于工作区。

## 四、瘦身方案

### 第一档｜立即执行（零风险，回收 ≈ 4.3 GB）

```bash
# 1) Flutter / Android 构建产物        → -2,893 MB
cd apps/khy-os-client-app && flutter clean

# 2) Dart 工具缓存                     → -190 MB
rm -rf apps/khy-os-client-app/.dart_tool

# 3) APK 归档（12 个历史 debug 版本）   → -489 MB
rm -rf apps/khy-mobile/release/*.apk

# 4) release APK 副本                  → -57 MB
rm -rf apps/khy-os-client-app/release

# 5) 后端 / 桌面端打包产物              → -128 MB / -107 MB
rm -rf services/backend/dist  apps/khyos-desktop/dist-electron

# 6) 运行时临时数据                     → -162 MB
rm -rf .khy/tmp/quarantine-*  .zcode/tmp

# 7) 重复的目录链接（确认后）            → -246 MB
rm -rf khy-Trajectory
```

**重建成本：** `flutter pub get`（约 1 分钟）、`flutter build apk --debug`（约 10–20 分钟）、`npm run build`（约 1 分钟）、桌面端重新打包。

### 第二档｜短期治理（低风险，回收 ≈ 1.65 GB）

**2.1 git 对象库回收 —— 约 670 MB**

```bash
git count-objects -vH
git fsck --unreachable --no-progress | wc -l

git reflog expire --expire=now --all
git gc --prune=now --aggressive
```

> ⚠️ `--prune=now` 会**永久删除**不可达对象。执行前确认：无依赖 reflog 恢复近期的需求；`.git-backup-20260913/` 保持原状直到 `git gc` 验证通过（`git log`、`git fsck`、切分支均正常）——它此刻正是唯一的历史兜底。

**2.2 历史副本外迁 —— 720 MB**

在 2.1 验证通过后，将 `.git-backup-20260913/` **移出仓库**（外部盘或对象存储归档），而非直接删除。

**2.3 调研克隆清理 —— 280 MB**

`.research-tmp/repos/` 是一次性调研资产。结论已沉淀进 `docs/` 则可直接删除；需保留时建议压缩为单文件（预计 60–80 MB）。

### 第三档｜结构性优化（防复发）

**3.1 补齐 `.gitignore` —— 消除 2,476 条状态噪音**

```gitignore
# 调研 / 归档产物
/.research-tmp/
/_产物/
/tmp-cmp/

# 移动端与客户端 APK 归档
*.apk
*.aab
/apps/khy-mobile/release/
/apps/khy-os-client-app/release/

# 本机 IDE / 工具临时状态
/.opencode/
/.zcode/
/.zcode-tmp/
```

> 这条比省空间更重要：仓库 `AGENTS.md` 的双机流水线依赖 `sync.py --status` 与 `--clean-only` 门禁，而门禁**要求工作树收敛到干净状态**。`.gitignore` 里已有两段注释专门记录这类事故，正是它们导致「工作树永远带未跟踪文件 → 门禁永远跳过 → 任务循环无法闭合」。2,476 条未忽略条目属于**完全相同**的故障模式。

**3.2 Electron 双版本去重 —— 266 MB**

```bash
rg -n "electron.*32\." package.json apps/*/package.json services/*/package.json
pnpm install --force
pnpm store prune
```

**3.3 建立体积守卫**

- 在 `scripts/ci/` 新增体积守卫，纳入现有 `ruleguard` 绑定层与 `check:wiring` 反孤儿检查，登记为 `PROCESS` 域规则（如「工作区非跟踪体积 > 2 GB 判 error」）。
- 把第一档清理收敛为可重复动作。仓库**已有** `npm run clean`（干跑）与 `npm run clean:apply`（真删，白名单 + `PROTECTED_SUBTREE` 保护，见 `scripts/maintenance/clean.js`），且**已覆盖** Flutter `build/` 与 `.dart_tool`——**无需新增脚本**。只需把本轮新增的两类补进该脚本的 `TARGETS`：`apps/khy-mobile/release/*.apk`（保留最新一份）与 `services/backend/dist/*.map`。
- Flutter 固定只构建目标 ABI：`flutter build apk --target-platform android-arm64`，可让 `build/` 直接降到约三分之一（三个 ABI 的 `libflutter.so` 合计 **694 MB**，通常只需 `arm64-v8a`）。

### 7.2 方案修正（4 处）

**① `services/backend/dist` 不能整删 —— 正文第一档第 5 步有误。**
`services/backend/esbuild.config.js` 明文写着 `dist/cli.cjs` 是**生产启动路径**（`invoke as node dist/cli.cjs`）。它**不是**纯粹的构建产物。正确做法是**只删 `*.map`**（101.5 MB 的纯调试辅助），保留 `cli.cjs` / `khy.cjs` / `khy.mjs` / `meta.json`（26.3 MB）。已按此执行，`node --check` 三个入口全部 exit 0。

**② `apps/khy-os-client-app/release/` 应保留 —— 正文第一档第 4 步方向反了。**
其中 `khy-os-client-20260915-2206.apk`（57 MB）是**唯一的 release 正式包**。它与 `build/app/outputs/apk/release/app-release.apk` 确实是同名的双份，但 `flutter clean` 会删掉 build 里那份——**删这个就等于两个都不剩**。正确取舍是保留「有版本号的那份」。已保留。

**③ `.khy/tmp/quarantine-*` 不得删除 —— 正文第一档第 6 步违反仓库红线。**
`[DESIGN-LAY-003] 仓库整理与巡检规范` HK-3 规定「**只隔离不删除**」，同规范 §3 风险分级把 L3 删除定为「**永不执行，一律人工确认**」。隔离区的存在意义就是「等人工确认」，清理它等于绕过该机制。**已保留，未动。**

**④ `khy-Trajectory` junction 不值得删 —— 正文第一档第 7 步的收益是虚假的。**
它是 NTFS reparse point，**本身几乎不占磁盘**；统计里的 246 MB 是按目标目录递归算出来的**重复计数**，删除链接**不释放任何真实空间**，却可能弄坏写轨迹的路径。**已保留。** 连带地，正文「可回收 ≈ 4.3 GB」这个数字偏高——其中含 246 MB 虚假重复计数与 132 MB 不该删的隔离区，**实际可回收约 3.6 GB**。

### 7.3 执行中遇到的两个环境约束

- **宿主批量删除安全门**：一次删除超过 **50 个文件/轮次**会被整体拒绝（`SAFE_DELETE_BULK_CONFIRM_REQUIRED`），`npm run clean:apply` 因此报「0/5 项已删」（**无半删状态**）。此门属于安全控制，须经人工确认后方可继续，不应以底层 API 静默绕过。
- **Windows 超长路径**：`build/` 内有 Android 生成的 100+ 字符 lambda 类名文件，普通递归删除会因超过 `MAX_PATH` 失败。解法是加 `\\?\` 扩展长度前缀。

## 九、防复发：把官方命令补齐并堵住误删（2026-09-16 20:xx 追加）

清理只是止血；这一节做的是**让它不再长回来**，并修补一处清理机制自身的缺陷。

### 9.1 `khy cleanup` 从「幻影命令」变为可用

**问题**：`diskClean.js` 与 `aliases.js` 的注释都把 `khy cleanup` 当作已存在的命令引述（「khy 自身数据保留：日志/快照/会话」），但实测：

- `handlers/` 下没有 `cleanup.js`
- `router.js` 里没有任何 `cleanup` 分派
- `aliases.js` 里只在**注释**中提到它，**没有别名条目**

即敲 `khy cleanup` 会落到未知命令。而 `cleanupService.js` 其实**早已实现** 20+ 个保留函数（日志轮转、快照、训练数据、遥测、审计轨迹、隔离区、会话 7 天、轨迹 30 天、任务输出 24h、检查点 500 MB 封顶），只是**一个入口都没有**——典型的「文档说有、实现没有」。

**做法**：按 `services/backend/src/cli/COMMAND_AUTHORING.md` 的**自注册机制**，只新增 `handlers/cleanup.js` 一个文件即可（别名自动注入、schema 自动补全，无需改 `aliases.js` 或 `router.js`）。

```
khy cleanup            预览：各目标当前占用 + 保留策略（默认，不动数据）
khy cleanup --yes      按保留策略执行
khy cleanup --report   查看上次清理报告
khy cleanup --json     机器可读（供脚本消费）
```

三条纪律与 `clean` 对齐：默认只预览、每项标出保留策略、不做激进删除。别名取 `数据保留` / `保留清理` / `khycleanup`——**刻意避开 `清理`**，因为该别名已被静态表占用并指向 `cleandisk`（静态别名优先，冲突会被静默吞掉）。

### 9.2 让保留策略只有一个真源

命令要展示「保留多久、上限多少」，而这些数值原本全是 `cleanupService.js` 的**模块内私有常量**。若在命令侧抄一份，两处迟早漂移——而**两个不一致的保留期比没有保留期更坏**（用户按 A 预期，实际按 B 删）。

因此新增 `cleanupService.getRetentionPolicy()`：由服务自己只读地导出当前生效的策略，命令只负责展示。命令侧**一个阈值都不写死**（`RUNTIME-001` 零硬编码）。

### 9.3 修补：`khy clean --runtime` 会销毁 housekeeping 隔离区

**这是本轮发现的最严重缺陷。** `clean.js` 的 `RUNTIME_TARGETS` 含 `{ rel: 'tmp' }` 且**无任何排除**，而 `.khy/tmp` 下躺着 131.7 MB 的 `quarantine-20260915`（housekeeping 隔离区）。也就是说：

> 跑一次 `khy clean --runtime --yes`，会把**待人工确认的隔离件全部销毁**，直接违反
> `[DESIGN-LAY-003]` 的 HK-3「**只隔离不删除**；淘汰一律进隔离区人工确认」与 §3
> 「L3 删除 —— **永不执行**」。**那是绕过机制，不叫清理。**

**修补**：给运行时目标加「保留前缀」能力（按名字前缀 `quarantine*` 匹配，不写死日期）：

- 计划侧：命中前缀的子项体积**从「将回收」中扣除**，并登记进既有的 `held` 列表（复用检查点那套「刻意不清 + 说明理由」机制）
- 执行侧：该目标改为**逐个删子项、跳过保留项**，而不是整目录 `rmSync`

**验证**：`.khy/tmp` 报的可回收从 136 MB 降为 **5.1 MB**，131.7 MB 隔离区出现在 `held` 中并附 HK-3 理由。修补前它会静默消失。
