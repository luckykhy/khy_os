零、结论先行（含一处前提纠正）#

#问题现状核验结果一句话结论
1organize.py 零接线前提已过期 —— check:wiring 现在 exit 0，不再报 TOOLING-005它变成假绿了，比原来更危险；真正的缺口（PR 门不跑它）依然存在
2体积守卫未登记事实成立，但初版方案写错了正确解法是接线并登记既有的 scripts/ci/check-dependency-size.js（它已实现同一套设计且 --strict 实测 exit 0），不是新建检查器

必须先纠正的前提：问题 1 不是「报两条红」#

你描述的状态是「check:wiring 报 TOOLING-005 两条」。实测现在它通过了：

$ npm run check:wiring
check-wiring 通过：72 个检查器全部接线（豁免 9 项），登记别名与规则绑定均无死指针。
EXIT=0

但它不是因为被接线而变绿的。实测证据链：

探针结果
organize.py 的引用面（wiring.references）仅 ["package.json"]
LAYOUT-004 在 manifest 中的形态kind: "enforced"、wired: true、surfaces: ["package.json"]
grep organize .github/workflows/ .githooks/空（没有任何 workflow 或 hook 调用它）
`git show HEAD:package.json \grep organize`
package.json 修改时间09-16 20:26（本会话期间被并发会话加入）

根因是守卫的判据本身有洞。scripts/ruleguard/lib/wiring.js 的 S1 采集面：

surfaces[rel] = Object.values(JSON.parse(text).scripts || {})
  .filter((value) => typeof value === 'string')
  .join('\n');

它把 package.json 里全部 scripts 的值都当作「门面」，不区分 check:*（门）与 maintenance:*（人工命令）。于是任何人往 package.json 塞一行 "maintenance:organize": "python scripts/maintenance/organize.py"，就能把一条 gate=pr 的规则从 declared 提成 enforced，而 checkRuleBindings() 的第 3 项检查（「声明的执行器未挂到任何门」）就此被绕过。

待修的是这个洗白通道，不只是 organize.py 那一行。

另有一处结构性事实：wiring.checkerFiles 共 72 个，全部位于 scripts/ci/。checkOrphans() 只遍历这些文件，所以 scripts/maintenance/organize.py 从来不在反孤儿子检查的射程内 —— 它只能靠「规则绑定」那一路被看见，而那一路现在被绕过了。

这不是孤例：同一类缺陷实测 30 / 67#

顺着这个洞做了一次全量可达性审计（只读探针，判据 = 从「聚合门 + workflow + hook」出发做传递闭包，跟随 npm run <目标>）：

门入口数 = 36  |  可达脚本数 = 46
scripts/ci 别名总数 = 67
=== 聚合门不可达的 scripts/ci 检查器别名：30 个 ===

67 个挂在 scripts/ci 上的别名里，有 30 个（45%）从任何门都到不了 —— 它们只有「自己定义自己」那一行引用，而 check:wiring 恰恰把别名定义行也算作接线面，于是全部判绿。

其中最值得注意的不是数量，而是中招的是哪几条：

别名检查器它本该守护的规则
check:build-rootscripts/ci/check-build-root.jsLAYOUT-005 构建产物单一根 声明的 enforcement
check:ai-gatewayscripts/ci/check-ai-gateway.jsGW-002 AI 模型降级与熔断规范 声明的 enforcement
check:dep-sizescripts/ci/check-dependency-size.js依赖体积预算（目前无任何规则登记它，见第二节）
check:gov-statusscripts/ci/check-gov-status.js治理状态（另一会话 09-16 02:06 新增，曾被其审查报告判为「零接线」，后来只补了别名、没补门）

逐条核验（grep workflow/hook 命中数 + 聚合门命中数，并排除 9 项豁免）：

检查器workflow/hook 命中聚合门命中在豁免清单
check-build-root00否
check-ai-gateway00否
check-gov-status00否
check-lifecycle-policy00否
check-dep-size00否

wiring-exemptions.json 的 9 项豁免是另一批（check-core-safety.js、security-scan.js 等），不包含上述任何一个。

所以问题 1 的准确表述是：不是「一个文件忘了接线」，而是「检查器零接线」这件事从未被真正测过 —— 判据弱到可以被别名定义行满足。修 organize.py 只是修一个症状；修判据（§1.3）才是修病。

一、问题 1：把每日巡检真正接进门#

1.1 一个绕不过去的前置事实：organize.py 不会失败#

scripts/maintenance/organize.py 的 run() 尾部：

        print(f"报告: {OUT_ROOT / 'reports' / f'khy-os-{date}.md'}")
        return 0                      # ← 恒 0

除「仓库不存在」返回 2 外，无论发现多少孤立 html / 产物 / 命名违规，一律 return 0。
它现在是一个纯报告器。直接把它塞进 pr-gate.yml 会得到一个永远绿的空步骤 —— 这正是仓库最忌讳的「纸面门」。

所以接线的前提是先给它一个可失败的档位。

1.2 改动点 A：让执行器具备门的能力#

A1. scripts/maintenance/organize.py 新增 --check 档（棘轮语义）

项内容
位置main() 的互斥组（现有 --report / --apply）
行为扫描后与基线比对，超标返回 1，未超标返回 0；--apply 行为不变
基线文件新增 scripts/ci/organize-baseline.json（与仓库其他棘轮基线同址，便于 --promote 风格统一）
纳入棘轮的计数orphan_html、artifacts（_产物 条目）、badname、bigfile、根目录镜像数
仅报告不入棘轮research（隔离候选，本就该有时存在）、symlinks（junction 属合法设施）

为什么用棘轮而不是硬阈值：仓库其余门（check-code-standards、check-pattern-coverage、check-repo-layout）都是「只降不升」的基线棘轮。用绝对值阈值会与既有约定不一致，且会让第一次接入就卡在存量债上。

A2. package.json 加本地别名，并挂进本地总门

"check:organize": "python scripts/maintenance/organize.py --check",

然后追加到 check:structure 链尾（该链现含 18 个子检查，本就包含 check:wiring）：

// 在 check:structure 链尾追加新增目标（别名定义见上）
"check:structure": "npm run check:layout && ... && npm run check:proposal-index && <追加 check:organize>"

check:structure 是 package.json 里既有的本地总门，且 TOOLING-005 规则卡原文写的正是「治理检查必须同时在根 check:structure 与 PR gate 注册」—— 这就是规则自己指定的落点，不要另造入口。

A3. .github/workflows/pr-gate.yml 加 CI 步骤

在 Check checker wiring（node scripts/ci/check-wiring.js）之后插入：

      - name: Check repo hygiene (organize)
        run: python scripts/maintenance/organize.py --check

注意 Python 运行时的落位：Contract checks job 当前没有 actions/setup-python（只有 200 行起那个 Python syntax job 有）。两种做法：

  • 方案一：给 Contract checks job 补 actions/setup-python（多一次 setup，但步骤语义集中在同一 job）
  • 方案二：把这一步并入既有 Python syntax job（复用其已装好的 Python，零额外 setup）

建议方案二 —— 该 job 已在收集变更 Python 文件，环境现成，且避免给主 job 增加 setup 耗时。

A4. 每日巡检的落点（解决 gate 与「每日」的语义冲突）

LAYOUT-004 的 gate 字段写 pr，但它的 grants 写的是「授权每日自动巡检并隔离白名单内超期临时文件」。这两者不是一回事：

档位触发用途是否阻断
--checkPR / 本地 check:structure防新增杂物是
--apply每日定时隔离白名单内超期临时文件否

建议新增 .github/workflows/repo-hygiene.yml：

name: Repo Hygiene
on:
  schedule:
    - cron: '17 3 * * *'        # 每日 03:17 UTC（避开整点高峰）
  workflow_dispatch:
jobs:
  organize:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.13' }
      - run: python scripts/maintenance/organize.py --apply
      - uses: actions/upload-artifact@v4
        with:
          name: housekeeping-report
          path: .khyos/housekeeping/**

先例：codeql-analysis.yml 是当前唯一带 schedule: 的 workflow，所以定时 workflow 本身不违反仓库惯例。

1.3 改动点 B：堵住洗白通道（这才是问题 1 的根因）#

B1. scripts/ruleguard/lib/wiring.js —— 给门面分类

surfaceTexts() 现在把 S1（package.json）、S2（workflows）、S3（hooks）、阶段表混成一个字典，下游无法区分本地与 CI。改动：让分类信息随 surfaces 一起透出。

  • S1 package.json（含 workspace 包） → local
  • S2 .github/workflows/*.yml → ci
  • S3 .githooks/* → ci
  • STAGE_TABLE_FILES（qualityGateStages.js / releaseGateStages.js / quality-gate/index.js / release-gate.js） → ci

B2. scripts/ci/check-wiring.js —— checkRuleBindings() 加一条

现行逻辑（第 127–133 行）只在 kind === 'declared-uwired' 时检查门；而 kind 一旦被 S1 提成 enforced 就整段跳过。补一条与 kind 无关的硬检查：

gate ∈ {commit, pr, release} 的规则，其执行器必须至少被一个 CI 侧门面引用；仅被 package.json 的非 check:* / 非 gate:* 脚本引用，不算挂门。

这条同时修掉两个问题：① 人工维护脚本不再能把规则洗成 enforced；② 「本地与 CI 双注册」这个规则名终于与判据一致（现状判据只要求「≥1 个面」，是单注册语义）。

B3.（比 B2 更关键）加「可达性」判据 —— 别名定义不算接线

B2 只堵住了「人工脚本」这一条路径。§零那 30 / 67 说明还有更深的一层：别名定义行本身就含检查器路径，于是自己把自己判成已接线。所以必须从「字符串出现过」升级为「从真实门入口可达」：

一个 scripts/ci/ 检查器只有在满足下列任一条件时才算接线：
① 其别名被某个聚合门传递可达（check:structure / check:changed，跟随 npm run <目标> 展开）；
② 其路径被 .github/workflows/*.yml 或 .githooks/* 直接引用；
③ 否则必须进 wiring-exemptions.json（带 reason + until）。

即把 wiring.js 现有的「surfaceTexts 里出现过」改成「从门入口做传递闭包」，并把闭包根限定为真实的门入口，而非「package.json 的任意一行」。

这一步会让 check:wiring 从绿变红、爆出约 30 条 —— 这是对的：它终于如实反映现状。因而必须与「补门」同批推进，否则会把门锁死在红色上。建议分两步：先按 B3 落地判据并把 30 条全部登记进豁免清单（带 until 到期日，形成一个可见的收敛清单），再逐条补门并消豁免。

B4. scripts/tests/ruleguard.test.js 补用例

该文件已有引用 TOOLING-005 的断言（第 318、421 行）。新增两个反向用例：
① 执行器只被 maintenance:* 引用时应报错（锁死 B2）；
② 检查器只有自己的别名定义时应报错（锁死 B3）。

1.4 改动点 C：一处需要你裁决的语义冲突#

LAYOUT-004 同时声明了 gate: pr（阻断）与「每日巡检」（非阻断）。二者只能偏重一个。三个选项：

选项做法
C1（推荐）保持 gate: pr，加 --check 档（A1）使其真的能阻断；每日 --apply 作为独立 workflow（A4）
C2把 gate 改为 advisory，只做每日巡检不阻断 —— 但这与「门」的定位相悖，且会让体积/杂物无门可守
C3保持现状（纯报告），仅靠 --report 输出给人看 —— 不推荐，等于承认这条规则不设防

2.2 改动内容（5 处，必须原子提交）#

⚠️ 方案修正（初版写错了）：初版建议新建 scripts/ci/check-repo-size.js。实测后否掉了 —— scripts/ci/check-dependency-size.js 已经存在且已经实现了同一套设计，新建等于造第二份会漂移的口径，正是本仓 RUNTIME-001 与反重复检查要防的事。

既有检查器实测（node scripts/ci/check-dependency-size.js --strict --no-bytes → exit 0）：

它已有的能力实测
--strict（超预算 exit 1）/ --update（重写基线）✅ 就是棘轮语义
基线文件 scripts/ci/dependency-size-baseline.json✅ 已存在（5.6 KB，人可读、进版本库）
三条预算线：dev / prod / bundle（发布产物）✅ 已实现
「包数=硬预算，字节=容差报告」的确定性口径✅ 已在文件头给出完整论证（且理由比初版更准：npm 提升顺序、@esbuild/* 按平台挑包、CRLF 都会让字节跨机漂移）

它缺的只有两件事：① 没有接线；② 没有任何规则登记它。 所以问题 2 的正确解法是「接线 + 登记」，不是新建。

① 接线既有检查器（唯一真正缺的东西）

package.json          "check:dep-size": "node scripts/ci/check-dependency-size.js --strict"
                      并把 check:dep-size 追加进 "check:structure" 链尾
.github/workflows/pr-gate.yml   加一步（或并入既有 Python/Node 检查 job）

注意 check:dep-size 当前有两个形态：默认（报告态，永远 exit 0）与 --no-bytes（跳过磁盘度量，快）。挂门必须用 --strict —— 否则又是一个永远绿的步骤，与 §1.1 里 organize.py 恒 return 0 是同一个坑。
--no-bytes 适合放在 PR 门（快、且字节本就只作报告）；完整度量建议放每日 workflow。

② 若要覆盖 .git 与工作树洁净度 —— 在既有检查器内加预算线，不新建文件

既有检查器只度量依赖与发布产物，不覆盖本次三大膨胀源中的另外两块。若决定纳入，应作为它的第四条预算线实现：

#指标来源口径建议
1未跟踪且未被忽略的文件数git ls-files --others --exclude-standard硬阈值（如 200）。它反映「忽略规则是否失效」，属配置正确性，不该随基线漂移
2.git 体积 + 松散对象数.git 目录字节数、git count-objects -v 的 count棘轮基线（只降不升），对应本次 2,001 松散对象 / 280 MB

建议顺序：先只做 ①（接线）落地并跑一两周，再决定 ② 是否必要。

2.3 为什么必须原子提交（这里有个必红的坑）#

scripts/ci/check-wiring.js 的 checkOrphans() 会遍历全部 scripts/ci/ 下的检查器，只要某个检查器没被任何门面引用就直接报 零接线 并 exit 1。

推论：任何新检查器若不在同批接线，会让 check:wiring 立刻变红。 —— 这也正是另一会话的 check-gov-status.js 至今只补了别名、没补门的原因（见 §零）。

按修正后的方案，必须同批落地的是这 5 处：

                       并追加进 "check:structure" 链
.github/workflows/pr-gate.yml   在 "Check checker wiring" 附近加一步

注意：scripts/ci/check-dependency-size.js 与它的基线都已存在，本方案不新增任何检查器文件 —— 所以严格说这里没有「新检查器孤儿」风险。但接线与登记必须同批：一旦 check:structure 里出现 check:dep-size，check:wiring 的 kind 会把它从「仅本地别名」提成 enforced，此时若 B3 的可达性判据已落地而 workflow 步骤还没加，CI 侧仍判不达标。先加 workflow 步骤，再改 check:structure。

三、问题 3：git 对象库维护周期化#

3.1 现状（全部实测，只读）#

配置值来源影响
gc.auto未设置 → 默认 6700—实测曾有 2,001 个松散对象，远低于 6700，自动 gc 永不触发 ← 这正是 280 MB 能积累起来的原因
gc.autoPackLimit未设置 → 默认 50——
maintenance.autofalsefile:.git/config⚠️ 仓库里被显式关掉了 —— 意味着 git maintenance run --auto 会空跑
maintenance.repo未设置——
core.fsmonitortruefile:.git/config正常（fsmonitor 守护进程本就常驻，非故障）
pack.compression6file:.git/config✅ 已正确，未来 gc 不会重新膨胀

关键更正：仅「启用 git maintenance」不足以解决问题。maintenance.auto=false 是一个隐性阻碍——它会让 git maintenance run --auto（含计划任务触发的自动任务）直接 no-op。所以要么把它改回 true，要么改用 gc.auto 路线。

3.2 分档方案#

Tier 1 —— 零系统痕迹（只改仓库内 .git/config）#

cd /d/Portable/khy-os

# 让内建 auto-gc 真正会触发：2001 个松散对象的历史证明默认 6700 形同虚设
git config gc.auto 500
git config gc.autoPackLimit 20

# 解开那个隐性阻碍，让 maintenance 的 --auto 档恢复工作
git config maintenance.auto true
项说明
痕迹范围仅 D:\Portable\khy-os\.git\config，不出仓库、不碰系统计划任务、不改全局配置
数值说明gc.auto 500 是策略选择：过大（6700）不触发，过小（如 50）会让每次提交都跑 gc。500 对应「约每 500 个松散对象回收一次」，对本仓的提交节奏是合理折中
单独是否足够基本足够。git 在 commit / merge / receive-pack / am 后会自动调 git gc --auto，而本仓持续有提交

Tier 2 —— 零系统痕迹（仓库内 hook，可选）#

若还希望跑 incremental-repack / commit-graph 这类内建 gc 不覆盖的任务，在 .githooks/post-commit 追加：

git maintenance run --auto --quiet || true
注意说明
前置必须先做 Tier 1 的 maintenance.auto true，否则这一行是空操作
既有缺陷.githooks/post-commit 目前有一个已知路径 bug（报 Cannot find module 'D:\d\Portable\khy-os\scripts\sync\mirror-sync.js'，多一层 d\；发生在提交完成之后，不影响提交）——建议先修它再往里加东西，否则会叠加一个新的静默失败点
代价每次提交多一次 --auto 判定（无事可做时开销很小）

Tier 3 —— 有系统痕迹（需你本人执行，我不代跑）#

git maintenance register          # 写 ~/.gitconfig 的 maintenance.repo
git maintenance start             # 写 Windows 计划任务
项内容
register 的痕迹改写全局 ~/.gitconfig（加 maintenance.repo）—— 这也是仓库外的痕迹，只是不落在计划任务里
start 的痕迹在 Windows 计划任务注册一项，名称形如 Git Maintenance (<路径哈希>)
查看痕迹schtasks /query /tn "Git Maintenance*" /v /fo LIST（PowerShell）
完整回退git maintenance stop（移除计划任务）→ git maintenance unregister（清全局 config）→ git config --global --unset maintenance.repo
我的判断Tier 1 已能覆盖本次问题（松散对象 2,001→0、.git 922.8→108.3 MB 已证明回收链路有效）。Tier 3 的价值是「不依赖是否有提交发生」，属于锦上添花。是否承担计划任务留痕，由你决定。

四、三者的相互关系与建议执行顺序#

三项不是并列关系，问题 3 的复发要靠问题 2 守住：

问题 2 的体积守卫  ──防──▶  问题 3 的二次膨胀
（把 .git 体积与松散对象数纳入 pr 门）

git gc 只解决「当下 280 MB」，不解决「下一季度再长回来」。本次已验证 pack.compression=6 正确、忽略规则已补齐，但没有门在看着 .git——所以 #2 的第 2 项指标（.git 体积 + 松散对象数）是 #3 的长期闭环。

建议顺序：

  1. 问题 3 / Tier 1（零痕迹、最独立、立刻止血）——可最先做
  2. 问题 1 / A1→A2→A3（先给执行器加 --check，再接本地与 CI）——再做 1.3 的加严（B），顺序反了会让 check:wiring 先红
  3. 问题 2（等登记表并发落定 → 原子落地 5 处 → 更新覆盖率基线）
  4. 问题 1 / A4 + Tier 3（定时巡检与计划任务，两者都涉及「定期」语义，可一并决策）
