丢弃 HQ + 保留多机协作：可行方案（修订版）#

前置条件（用户已确认）：① 多机协作是刚需；② 要丢弃 khy-os-hq 这个独立仓库。
调研日期 2026-09-17。本文取代前一份《可行性调研》的方案取舍部分。

结论：这两条可以同时满足，但方式不是「把 HQ 搬进 khy-os」，
而是 「把 HQ 的能力吸收进 khy-os 的现有机制，然后废弃 HQ 仓库」。
khy-os 已经具备承接的全部基础件，不需要新建子系统。

一、先纠正一个关键认知#

前一版调研驳的是「把 HQ 目录搬进 khy-os」—— 那条路的致命处在于
HQ 的 7 个脚本靠向上四级推算 PORTABLE_ROOT 来定位 khy-os（hq_common.py:26-29），
嵌进去就找不到宿主；且 hq_check.py 会递归扫整个 khy-os（35 → 3985 文件）必然报错。

但你要的其实不是「搬家」，是「废弃这个仓库」。 这两者解法完全不同：

搬家（已否决）废弃仓库（本方案）
HQ 脚本被迫在 khy-os 内部运行 → 路径地基崩不迁移、不运行 → 问题消失
HQ 数据嵌入 khy-os 树 → 被 hq_check 自扫改为 khy-os 的一等公民数据
HQ 多机同步两仓编排逻辑被迫重写直接复用 khy-os 已有的 git 通道
代价来源推倒地基一次性数据迁移 + 几条命令

判据：HQ 的价值 = 提示词库 + 任务/Bug 状态 + 机械检查。
这三样都可以是 khy-os 内的数据与命令，不必是另一个仓库。

二、khy-os 已有的承接件（实测，无需新造）#

HQ 的能力khy-os 现有对应物实测结论
任务/Bug 状态真源.ai/ 已入库（git ls-files .ai = 4 个 .md，且带 .html 孪生件）✅ 已有「入库的状态目录」先例，不必新发明
多机同步通道khy-os 自带 3 个远端（origin / gitee / khy-mirror）✅ 通道现成，HQ 的 sync.py 双仓编排是多余的一层
任务服务层taskControlService / taskClosure / taskScheduler / taskDecomposer / planModeService / goalModeService / todoStorePath 等 ~30 个模块✅ 任务基础设施已相当完备
机械检查scripts/ci/ 61 个检查器 + ruleguard 门禁体系 + check-wiring✅ HQ 的 hq_check.py 七组检查大部分可被现有体系吸收
CLI 命令src/cli/handlers/ 152 个自注册 handler✅ 加命令是常规操作（自注册，无需改路由）
AI 指令文件AGENTS.md（42 KB，compat 链全量注入）+ CLAUDE.md + docs/10_规范/[DESIGN-DOC-002] 标准✅ 有标准可依（DOCS-003，22 场景矩阵）
规则登记与接线RULES-REGISTRY.json + [DESIGN-ARCH-111] 三步接线✅ 新规则有明确落点流程

关键结论：不需要移植 HQ 的脚本，只需要移植 HQ 的数据与知识，
并把「下一步做什么」变成 khy-os 的一条本地命令。

三、方案：能力吸收（推荐执行）#

3.1 落点设计#

khy-os/
├── .ai/                          # ← 已入库的状态目录（沿用既有先例）
│   ├── MAP.md / GUARDS.md        #   （现有）
│   └── hq/                       # ← 新增：HQ 数据的新家
│       ├── ROADMAP.md            #   路线图（人读）
│       ├── PROGRESS.json         #   任务状态（机读真源）
│       ├── BUGS.json             #   Bug 状态机（机读真源）
│       ├── MODELS.json           #   模型能力档案
│       └── CONTEXT.md            #   架构速查 + 工程红线（AI 领域注入）
├── prompts/hq/                   # ← 新增：19 条自包含提示词（迁移自 HQ prompts/）
├── docs/10_规范/
│   └── [DESIGN-HQ-001] 协作指挥规范.md   # 规则真源（PROCESS-006）
└── services/backend/src/cli/handlers/
    └── hq.js                     # ← 新增：khy hq <子命令>

为什么放 .ai/hq/ 而不是根目录：.ai/ 已是「入库的 AI 元数据目录」，
有先例、有孪生件惯例，且不撞根目录白名单（check-repo-layout.js:124 只管根级 .md）。
prompts/ 放根级需在 DESIGN-LAY-005 §1.4 登记为例外目录（门槛见该节）。

3.2 命令面（替代 HQ 的 7 个脚本）#

一条 khy hq 命令族，覆盖 HQ 现有的全部功能：

HQ 原命令新命令说明
next.py --statuskhy hq status局面总览（含模型路由建议）
next.pykhy hq next领取下一步提示词（自动选最高优先级）
next.py --bug X --copykhy hq next --bug X指定 Bug，可直接 --copy
next.py --verify Xkhy hq verify X回归验证提示词
new_bug.pykhy hq bug new "标题"登记 Bug
update_status.pykhy hq bug set X <状态> / khy hq task set T-XXX <状态>推进状态机（非法迁移当场拒绝）
hq_check.py并入 npm run check:structure见 §3.3
sync.py删除khy-os 自身 git 通道已足够（见 §3.4）
check_sync.py删除同上

3.3 机械检查的去处（不要新建第 62 个检查器）#

HQ 的 hq_check.py 七组检查，逐条映射：

HQ 检查处置理由
portability（零盘符硬编码）删除HQ 自身铁律；khy-os 对应规则是 RUNTIME-001（已有守卫 check-agent-rules.js）
meta（JSON↔MD 一致性）⚠️ 降级为命令内校验数据一致性在 khy hq 命令的写入路径上强制，不单独立门
prompts（提示词质量）⚠️ 降级为 check:agent-docs 的一个场景提示词属 AI 指令文件，已有标准
drivability（双入口同步）⚠️ 同上并入 DOCS-003 场景矩阵
autopull_task删除计划任务方案变更（见 §3.4）
sync_readonly删除sync.py 已删
merge_flow删除属 khy-os 侧 git 操作，走 PROCESS-001

纪律依据（MEMORY §七.2）：新检查器一旦落 scripts/ci/，
check-wiring.js 就要求它必须有门引用，否则 error。
而 HQ 的这些检查大半是自有流程的自检，搬进 CI 属职责错配。
能落在命令写入路径上的约束，就不要升级成仓库级门禁。

3.4 多机协作怎么办（这是你真正的刚需）#

HQ 的 sync.py 是一层多余的编排 —— 它存在的唯一理由是「HQ 与 khy-os 是两个仓库，
要协调两者的 pull/push 顺序」。仓库合并后这层编排失去存在理由：

原来（两仓）现在（单仓）
先 pull HQ、再 pull khy-os；--clean-only 要求两仓都干净只需 pull 一个仓库
收工：hq_check 全绿 → commit HQ → （可选）push khy-os收工：npm run check:structure 绿 → commit → push
autopull 计划任务跑 sync.py --push-only --push-khyos --clean-only改为 khy-os 自己的 autopull（见下）

新的多机协作流程（更简单，且消灭了undefined那个「嵌套仓库导致 --clean-only 永不触发」的前科）：

# 开工
git pull --ff-only                    # 只拉一个仓库了
khy hq status                         # 看局面

# 干活
khy hq next                           # 领取提示词
# ...在 khy-os 内执行...

# 收工
khy hq task set T-002 done --note "..."   # 回填状态
npm run check:structure                   # 门禁（含原 HQ 检查吸收进来的部分）
git add -A && git commit -m "..." && git push

autopull 计划任务：改为在 khy-os 仓库跑
git fetch --quiet && git status 判定 + --ff-only 拉取 + 已提交内容推送。
要点：不再需要 --clean-only 的「两仓都干净」双条件，单仓判定即可 ——
这直接消除了undefined前科的成因。

3.5 数据迁移（一次性，可回滚）#

步骤动作校验
1把 _meta/{ROADMAP.md,PROGRESS.json,bugs.json,MODELS.json,CONTEXT.md} 复制到 .ai/hq/JSON 可解析；任务/Bug 计数与源一致（23 任务 / 8 Bug）
2把 prompts/ 19 个文件复制到 prompts/hq/文件数一致；渲染占位符 {{XX}} 仍完整
3写 khy hq 命令（读 .ai/hq/*.json）状态机非法迁移被拒；--status 输出与原 next.py --status 等价
4补 docs/10_规范/[DESIGN-HQ-001] + 登记 PROCESS-006check:rules / check:gov-rules 绿
5验证多机流程跑通（本次机器 + 另一台）两边 khy hq status 一致
6确认无误后再删 HQ 仓库（先归档，不立刻删远端）—

⚠️ 迁移期双轨：步骤 1–5 完成前，HQ 仓库保持可用（只读使用，不再写入）。
步骤 6 建议先 git clone --mirror 归档一份，确认新流程跑顺 2 周后再废弃远端。

四、诚实代价清单#

代价量级可否避免
写 khy hq 命令（读状态 + 渲染提示词 + 状态机）中（~300-500 行，可拆叶子 + 测试）否，这是核心
迁移 5 个数据文件 + 19 个提示词低（复制 + 校验）否
写 1 篇规范 + 1 条规则登记低（有 [DESIGN-ARCH-111] 三步流程）否
计划任务重写（单仓 autopull）低否
prompts/ 若放根级需登记为例外目录低✅ 改放 docs/ 或 .ai/hq/prompts/ 可免
丢弃 HQ 的 57 个 commit 历史不可逆✅ 先 mirror 归档可缓解
HQ 的「双入口 + drivability 强制」机制中⚠️ 需在 DOCS-003 场景矩阵补新形态，否则会退化

最大的一处损失要明说：HQ 的 hq_check.py drivability 强制
「CLAUDE.md 与 AGENTS.md 必须同步修改」那条机械保障，khy-os 侧
没有等价守卫（khy-os 的 AGENTS.md/CLAUDE.md 是两份独立文档）。
迁移时要么补一条场景，要么接受这条保障的降级。

五、三个必须你拍板的决策点#

#决策选项

| 1 | HQ 历史怎么处理 | (a) git clone --mirror 归档后废弃远端 ← 推荐
(b) 直接把 57 个 commit 并入 khy-os（rewrite，风险高）
(c) 直接删（不可逆） |
| 2 | 提示词放哪 | (a) .ai/hq/prompts/（不入根目录，免登记例外）← 推荐
(b) 根级 prompts/（需 DESIGN-LAY-005 §1.4 登记例外） |
| 3 | khy hq 命令的首要入口 | (a) 纯本地命令（不联网、零依赖）← 推荐
(b) 加 Web API 端点（可远程查看，但多一处维护） |

六、建议的执行顺序（每步独立可验收，遵守「一次提交只做一步」）#

  1. 写规范：docs/10_规范/[DESIGN-HQ-001] 协作指挥规范.md（含数据契约、状态机、khy hq 命令面）
  2. 迁移数据：.ai/hq/* + 提示词（双轨期，HQ 仍可用）
  3. 写命令：khy hq status / next（最小可用；先不做 bug new/set）
  4. 补状态写命令：khy hq task set / bug set（带状态机校验）
  5. 重写 autopull：单仓版
  6. 补规则登记：PROCESS-006 + 接线
  7. 跑通双机验证
  8. 归档并废弃 HQ（确认 2 周后）

步骤 1–2 是纯增量，零风险；真正的风险点在步骤 8，且那一步有归档兜底。
