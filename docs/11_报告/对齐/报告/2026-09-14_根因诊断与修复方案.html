2026-09-14 根因诊断与修复方案#

本文是一次「测试先行」修复的产物：先为本节各项补测试作为验收标准，再出方案，最后实现。
起点是 2026-09-13～15 三份对齐报告连续三天把同一个问题误判为「密钥失效」。

零、先纠正三份报告里的三个误判#

报告记载实测真相证据
「本机所有 AI 渠道鉴权失效，需修复 key 后重测」密钥完全有效，不是鉴权问题用 .khy/api_keys.json 里的 agnes key 直接打 POST https://apihub.agnes-ai.com/v1/chat/completions，agnes-2.5-flash 与 agnes-3.0-flash 均返回 HTTP 200
「khy 默认渠道已切至 codex 且直接 unavailable，未回退到 relay/agnes」方向对，但没找到原因：是 .env 里的首选通道钉选残留services/backend/.env 第 14–16 行原值 GATEWAY_PREFERRED_ADAPTER=codex + GATEWAY_PREFERRED_STRICT=true + GATEWAY_PREFERRED_MODEL=gpt-5.3-codex-review
「inkRenderSmoke 未定位根因，可能是 loadInk() 动态 import 在 jest 沙箱里挂住/没 resolve」loadInk() 本身是好的——实测 424ms 成功返回、typeof render === 'function'临时诊断用例 Promise.race 计时
（09-13）「3 个测试文件的断言笔误导致 118 用例失败」那 3 个文件早已修好、当前全绿本轮实跑：ccFormat / toolResultTransparency / diffLineNumbers 全部 PASS

为什么这个误判代价最大：buildChannelFailureAdvice 只认 5xx / auth / 限流 / 网络 / 模型不存在五类信号，
没有「首选通道被 strict 钉死导致不回退」这一类。于是真因被翻译成 auth / 404 之类的表象，
排障者自然一天天去查密钥——真因三天未浮出。这是本次修复第 1 项要堵的结构性缺口。

一、AI 通道：真因是首选通道钉选残留#

证据链#

  1. services/backend/.env 被每次启动加载：src/cli/bootstrap.js:42 → path.resolve(__dirname, '../../.env')

= services/backend/.env。

  1. aiGatewayGenerateMethod.js:2072-2081：
   const strictPreferredByEnv = !!(preferredAdapter && preferredAdapter !== 'auto' &&
     String(preferredStrictRaw).toLowerCase() !== 'false');

→ adapter=codex（≠auto）+ strict=true ⇒ strict 生效。

  1. 仓库自己的注释写明 strict 语义：ilinkDispatcher.js:1293

「GATEWAY_PREFERRED_STRICT=true 的含义是「首选通道不可用就硬失败」」。

  1. 本机 codex 无凭据 ⇒ 硬失败，报 codex [unavailable]: OpenAI Codex unavailable，且不回退。
  2. api_keys.json 只有 agnes 一个 provider，而 .env 里 GATEWAY_API_POOL_PROVIDER=relay

—— 池 provider 名与池内容不一致，进一步削弱回退能力（本次未改，见「待人工确认」）。

已实现改动#

  • .env 修复（已备份 .env.bak-20260914-codexpin，只改钉选三行，密钥未触碰）：
  GATEWAY_PREFERRED_ADAPTER=auto      # 原 codex
  GATEWAY_PREFERRED_STRICT=false      # 原 true
  # GATEWAY_PREFERRED_MODEL=gpt-5.3-codex-review   # 原启用

选 auto 而非指定某通道：让网关按健康度级联，不对具体通道做任何预设。

  • 诊断缺口封堵：buildChannelFailureAdvice 新增 channelPinned 信号

（src/services/gateway/buildChannelFailureAdvice.js），并在调用点
aiGatewayGenerateMethod.js:6303 传入 pin: { adapter, strict, hard, fallbackSuppressed }。
钉选是元原因，指引置顶输出，点名被钉通道与两个 env 开关。

验收#

cd services/backend
node --test tests/gateway/buildChannelFailureAdvice.test.js   # 17/17 通过

未能完成的部分（诚实标注）#

端到端复验 在本沙箱内跑不通：khy -p "…" 启动时会调用 reg.exe（硬件探测），
被当前环境的程序黑名单拦截并终止，输出为空。因此「.env 改完后 khy -p 立即恢复」
这条尚未实测确认，只完成了代码路径与配置层面的证明。

请在有权限的终端跑一次以终验：

khy provider status          # 应显示 adapter=auto / strict=false
khy -p "1+1等于几？只回答数字"  # 应拿到正常回答；若仍失败，输出里现在会直接给出钉选指引

一个已确证的潜伏崩溃#

services/backend/src/cli/autoConnect.js 位于 src/cli/，却写成：

require('../../services/crossPlatform/clients/terminalClient')  // → services/backend/services/… ✗
require('../../constants/serviceDefaults')                       // → services/backend/constants/… ✗

真实位置是 src/services/… 与 src/constants/…，只需上一级 ../。
两条 require 都指向不存在的路径，加载即 MODULE_NOT_FOUND。已修复 + 加回归锁。

其余 25 处 unresolved-require 属同一类 off-by-one，应从该规则的全量清单逐条回收：

node scripts/ci/check-repo-layout.js --list=unresolved-require

三、根目录卫生：规则存在，但视野太窄#

规则 1（root-whitelist）只扫 .md/.txt 且只扫文件（见该文件第 125 行注释自述），
因此现场真实的垃圾全部漏网：

  • 1、console.log(r))、console.log((11441+i)+' —— 重定向/贴错的截断名
  • tmp-*.js / tmp-*.log / tmp-*.out / tmp-*.txt —— 20+ 个，实为 约 270 个探测残留
  • _flagcheck.txt、_gitst.txt、_p*.txt —— 下划线开头的一次性笔记
  • .coverage、.tmp_startup_lines.txt —— 构建残留
  • -p/ —— shell 事故目录
  • 还有 tmp-bb.py;、tmp-lean.json; 这类带尾分号的 shell 打字事故

历史 commit dafef34c（「remove 7 stray junk/debug files」）曾手工清过同类垃圾
—— 说明这是复发问题，必须由门禁兜住，而不是靠人记得清。

已实现改动#

scripts/ci/check-repo-layout.js 新增 root-junk 规则：

  • 文件签名（高精度，不试图枚举合法根文件）：^tmp[-_.]、^_、^\d+$、

^\.(tmp|coverage|nyc_output|eslintcache)、[-+]{1,}$、含 shell/jest 元字符 [(){}'"\s]`

  • 目录签名更窄（^-、^tmp[-_.]、元字符）：_产物/对齐 这类是「未登记」而非「垃圾」，

归 layer-registry 管，本规则不得误伤

  • 新增导出 isRootJunkName / findRootJunkEntries / checkRootJunk，

并把 main() 包进 if (require.main === module)——否则 require 它就会因 process.exit(1) 直接杀掉测试进程

npx jest --runInBand --testPathPattern "repoLayoutRootJunk"   # 6/6 通过
node ../../scripts/ci/check-repo-layout.js --list=root-junk   # 打印全部 297 条

四、TUI 冒烟：改超时是必要但不充分（未解决）#

已做#

tests/tui/inkRenderSmoke.test.js:214 的 beforeAll 补了 , 15000。
理由：同文件每个 test 都显式给了 15000（第 242 行，注释还专门解释了冷缓存与 babel 变换的开销），
唯独 hook 漏了，用 jest 默认 5s。Hook 一超时，全部 112 个用例一起失败，
现场读起来像「整个 TUI 树炸了」，而实际什么都没渲染过。

但它没修好问题 —— 诊断结论#

运行inkRenderSmoke套件总计
改前（5s hook）FAIL 18.1s112 失败 / 323 通过 / 435
改后（15s hook）FAIL 34.9s（hook 在 15000ms 超时）112 失败 / 323 通过 / 435
带诊断文件一起跑FAIL 87.7s7 失败 / 429 通过 / 436

同一个 hook，一次烧满 15s 全灭、一次 424ms 顺利通过 —— 是间歇性的，不是「慢」。

进一步实测（临时诊断用例，已删）：

DIAG_LOADINK >>> RESOLVED in 424ms; typeof render=function
DIAG_REGISTERJSX >>> ok

⇒ loadInk() 与 registerJsx() 本身都是好的。09-13 报告猜的「loadInk 挂住/没 resolve」也不成立。
失败概率随运行顺序/文件集合变化，形态是「永不 settle」，指向 jest 的 VM-modules 运行时对
动态 ESM import() 的处理（ink 6.8.0 是纯 ESM：type: module，exports.default = ./build/index.js）。

真正的下一步（建议单独一轮做，不建议顺手改）#

  1. 先量化抖动：把 tests/tui 连跑 5 次，统计 hook 失败率，确认是稳定复现还是概率性。
  2. 主要嫌疑：inkRuntime.js:66-83 的 loadInk() 在同一个 _loading promise 里串了两个动态 import

（import('ink') 之后又 eager import(pathToFileURL(instances.js))）。
instances.js 已确认存在，但第二个 import 是为 getInkInstance() 的同步访问服务的可选优化
（代码注释自称 best-effort）—— 它失败/挂起会连带拖死整个 _loading。
建议：把该 eager import 移出关键路径（改为首次用时再做，或加 fs.existsSync 前置 + 独立超时），
让「ink 本体已就绪」不再被一个可选优化阻塞。

  1. 若仍抖动，检查 jest 配置对 ink 的 ESM 处理（transformIgnorePatterns / 独立 project），

让这个套件以真正的 ESM 入口跑，而不是在 CJS 测试里动态 import。
